# ADR-0027: 资源引擎的接口契约

- **状态**：已接受
- **日期**：2026-08-02
- **相关**：[ADR-0001](0001-agent-based.md)、[ADR-0008](0008-immutable-generation-linkinto.md)、[ADR-0010](0010-runtime-abstraction.md)

## 背景

资源引擎是 mechlet 的核心：它把「一份已解析的期望状态」变成机器上的实际状态。M2 全部围绕它展开，而它的接口一旦被 16 种资源类型实现，就很难改。

需要定死四件事：`Read` 返回什么、`Diff` 的粒度、`Apply` 的幂等契约、失败后的状态。

## 决策一：`Read` 返回三态

### 问题

读完之后可能处于三种境地，而不是两种：资源不存在、存在且读到了、**读不了**（NFS 挂死、systemd 未运行、nsswitch 配错、权限不足）。

把「读不了」归为「不存在」会让 `Apply` 去创建它，然后失败在一个莫名其妙的位置；归为 `error` 则一个坏掉的资源会中止整轮调和。

### 候选

| | 形态 | 评价 |
|---|---|---|
| A | `Read() (Observed, error)`，不存在用 `Observed{Exists:false}`，读不了返回 error | 最简单；但一个读不了的资源中止整轮调和 |
| **B** ⭐ | 三态 `Absent \| Present \| Unknown` | 「不一致」与「无法观测」在 status 中是两件事，运维看到的信息更准确 |
| C | 三态 + 「存在但部分字段读不到」 | 过度设计，实际罕见 |

### 决策：B，并附一条防滥用判据

> **「本环境不适用」不是 `Unknown`，是错误。**

例如 `sysctl vm.max_map_count` 在没有该键的内核上——那是用户选错了内核，应当报错让他知道，而不是静默记为「无法观测」。`Unknown` 只用于「本该能读、但这次读不到」。

没有这条判据，`Unknown` 会变成所有疑难情况的垃圾桶，从而失去信息量。

## 决策二：`Diff` 字段级，行级 diff 在 CLI 层

### 问题

`mechctl component diff` 的输出质量**完全取决于这个选择**。

| 粒度 | 输出 |
|---|---|
| 资源级布尔 | `nginx.conf 不一致` |
| **字段级** | `nginx.conf: mode 0644 → 0640` |

差距是天壤之别：「只有 mode 变了」能让运维**立刻判断这重不重要**，「文件不一致」不能。

### 决策

`Diff` 返回 `[]Change{Field, Want, Got, Kind}`——**纯描述性，不参与 Apply**。

**行级 diff 的计算与呈现在 CLI 层**，资源引擎完全不碰 diff 算法。它只说「`content` 字段：期望是 X，实际是 Y」，怎么显示由调用方决定：短值直接 `X → Y`，长文本走 unified diff，Web UI 换一种呈现。

这一划分把「字段级 diff 会不会太复杂」这个顾虑消解掉了——每种资源类型只需约 10 行来枚举自己的字段，复杂度全在呈现层，而呈现层只写一次。

### 不做敏感内容脱敏

引擎**没有可靠手段识别渲染产物中的敏感片段**：它只知道渲染前的参数值，不知道渲染后文件里哪一段是它。文本替换既不可靠（密码是 `postgres` 这种常见词时会误伤全文），又会掩盖问题。

对应的保护措施是 **[spec 规则 46](../spec/pack-v1.md#19-校验规则汇总)**——引用了 `sensitive` 参数的模板，其渲染目标的 `mode` 的 others 位必须为 0。**保护磁盘上的文件，比脱敏某一次输出实在得多。**

参数值本身的脱敏（spec §7.3）不受影响，照常执行。

## 决策三：`Apply` 幂等，不接收 Diff 结果

### 问题

`Apply` 是否应当接收 `Diff` 的结果，从而「只做需要做的部分」？

### 候选

| | 契约 | 评价 |
|---|---|---|
| **A** ⭐ | `Apply(ctx)` —— 必须自身幂等，不接收 Changes | 接口最小 |
| B | 引擎保证只在有差异时调用 | Apply 可假设有事可做，但与引擎耦合更紧 |
| C | `Apply(ctx, Changes)` —— 接收 Diff 结果作为提示 | 日志能精确到字段 |

### 决策：A

初期倾向 C，理由是「日志能说出改了什么」。**这个理由不成立**——引擎本来就持有 `Diff` 的结果，日志由引擎打印即可，`Apply` 根本不需要知道。

把「日志要精确」和「Apply 要知道差异」混为一谈，是这次差点做出的错误设计。

方案 A 三方面都更好：

- 接口少一个参数
- 实现不必处理「Changes 与实际不符」（Diff 与 Apply 之间世界可能已变）
- 日志格式由引擎统一，16 种资源类型不会各写各的

## 决策四：资源级无事务，回滚能力来自 generation

### 问题

一个资源 `Apply` 失败后，已执行的资源怎么办？

### 决策

```
某资源 Apply 失败
  → 该资源标记失败，后续资源不再执行（可能有隐含依赖）
  → 已执行的资源**不回滚**
  → 由上层决定：切回上一 generation（升级场景）或保持现状上报（首次安装场景）
```

这是诚实的模型——**文件系统操作本来就没有事务**。假装有会导致更糟的结果：一个「回滚」到一半又失败的资源引擎，留下的状态比不回滚更难诊断。

> **回滚能力来自 generation 的不可变与原子软链切换（[ADR-0008](0008-immutable-generation-linkinto.md)），而不是来自资源引擎。**

这一点必须写进文档，否则会有人期待资源级回滚，并在它不存在时认为是缺陷。

## 决策五：`notify` 聚合，Diff 为空不触发

四条规则：

| 规则 | 说明 |
|---|---|
| 收集去重，**调和结束后**统一执行 | 三个 template 都 `notify: reload`，只 reload 一次 |
| **`restart` 吸收 `reload`** | 同一轮里既有 restart 又有 reload，只执行 restart |
| **Diff 为空不触发** | 见下 |
| notify 失败算调和失败 | 配置改了但服务没重载，等于变更没生效 |

### 为什么第三条是硬约束而非取舍

调和每 60 秒跑一次。若无差异也触发 notify：

```
12:00:00  调和 → 无差异 → restart → PostgreSQL 重启（冷启动 30s）
12:01:00  调和 → 无差异 → restart → 又重启
```

**服务会每 60 秒被重启一次，永远无法稳定运行。**

而且这不是「配置一下就能避免」的——`apply` 与周期性调和走**同一条代码路径**，引擎无法区分「用户主动触发」与「定时器到期」。

> **幂等是声明式模型的全部基础。** 一旦调和有了副作用，它就不能被安全地重复执行，而「安全地重复执行」正是持续调和存在的前提。

「我改了外部依赖，想强制重启」是**显式意图**，用 `mechctl component restart`——它绕过调和逻辑直接调 `Runtime.Stop` + `Start`，不影响期望状态。

**原则：显式意图用显式命令，不要让调和循环承担「强制生效」的语义。**

## 决策六：不做自动清理，但上报

Pack 升级后某个资源从声明中消失了（比如去掉了一条 `sysctl`），引擎该不该把它从系统上抹掉？

| 做法 | 评价 |
|---|---|
| 自动反向操作 | ❌ **多数资源没有可靠的「反向」**——`sysctl` 恢复成什么？引擎不知道系统原本的值 |
| 完全不管 | ❌ 留下无人知晓的残留 |
| **记录并上报「已不再声明但仍存在」** ⭐ | 与 `driftPolicy: report` 的哲学一致：先让人知道，由人决定 |

Puppet 与 Chef 都选择「不管理的资源不触碰」。我们在此基础上补上「上报」，让残留可见。

**真正的清理路径是 `component remove`**——那时按逆序调用各资源的 `Remove()`，语义明确、用户显式发起。

## 后果

### 收益

- `Read` 三态让 status 能区分「不一致」与「无法观测」
- `Diff` 字段级 + 呈现层分离，让 CLI 与 Web UI 共用同一份数据
- `Apply` 接口最小，16 种实现的心智负担最低
- 失败语义诚实，不承诺做不到的事务性

### 代价

- **每种资源类型多处理一个 `Unknown` 分支**：约 5 行，但 16 处
- **`Apply` 幂等是实现者的责任，编译器不检查**：需要靠测试保证。每种资源类型的测试必须包含「连续 Apply 两次，第二次无副作用」
- **不做自动清理意味着残留会累积**：以上报缓解，但用户可能忽视报告。UI 需要把「已不再声明但仍存在」做成醒目条目而非日志一行
- **`command` / `script` 类资源没有真正的 `Read`**：它的「实际状态」只能由守卫（`unless` / `onlyif` / `creates`）表达。这是逃生舱的固有代价，也是 [spec 规则 31](../spec/pack-v1.md#19-校验规则汇总) 强制要求守卫的原因
