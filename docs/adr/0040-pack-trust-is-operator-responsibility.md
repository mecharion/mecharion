# ADR-0040: Pack 信任是运维方自己的责任，Mecharion 不做签名校验

- **状态**：已接受
- **日期**：2026-08-13
- **相关**：[ADR-0016](0016-mandatory-pack-signing.md)（本 ADR 取代）、[ADR-0015](0015-offline-first-hermetic.md)、[ADR-0005](0005-pack-logic-payload-split.md)

## 背景

[ADR-0016](0016-mandatory-pack-signing.md) 决定 Pack 签名是必需项，默认 `enforce`：`mechpack sign --key`、节点侧 `/etc/mecharion/trust/` 可信发布者公钥列表、mechlet 物化前校验签名与逐 blob sha256、`packVerification: enforce|warn|disabled` 配置项。

20260809 全面审阅（[REV-010](../review/20260809/06-defect-register-and-roadmap.md)）指出：从 ADR-0016 写下到 M0–M9 走完，这套机制**没有任何一部分被实现**——`cmd/mechpack/main.go` 里 `sign` 一直标着"还没做"且明确写着"密钥分发未定"；`internal/` 全仓库搜不到 `packVerification` 或 `/etc/mecharion/trust` 的踪迹。而 08-security.md、pack-v1.md 等设计文档一直在用"必需项""唯一信任锚""默认 enforce"描述它，形成审阅报告点名的那种状态：**设计说必需，代码全接受**。

## 候选方案与调研

### 方案 A：按 ADR-0016 原样补全签名闭环

实现 `mechpack sign`、密钥生成与分发方案、节点侧信任库管理（增删/轮换/吊销）、mechlet 侧强制校验、`packVerification` 三态配置及其告警。

- ❌ 这是一个独立的小型 PKI 工程：签名算法选型、密钥格式、分发与轮换机制、吊销语义都要从零决定——ADR-0016 自己都承认"密钥管理成为必须……这是真实的运维负担"
- ❌ 规模与本里程碑已经因体量过大而暂缓的 B3（OpenAPI 契约）相当或更大，不是能在验证同一批 P1 缺陷的节奏里顺带做完的量

### 方案 B：签名默认关闭（`packVerification: warn` 或 `disabled`）

- ❌ ADR-0016 引用的 Helm/Docker Content Trust 先例已经证明：默认关闭的信任机制实际采用率趋近于零，等于既背负实现成本又拿不到收益
- ❌ 仍然要做密钥格式、分发、轮换的全套设计，只是校验结果不强制——工程量没有减少多少

### 方案 C：不做签名校验，Pack 信任是运维方自己的责任 ⭐

系统不提供、也不假装提供任何"这个 Pack 确实来自某个可信发布者"的密码学证明。管理员对自己要在 Site 上部署哪个 Pack、来自哪里，负全部责任——这与"装 Pack ≡ 在目标机器上执行 root 代码"这一既有事实本来就是同一件事的两种说法：**如果这一步的信任判断本就必须由人来做，系统提供一层可被绕过、可能疏于维护的签名校验，换来的是复杂度与可用性的双重代价，而不是真实的额外安全性。**

## 决策

**Mecharion 不实现 Pack 签名或可信发布者校验。Pack 内容的真实性/来源可信，由运维方自己保障，不是 mechlet 的门禁。**

具体变化：

- 撤销 `mechpack sign` 子命令的实现计划；`mechpack` 不提供任何签名/验签能力
- 不引入 `/etc/mecharion/trust/`、`packVerification` 或任何等价的强制校验开关
- mechlet **不会**因为 Pack 未签名/发布者不在信任列表而拒绝物化或执行

**保留、且与本决策无关的机制**：Pack 的 blob 已经按 sha256 内容寻址（[ADR-0005](0005-pack-logic-payload-split.md)），`internal/protocol/client.go` 的 `FetchBlob` 在写盘前会校验拉到的字节与文件名里的 sha256 一致，对不上就丢弃重拉。这挡的是**传输/存储过程中的损坏或篡改**，是一个完整性机制，不是身份认证机制——它回答"这份内容和我请求的是同一份"，不回答"这份内容是谁做的、能不能信"。ADR-0016 把这两件事捆在一起描述（"摘要天然是完整性校验，与签名机制无缝衔接"），本 ADR 把它们拆开：完整性校验留下，身份认证不做。

## 理由

### ① 用户明确要求：不要用强校验换复杂度

这不是纯工程判断，是产品定位的选择：Mecharion 面向的是运维方自己决定信不信一个 Pack、自己承担后果的场景，不是面向陌生第三方发布者的公共市场（不同于 npm/PyPI 那种任何人都能发布、消费者互不认识的场景，APT/YUM 的强制签名解决的正是那类问题）。在"管理员本来就要亲自决定装哪个 Pack"的前提下，系统另外维护一套公钥信任库，换来的保护面很窄（挡不住"可信发布者本身写了坏 Pack"，ADR-0016 自己也承认这条），却让**每一次本地开发迭代**（`--dev` 模式）、**每一次引入新 Pack**都多一步密钥相关的操作。这个代价与收益不成比例。

### ② 没有实现的强制项，比没有这个功能更糟

REV-010 的核心问题不是"没有签名"，是"文档说必需、代码全接受"——一个用户读到 08-security.md"签名是唯一信任锚"之后,会误以为系统已经在做身份校验，而实际上任何 Pack、任何来源都会被无条件接受。**明确不做**，比维持这种落差更诚实，也是审阅报告给出的两条可选修复路径之一（另一条是补全，本 ADR 选择了这条）。

### ③ 完整性与身份认证是两件事，只留前者仍然有真实价值

即使不做签名，sha256 内容寻址仍然挡住"传输过程中数据坏了"这类真实会发生的问题（网闸摆渡、U 盘复制、断线重传），且这部分已经实现、不需要新增工作。丢弃身份认证不等于丢弃全部完整性保证。

## 后果

### 收益

- 去掉一个"设计已定、代码全空"的落差，REV-010 的具体症状不再存在
- 不需要投入密钥格式/分发/轮换/吊销这一整块独立工程
- 本地迭代 Pack、引入第三方 Pack 都不再有额外的签名/信任配置步骤

### 代价

- **没有密码学意义上的来源认证**：一个被替换、被篡改（但 sha256 也同步被替换，因而"完整性校验"也测不出来——这是主动攻击而非传输损坏时的真实边界）的 Pack，系统不会拒绝。这个边界必须写清楚：sha256 挡的是意外损坏，不是主动构造的恶意替换
- **信任判断完全在运维方**：装错 Pack、装了被投毒的 Pack，是操作者自己的责任，系统不提供额外的技术兜底
- **离线场景失去"签名是唯一信任锚"的保护**：ADR-0016 原本认为离线场景下没有 HTTPS/registry 兜底，因此签名更重要；本决策接受这一点不再由系统解决，改为运维流程问题（比如：只从可信介质获取 Pack、物理传递链路本身可控）
- **`internal/pack/hermetic.go` 与 `internal/resource/archive.go` 里原先"对抗恶意作者由签名与可信发布者列表处理"的注释不再成立**：这两处代码本身的职责（防路径穿越、hermetic 静态检查）不变，只是不能再假设有一层签名机制兜底更严重的恶意输入——已同步更正注释
- **将来若出现真实的第三方 Pack 生态需求**（陌生发布者、供应链场景），需要重新评估——那时候的取舍前提（谁在发布、谁在消费、能否互相认识）和现在完全不同，届时应写新 ADR，不是复用本次的结论
