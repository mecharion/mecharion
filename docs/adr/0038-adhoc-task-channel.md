# ADR-0038: ad-hoc 命令走独立的 Tasks 流，不塞进期望状态

- **状态**：已接受
- **日期**：2026-08-09
- **相关**：[ADR-0029](0029-push-over-server-stream.md)、[ADR-0001](0001-agent-based.md)、[17-protocol §7](../design/17-protocol.md)

## 背景

M9 要做 `component restart`。它撞上一堵墙：**协议里没有命令通道**。

17-protocol §7 把「在协议里塞业务语义（如「执行这个 hook」）」列为不做的
事，并写下那条根本性的约束：

> `Assignment` 里没有动词。mechlet 收到的是「这台机器上应该有什么」，
> 怎么达成是它自己的事——这正是它在断连时仍能工作的原因。

而 06-state-and-drift 对 restart 的设计恰恰相反：

> 它绕过调和逻辑直接调 `Runtime.Stop` + `Start`，不影响期望状态。
> **原则：显式意图用显式命令，不要让调和循环承担「强制生效」的语义。**

这两句都对，但它们描述的是**两条不同的通道**——而第二条从来没有建过。

decision-log 第 37 条早就规划了 ad-hoc（`mechctl node exec -l role=db --<script>` 
走 agent 通道、不用 SSH），同样只有结论没有形态。

**restart 只是第一个用户。** `node exec`、`component exec`、`logs -f`
全都要踩这条通道，因此它值得单独定一次，而不是为 restart 凑一个特例。

## 期望状态与命令的分界

这不是「哪个更好」，而是**两类语义**，判据是**丢一次会怎样**：

| | 期望状态 | 命令 |
|---|---|---|
| 例子 | 「这个实例该跑着」「这些孤儿不该存在」 | 「重启一下」「跑这条脚本」 |
| 丢一次 | 无所谓，下一轮重新确认 | **就是没执行**，必须告诉人 |
| 断连三天回来 | 照做，仍然正确 | **不该补做**——那三天里世界变了 |
| 结果 | 靠上报观测出来 | 必须逐节点带回来 |

`orphans purge` 被刻意做成了状态（24-lifecycle §2.4），因为「这些目录不该
存在」是一句可以重复确认的话。**restart 不是**：「重启过一次」本质上就是
个事件，而一台断连三天的机器回来之后补做一次重启，是纯粹的伤害。

用户对这一条的表述最清楚：**「如果某个节点掉线了，最终告知用户某个节点
不可达、没有执行重启命令即可。」** 那正是命令语义——不排队、不补做、
如实报告。

## 候选

| 做法 | 送达 | 代价 |
|---|---|---|
| **A. 新开 `Tasks` 服务端流** + 上行结果 RPC | 即时推送 | 每节点多一条长连接与重连逻辑 |
| B. `Subscribe` 流改成 `oneof(Assignment\|Task)` | 即时推送 | 那条流不再只是「期望状态流」；命令与全量下发抢同一条流 |
| C. 搭 `Report` 的便车（`ReportResponse` 带任务） | 轮询，最坏 15s + 15s | Report 是「高频小包」，塞任务进去让它承担两种职责；一次 restart 要等半分钟 |
| D. 把 restart 做成「重启代次」状态 | 随全量下发 | 与命令语义冲突：断连的机器回来会补做一次重启，且拿不到逐节点结果 |
| E. mechd 主动连 mechlet 发命令 | 即时 | 节点要开入站端口，与「零入站」直接冲突（17-protocol §7） |

其它系统的做法：**Salt** 有独立的 event bus 与 job cache（状态与命令彻底
分开）；**Ansible** 全靠 SSH 的一次性连接（没有常驻通道，因此不存在这个
问题）；**Kubernetes** 没有 ad-hoc 命令，`kubectl rollout restart` 是改
annotation——即上面的 D，而它能这么做正是因为 Pod 可漂移、重建代价为零。

## 决策

**A：新开一条 `Tasks` 服务端流，结果走一条上行 unary RPC。**

```protobuf
rpc Tasks(TasksRequest) returns (stream Task);
rpc ReportTaskResult(TaskResultRequest) returns (TaskResultResponse);
```

两条流各司其职，**互不影响**：

```
Subscribe → Assignment   期望状态。没有动词，可重复确认，断连即重推全量
Tasks     → Task         命令。带 task_id，一次性，结果必须回来
```

`Assignment` 因此**一个字段都不用动**——那条 `TestAssignmentHasNoVerbs`
守卫继续成立，而它守的东西也确实没有被侵蚀。

mechd 侧的语义直接来自「谁连着」这个它本来就知道的事实：

```
在线（sessions 里有）→ 推 Task，等结果（超时可配）
离线                 → 立刻判为 unreachable，**不排队、不补做**
```

## 后果

**得到的：**

- 期望状态那条流保持纯净。它是断连自治的地基，值得不被任何「顺手加一个
  字段」侵蚀——而 B 方案的第一步就是那个「顺手」。
- 命令有明确的结果与超时，逐节点可见。`n3 ✗ 不可达，未执行` 是一句
  确定的话，而不是「不知道有没有生效」。
- 命令流断了不影响下发，反之亦然。这与「不用双向流」是同一条理由
  （17-protocol §1），只是这次把它用在了两条流之间。
- `node exec` / `component exec` / `logs -f` 之后直接复用，不必再设计一次。

**代价照实说：**

- **每个节点多一条长连接**，mechd 侧多一份会话表与 goroutine。一个
  1000 节点的站点因此多 1000 条 gRPC 流——它们绝大多数时间空闲，但连接
  本身的内存与 fd 是实打实的。
- **agent 多一套重连循环**。虽然可以复用 Subscribe 那套的形状，但它是
  第二处「断了要重连」的代码，而那类代码的 bug 只在网络不好的时候出现。
- **多了一个必须想清楚超时的地方**：命令等多久算失败？等待期间 mechd
  要占着一个请求。默认给一个保守值（30s），并允许调。
- **它是一条真正的命令通道，将来会被滥用。** 「顺手加个 task 类型」比
  「顺手往 Assignment 里加字段」容易得多。因此 Task 的类型集合要显式
  枚举，加一种就要过一次评审——这条纪律得靠人守，与「Assignment 没有
  动词」当初一样。

**没有做的：**

- **任务不落库、不重试、不排队。** 离线就是离线，如实报告。一个「等它
  上线再执行」的队列会让人以为命令一定会生效，而那是期望状态的语义
  ——真需要那种语义的东西，本来就该做成期望状态。
- **不做任务历史。** 结果回到敲命令的那个人面前就完成了使命。要留痕的
  是审计（已有），不是任务表。
