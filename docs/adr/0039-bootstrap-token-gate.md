# ADR-0039: 首次初始化用一次性 admin token 门禁，不用 PoW/滑块

- **状态**：已接受
- **日期**：2026-08-12
- **相关**：[ADR-0037](0037-login-is-full-privilege.md)、[08-security §3.3](../design/08-security.md#33-初始凭据)、[23-web-ui §3](../design/23-web-ui.md)

## 背景

ADR-0037 定下首访 UI 初始化的模型：`admin` 是唯一账号，在浏览器首次打开时设定口令。这带来一个被明确接受的代价（决策 194）：

> 初始化前存在抢注窗口（默认监听 `0.0.0.0`）。缓解 = 一次性 409 + 启动即 WARN + 审计记来源 IP + 限流。

后来 `Setup.vue` 又加了一套 PoW + 滑块（决策 174/175，抄的是登录页那一套），意图是再叠一层防护。20260809 全面审阅指出（[REV-006](../review/20260809/06-defect-register-and-roadmap.md)）：这套仪式从未接到服务端——`POST /auth/bootstrap` 的请求体只有 `password`，`bootstrapAdmin` 里既不读也不验挑战答案。用户等进度条转到 100%、拖完滑块，那次提交实际上什么都没验证。

## 这个仪式本来就验不动想验的东西

先把"接上"这件事放一边：PoW/滑块防的是**重复尝试**——它让一次自动化撞库的单次成本变高，多次尝试的总成本因此升上去。但初始化抢注不是"猜密码"，是**谁先提交谁赢**的一次性竞赛：攻击者只需要成功一次，而 PoW 只让"再试一次"变贵，对第一次、也是唯一有意义的那次尝试没有任何影响。真把它接上，也只是把"无效仪式"从"完全没验证"变成"验证了一个测不出真正风险的东西"——防护上的收益基本是零，UI 上的等待感却是真的。

这与登录页的 PoW 不同：登录要防的正是"重复尝试慢速撞库"，那里 PoW 有意义。同一套机制套两个不同的威胁模型，其中一个套错了。

## 候选方案与调研

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 接上现有 PoW/滑块 | `bootstrap` 请求体加 `challenge`，服务端复用 `Challenges.Verify` | 如上所述，对一次性竞赛基本无效，纯粹是把"看起来防护"做实成"确实在算，但算的东西答不对问题" |
| B. `/auth/bootstrap` 限制只认回环地址 | `remoteIP(r) != "127.0.0.1"` 直接拒 | 与决策 193 的目标正面冲突："要求先 SSH 敲命令等于把自动化链断在最后一步"——边缘设备常见的用法是"装完之后拿笔记本连过去初始化"，那台笔记本几乎不会是回环 |
| **C. 复用首次启动就有的一次性 admin token** | `bootstrap` 请求体加 `token`，比对 `serve.go` 的 `ensureToken` 生成的那个 | 需要操作者手上有那个 token（见下）——但那正是唯一一件区分"刚装完这台机器的人"与"路过这台机器 IP 的人"的东西 |

C 复用的是**已经存在、已经在解决同一类问题**的机制：`mechd` 首次启动时生成一次性 admin token，只打印一次、同时落盘到 `<confDir>/admin.token`（`0600 root:root`），本来是给 `mechctl` 当 Bearer 凭据用的。它的性质与 bootstrap 需要的东西完全一致——"证明你是刚装完这台机器、看得到它输出或者读得到它文件系统的那个人"，而不是"证明你算得动 Argon2"。

## 决策

**`POST /auth/bootstrap` 的请求体加一个 `token` 字段，服务端拿它去比对启动时生成的 admin token（哈希、定长比较），不对就拒；PoW/滑块从这条路径上整个撤掉。**

```go
type BootstrapBody struct {
    Password string `json:"password"`
    Token    string `json:"token"`
}
```

`API` 在 `serve.go` 构造时把 `ensureToken` 已经算出来的 token 的哈希一并传进去（`BootstrapTokenHash`），`bootstrapAdmin` 用 `subtle.ConstantTimeCompare` 比对，**在调用 `Service.InitializeAdmin`之前**——顺序与 `login` 里"先验挑战再验口令"是同一条纪律：不该做的校验不通过时，不该碰任何有状态的东西。

`Setup.vue` 撤掉 `SliderCaptcha` 与 PoW 进度条，换成一个"初始化令牌"输入框，说明文字指向 `mechd` 启动时打印的那段话与 `admin.token` 文件路径——操作者装完机器时就站在那段输出前面，不需要为这一步单独再连一次。

限流（`Limiter`，与登录共用同一套 IP 失败锁定）继续接在这条路径上——token 本身 192 位熵，暴力破解不现实，但限流是现成的、不接白不接，防的是"脚本写错了一直重试"这类意外，不是这个方案的承重部分。

## 理由

- **不是新发明一个机制，是把已有的两个"这是刚装完的人"信号接到一起。** admin token 已经承担"证明你有权跟这台机器说话"的角色（CLI 的 Bearer 凭据），bootstrap 需要的恰好是同一件事。
- **不违反决策 193 的目标。** 操作者不需要为初始化单独发起一次 SSH/控制台会话——token 就在他们装机时已经看着的那段输出里，复制粘贴一次，不是一次新的往返。
- **抢注窗口被真正关上，而不只是"记录下来、算是尽力了"。** 决策 194 当初接受的是"关不严，但能追责"；这个方案把它升级成"没有 token 就是完成不了"——不知道 token 的网络攻击者，无论抢得多快都赢不了这场竞赛。

## 后果

**得到的：**

- 初始化的安全性来自一个真实起作用的机制，而不是一段看起来在验证、实际什么都没验证的前端仪式。
- `Setup.vue` 变简单：一个输入框，不需要 `useChallenge` 那套轮询 PoW 进度、渲染滑块的逻辑，`SliderCaptcha` 的可访问性问题（REV-012）在这条路径上不复存在——因为它被删掉了，不是被修好了。
- HTTP 层"不该做的校验不通过就不碰有状态的东西"这条纪律与 `login`（先验挑战再验口令）一致，读这段代码的人不需要学第二套约定。具体顺序是：先判"是否已经初始化"（这条判据对谁都是同一个答案，`GET /auth/state` 本来就无鉴权地公开着同一件事，排在最前不泄漏任何新信息），再验 token，最后才调用 `InitializeAdmin`——这个顺序在实现阶段被 `test/webui` 的真机验收撞出来过一次（第一版是"先验 token"，导致"已初始化后重复调用必须 409"这条判据被误判成 401），记在开发日志里，不重复展开。

**代价照实说：**

- **操作者必须还留着装机时的那段输出，或者能读到 `<confDir>/admin.token`。** 如果终端关掉了没保存、也没有文件系统访问权限，初始化就卡住——出路与丢失 admin token 时完全一样（本来就要保留这份凭据）。这不是新增的负担，是把"已经存在的凭据丢失"这条已知代价延伸到了多用一次的场景。
- **`admin.token` 现在身兼两职**（API Bearer 凭据 + bootstrap 门禁）。两者混在一起不是巧合，但确实意味着这个文件的重要性又高了一档；它原本就是 `0600 root:root`，权限模型不需要改变。
- **移除了 PoW/滑块给用户的"确实做了人机验证"的直觉**，即便那种直觉此前就是假的。文案要在 Setup 页说清楚这一步在防什么（"证明你有这台机器的访问权限"），不要留空档让人猜。

## CLI 侧的自动化入口：`mechctl user bootstrap`

浏览器令牌门禁本身仍然要求**一次人的动作**——把令牌从终端输出或
`admin.token` 文件抄进 Setup 页。这对人工部署没问题，但对完全无人值守
的场景（云初始化脚本、批量铺设边缘设备）是一步没人会去做的手动操作，
等于把决策 193 想避免的"最后一步断自动化链"换了个地方重新引入。

**加一条 `mechctl user bootstrap [--password-file <path>]`**，效果与浏览器
初始化完全一样，但不需要人打开浏览器：

```
mechlet install --standalone   # 装完，打出令牌
mechctl user bootstrap --password-file /run/secrets/admin-pw   # 紧接着跑，同一台机器
```

它能省掉"人去抄令牌"这一步，靠的是 `mechctl` 本来就有的零配置读取
——`Client` 解析 token 时已经会依次尝试 `--token` flag、context 配置、
`/etc/mecharion/admin.token`（[08-security §3.2](../design/08-security.md#32-mechd-的-http-接口)），这与 CA 证书的零配置读取
是同一条既有纪律，不是为这条命令新开的口子。命令本身只是把
`Client` 已经解析出来的 token 值，同时当作 bootstrap 请求体里的
`token` 字段发出去——**没有新的信任来源，只是把人工搬运这一步去掉**。

远程执行（在另一台机器上跑 `mechctl` 对着目标 mechd）时，本机零配置
读不到目标机器的 `admin.token`，退回显式 `--token`——与 `mechctl context
set` 一直以来的用法一致，不是这条命令引入的新负担。

代价：多了一条能完成初始化的入口，意味着"谁能读到 admin.token 或
拿到 --token"这个既有的信任边界现在同时决定"谁能通过浏览器初始化"
与"谁能通过 CLI 初始化"——两者本来就是同一份凭据、同一个信任边界，
这里没有新增攻击面，只是多了一条使用它的路径。
