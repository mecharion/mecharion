# ADR-0028：ordinal 一次分配后固化，不由节点名排序推导

- 状态：已接受
- 日期：2026-08-04
- 相关：[ADR-0009](0009-node-volumes-multidisk.md)、[spec §9.3](../spec/pack-v1.md#93-topology-引用)、[14-placement](../design/14-placement.md)

## 背景

`.Topology.Ordinal` 是实例在同角色内的序号，Pack 用它生成**节点身份**：

```
ZooKeeper   myid = ordinal + 1
Kafka       node.id = ordinal（+ 角色偏移）
HDFS        JournalNode 的编号
MinIO       端点顺序
```

规范 §9.3 原先写的是「从 0 起，**按节点名排序**，稳定」。

## 问题

「按节点名排序」**不稳定**。它在成员集合不变时稳定，而成员集合恰恰是会变的。

一个 3 节点 ZooKeeper 部署在 `n2, n3, n4`：

| 节点 | ordinal | myid |
|---|---|---|
| n2 | 0 | 1 |
| n3 | 1 | 2 |
| n4 | 2 | 3 |

运维扩容，加入 `n1`。按名字重排：

| 节点 | ordinal | myid |
|---|---|---|
| **n1** | **0** | **1** |
| **n2** | **1** | **2** ← 原来是 1 |
| **n3** | **2** | **3** ← 原来是 2 |
| **n4** | **3** | **4** ← 原来是 3 |

**三个已有节点的身份全部改变。** 它们数据目录里的 `myid` 与集群配置不再对应：
ZooKeeper 会以为自己是另一个成员，轻则拒绝启动，重则在选举中造成脑裂。
Kafka 的 `broker.id` 变化会让分区副本的归属彻底错乱。

这类故障的恶劣之处在于：**触发条件是一次正常的扩容操作**，而症状出现在
毫不相干的地方（选举失败、副本丢失），排查时几乎不会有人怀疑到序号上。

## 候选方案

### A. 按节点名排序（原方案）

- ✅ 无状态，任何时候都能重新算出来
- ❌ **成员变化即身份洗牌**，如上

### B. 按加入顺序递增，一次分配后固化

- ✅ 已有实例的序号**永不改变**
- ✅ 与[路径固化](../design/04-paths-and-storage.md)、[绑定固化](../spec/pack-v1.md#52-绑定规则)是同一条原则的第三次应用
- ❌ 需要持久化，不能凭规格算出来
- ❌ 删除中间的实例会留下空洞（`0, 2, 3`）

### C. 由用户显式指定

- ✅ 完全可控
- ❌ 把一个引擎能负责的事推给用户，且用户填错时后果同样严重

## 决策

**采用 B：ordinal 在实例首次创建时分配，之后固化，永不重算。**

规则：

| 情形 | 行为 |
|---|---|
| 新实例 | 取该角色**当前最大 ordinal + 1**；首个为 0 |
| 已有实例 | 原样保留，与节点名、成员集合都无关 |
| 实例被移除 | 序号**不回收**，留下空洞 |
| 同一节点上移除后重建 | 视为新实例，拿新序号 |

**序号不回收**是刻意的：回收意味着新实例可能拿到一个刚被释放的编号，
而集群里其它成员的元数据中可能还留着对旧成员的引用——这正是要避免的
「身份复用」，与[不删除 user/group](../design/11-resource-engine.md#user--group)
的理由完全一致。

固化值存在 mechd 的 `role_instances` 表中，是**期望状态的一部分**，
随备份一起走。

## 代价

- **序号有空洞**，`0, 2, 5` 这样的序列会让人第一眼觉得是 bug。因此
  `mechctl component show` 必须显式展示序号，并在有空洞时说明原因。
- **不能凭一份 site.yaml 算出全部序号**——重建 mechd 数据库而不带上
  它，会让所有实例被当成新实例重新编号。这条要写进备份与恢复文档：
  **mechd 的数据库是期望状态的一部分，不是缓存。**
- 需要一条迁移/修复路径：`mechctl component set-ordinal`（受限、需确认），
  用于灾难恢复时把序号手工对回去。

## 后果

- `.Topology.Ordinal` 的语义从「可推导」变为「已分配」
- 规范 §9.3 的措辞需修正
- 放置阶段的输出不再是纯函数，而是「读取已有分配 + 为新实例分配」
