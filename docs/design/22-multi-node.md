# 多节点：加入、身份与分批 Rollout

M7 把「一台机器」变成「一群机器」。它不新增任何用户可见的概念——
Site / Node / Component / Rollout 在 M3 就定形了，单机形态一直在用它们。
M7 补的是**这些概念在多台机器上真正成立所缺的那几样东西**。

## 0. 现状：第二台机器现在加不进来

不是「不好用」，是**真的做不到**。三处各缺一半：

| 环节 | 现状 |
|---|---|
| 节点入册 | 全仓库只有 `mechlet install --standalone` 会写 `nodes` 表（`install.go:361`），而它写的是本机 |
| `mechctl node add` | **不存在**——`backend.go:41` 的错误信息让用户去敲一条没有的命令 |
| 传输 | mechd 只监听 unix socket（`serve.go:153`），没有 TCP gRPC 监听 |

`rollouts` / `rollout_batches` 两张表从 `00001_init.sql` 起就在，
`rollout_batches` **一次都没被写过**——M6 的单机 Rollout 直接用 `rollouts`。

## 2. 要定的问题

### 2.1 一台新机器怎么进到册子里

这是整个里程碑的第一道门，也是唯一一处**安全姿态与易用性直接冲突**的地方。

**调研过的做法：**

| 项目 | 机制 | 代价 |
|---|---|---|
| Kubernetes | kubelet TLS bootstrap：bootstrap token 换取**提交 CSR 的权限**，CSR 需被批准（可配置自动批准） | 两段式，概念多（CSR 对象、审批者、签名者） |
| Salt | minion 生成密钥并**自报名字**，master 端 `salt-key -a` 人工接受 | 简单，但接受之前 minion 一直在轮询；名字可被抢占 |
| Puppet | 同上，`puppetserver ca sign`；`autosign` 可按域名白名单或自定义策略自动签 | autosign 白名单是**基于名字**的，冒名即可绕过 |
| Chef | 预先在 server 上建 client 并下发 validator key | validator key 是长期共享凭据，泄露即全网可加入 |
| HashiCorp Nomad | gossip 加密密钥 + ACL token；节点加入即生效 | 无人工确认环节 |
| Consul | 同上，`auto_encrypt` 用 ACL token 换 TLS 证书 | 同上 |

**共同点**：所有做法都是「先有一个凭据，再换一份长期身份」。分歧只在
**换取的那一刻要不要有人点头**。

**决定：token 即授权，不设人工批准环节**（[ADR-0034](../adr/0034-node-join-and-identity.md)）。
Mecharion 的场景（边缘、门店、几十台到几百台，运维人手少）里，token 是
**带外交付**的——运维自己拿到手上再敲进那台机器——那次交付本身就是点头。
批准式（Kubernetes / Salt / Puppet）每加一台都要人点两次，批量预置
（cloud-init / 镜像）基本走不通，而边缘门店场景恰恰是批量的。

冒名问题用一条更强的约束堵住：**token 可以绑定节点名**。

```bash
mechctl node token create --node store-042 --ttl 30m   # 只能叫这个名字
mechctl node token create --ttl 30m --uses 20          # 批量预置：名字先到先得
mechctl node token list / revoke <id>
```

绑名的 token 只能签出 CN=`store-042` 的证书；不绑名的 token 允许自报名字，
但**不能顶替一个已经签发过证书的名字**——那需要先 `node remove`。

> 「不绑名 + 多次可用」是给批量预置（cloud-init / 镜像）留的口子。
> 它的风险要说清楚：拿到这个 token 的人可以往集群里塞一台机器。
> 因此它有 TTL、有次数上限、可吊销、且每次使用都进审计。

### 2.2 节点身份以什么为准

**证书的 CN，不是请求里的 `node_name`。**

`RegisterRequest` 里有 `node_name`（[17-protocol §2](17-protocol.md)），
那是单机形态留下的——unix socket 上没有证书，只能自报。多节点下如果继续
认它，mTLS 就白做了：任何一张合法证书都能冒充任何一个节点。

因此两条监听两套身份来源，**在同一处收口**：

| 监听 | 身份来源 | 校验 |
|---|---|---|
| unix socket | 隐式（socket 权限 `0600 root:root`） | 用请求里的 `node_name` |
| TCP + mTLS | 客户端证书 CN | **忽略**请求里的 `node_name`；不一致时拒绝并说明 |

不一致时**拒绝而不是静默以证书为准**：静默会让一次配置错误（改了
`--node` 却没换证书）表现成「节点名莫名其妙变回去了」，那是最难查的一类现场。

落地在 `internal/protocol/identity.go` 的 `nodeOf`，**协议层唯一确定节点
身份的地方**。五个 RPC（Register / Subscribe / Report / PushEvents，以及
它们各自读 `node_name` 的分支）全部经过它——散在五处的话，
「某个 RPC 忘了忽略 node_name」就是一个能绕过 mTLS 的洞。

### 2.3 证书的轮换与吊销

**轮换**沿用已有的 30 天规则：mechlet 发现自己的证书剩余 <30 天时，
用**当前仍然有效的证书**调一个 `RenewCert` RPC 换一张新的。
不需要新 token——现有证书就是身份证明。这与 mechd 服务端证书的自动轮换
是同一条规则，只是方向相反。

> 剩余期限的判断在 mechlet 侧做而不是 mechd 侧推：证书在谁手上谁最清楚，
> 而且这让「节点断连三个月后回来」这件事有明确行为——它一连上就发现
> 自己过期了，走重新加入而不是悄悄用一张废证书。

**吊销**是要定的那一半。两条路：

| 做法 | 代价 |
|---|---|
| 标准 CRL / OCSP | 需要分发与刷新机制、有缓存窗口；对**单个** mechd 是纯粹的额外机器 |
| mechd 侧状态检查：握手照常，**应用层**查 CN 对应的节点是否仍有效 | 不是标准做法；如果将来有多个 mechd，状态要同步 |

**决定：应用层检查**（[ADR-0034](../adr/0034-node-join-and-identity.md)）。
ADR-0014 已经定了 v1 不做 mechd 高可用，只有一个 mechd 持有全部状态，
CRL 要解决的「校验方与签发方分离」这个问题在这里不存在。
`node remove` 与 `node revoke` 之后，那张证书握手仍会成功，但**任何 RPC
都会被拒**，并在审计里留下一条「已吊销的节点尝试连接」。

> 代价照实说：这不是标准 PKI 姿态，**一张被吊销的证书仍能完成 TLS 握手**。
> 任何依赖「握手成功即已授权」的中间件（反向代理、L7 网关）在这里都会
> 得到错误的结论。将来真要多 mechd，吊销状态得跟着一起同步——但那时要
> 同步的东西远不止吊销列表。

### 2.4 批次怎么划

一次多节点 Rollout 是**两层**结构，不是一层：

```
Rollout
 └─ 阶段（stage）   按角色的 requires 拓扑序，一个角色一个阶段
     └─ 批次（batch） 阶段内按 maxUnavailable 切
         └─ 目标      RoleInstance（落在具体节点上）
```

**调研过的做法：**

| 项目 | 参数 | 特点 |
|---|---|---|
| Kubernetes Deployment | `maxUnavailable` + `maxSurge` | maxSurge 依赖「可以多起一个副本」——裸机有状态组件做不到 |
| Nomad `update` | `max_parallel`、`canary`、`healthy_deadline`、`auto_revert` | 与本项目场景最接近 |
| Cloudera Manager 滚动重启 | 批大小 + 失败阈值 + 「先重启从、后重启主」 | 组件语义写死在产品里 |
| Ansible | `serial:` | 只有批大小，没有健康门禁 |

**不做 `maxSurge`**（[ADR-0035](../adr/0035-no-maxsurge.md)）。它的前提是
同一个角色可以临时多出一个实例，而 Mecharion 管的是裸机上带数据目录、
带固定端口、带 ordinal 的实例（[ADR-0028](../adr/0028-stable-ordinals.md)）
——多起一个不是配置问题，是「那台机器上没有第二份数据目录」。

代价要正面写进文档：**做不到严格零中断**。每个实例升级都有一次真实的
停机窗口，可用性靠「同时只动 `maxUnavailable` 个」维持，而不是靠
「总副本数不下降」。单实例组件的滚动升级必然有中断。来自 Kubernetes 的
用户会有错误预期，不能让他们在找不到 `maxSurge` 时自己猜。

因此只有两个旋钮，都在 Component 上：

```yaml
rollout:
  maxUnavailable: 1     # 默认 1；quorum 角色强制 ≤ (N-1)/2
  canary: 1             # 首批大小，默认 1；设 0 关闭
```

**默认 canary=1 是刻意的**：第一批只动一台，它失败时受影响的面最小，
而绝大多数「新版本根本起不来」的问题在第一台上就暴露了。

批内的顺序按 **ordinal 升序**——稳定顺序让「上次停在第几台」这个问题
有答案，而随机顺序会让同一次故障每次复现在不同机器上。

### 2.5 健康门禁：什么算「这批过了」

判据**四条全部**成立才算过：

1. 批内每个实例上报的 digest == 期望 digest（收敛）
2. 每个实例的最近一次调和结果不是 failed，且健康探针没有说 unhealthy
3. 工作负载的**重启计数在窗口期间没有增加**
4. 以上状态**持续了 `stableFor`（30s）**

第 4 条不能省。一个刚起来还没崩的进程，在起来后的那一瞬间前三条都满足——
没有稳定窗口，Rollout 会用一台正在崩溃循环里的机器去批准下一批，
**故障因此被逐批放大**。这与 M6 「崩溃重启循环曾经被报成 ok」是同一类错误
的多节点版本。

第 3 条是实施时加的（原设计只有三条），理由是**有限窗口必然漏掉周期比它
长的崩溃**：一个每 40 秒崩一次的进程能从 30 秒窗口里干干净净地溜过去。
重启计数不会漏——涨了就是崩过，与观察时机无关。它的数据本来就在上报里
（`WorkloadStatus.Restarts`，systemd 的 `NRestarts` / docker 的
`RestartCount`），此前只是没落库。

> 代价：`systemctl reset-failed` 会把 `NRestarts` 清零。那时这一条退化成
> 「没有增加」——**不会误判失败，只会漏判**，方向是安全的。

**「健康探针没有说 unhealthy」而不是「健康探针通过」**：没有声明探针的
Pack 拿不到任何健康信号，要求 `healthy` 会让它们永远卡在门口。空值与
`unknown` 都放行，代价是这类 Pack 的门禁只剩收敛与重启计数两条。

批次超时 `batchTimeout`（10 分钟）：超时未满足即判这批失败，
**错误信息要指名是哪台、卡在哪一条**（没上报 / digest 没跟上 / 不健康 /
一直在重启）。「10 分钟内未收敛」说不出该去看哪台机器。

计时从**批次放行**起算，不是从 Rollout 开始起算：一次 4 批的升级合法地
要花 4×（物化 + 稳定窗口），拿一个全局 10 分钟去卡它必然误判。M6 的全局
`RolloutTimeout` 因此只在**没有批次记录**的退化路径上继续生效。

**两个都不是旋钮**，与 M6 的 `RolloutTimeout` 同一条理由：它们是判据，
不是配置。慢启动的组件靠 Pack 的 `health.startupGrace` 表达——那是节点侧
的事，节点在 grace 期内不报 unhealthy，因此 `stableFor` 不需要跟着变。
加一个 `stableFor` 旋钮等于把同一件事表达两遍，而两处迟早会打架。

**窗口的起点落盘，不放内存**（`rollout_batches.healthy_since` 与
`restart_baseline`）。放内存的话 mechd 一重启窗口就重置——那个方向是安全的
（多等 30 秒），但「状态可以重复确认」这条纪律要求重启前后看到同一个答案。

**单机也走这道门禁。** 单机现在也是一批，因此 `rollout status` 说「已成功」
会比 M6 晚 30 秒。这是对的：M6 那个「崩溃重启循环被报成 ok」的缺陷本来就是
单机的。§5 第 14 条说的「与 M6 完全一致」指的是**结构**（一阶段一批次、走
unix socket、不碰证书），不是时序。

### 2.6 一批失败之后

路线图的判据是「**一个失败则整体暂停**」。这里把它精确化：

| 动作 | 做不做 | 理由 |
|---|---|---|
| 停止下发后续批次 | **做** | 这就是「暂停」 |
| 失败实例自身回滚到旧版 | **已经在做** | 节点侧自治，M6 的自动回滚，与 Rollout 无关 |
| 已完成批次回滚 | **不做** | 那是一次新的、更大的变更；由人决定 |
| 保持 Rollout 可恢复 | **做** | `rollout resume` 从断点续做，不重做已完成的批次 |

**「不自动回滚已完成批次」要说清楚代价**：集群此刻是**混合版本**的——
前几批是新版，其余是旧版。这对无状态服务通常无害，对有协议版本约束的
组件可能有害。判断依据只有 Pack 作者知道，而 v1 没有表达它的地方。
因此这里选择停下来等人，并让 `rollout status` 把混合状态**明确显示出来**，
而不是替用户做一个可能更糟的决定。

> 想自动回滚整体的用户有现成的路：`rollout abort` 会真的回退（M6 已实现），
> 只是需要人点一下。

**停下来之后处在哪个状态**，是这里要定的最后一件事。新增 `halted`：

| 状态 | 谁停的 | 还能往前走吗 |
|---|---|---|
| `paused` | 人（`rollout pause`） | 能 —— `rollout resume` |
| `halted` | 系统（某批没过门禁） | 能 —— 修好机器之后 `rollout resume` |
| `failed` | 系统，且没有前路 | 不能 |
| `aborted` | 人（`rollout abort`），且已经退回去了 | 不能 |

**不复用 `paused`**：脚本判 `state == "paused"` 时分不出「我按的」和
「出事了」，而这两件事在复盘里差得远。这与 `aborted` 当初要与 `failed`
分开是同一条理由。

**不让 `failed` 可恢复**：failed 读起来就是终态，一个能变回 running 的
failed 会让 `rollout history` 说不清一次升级到底怎么了。`failed` 留给真正
没有前路的两种：节点自动回滚（那个 digest 在节点侧已被 blocked，再推一遍
也不会动），以及没有批次记录的退化路径超时（没有「断点」可续）。

`resume` 做三件事，一件不多：

1. 把失败那一批退回 `released`，**清掉门禁窗口、重置放行时刻** ——
   `batchTimeout` 从头算，否则刚 resume 就会立刻再次超时
2. 已完成的批次**一个都不碰**，这就是「不重做」
3. 状态回 `running`

它**不重新分批**（批次在创建时一次算好，§4），也不去动已完成批次的机器。

> resume 不检查「机器是不是真的修好了」——mechd 判断不了，而人比它清楚。
> 没修好的话下一轮门禁照样拦，再过一个 `batchTimeout` 重新 halt。代价是
> 一次过早的 resume 要白等 10 分钟，因此 `rollout status` 在 halted 时要
> 把**卡在哪台、哪一条**摆在最显眼的位置。

**`resume` 能救的是「还没做」，不是「做坏了」。**

这条边界来自一个真实的边缘情形：把 agent 在**物化途中**杀掉，重启之后节点
发现那个 digest 上次失败过（M6 的 `Blocked`），于是回落到旧版并上报回滚
——mechd 观测到回滚就判 `failed`，而 resume 推的还是同一个 digest，
节点根本不会再试。**解锁要靠一个新的 digest**（M6 §6 记在案的那条限制）。

因此两类停下要分清：

| 停下的原因 | resume 有用吗 |
|---|---|
| 没上报（离线）、没轮到、物化还没做完 | **有用** —— 那一批只是没做 |
| 节点已经试过并回落（Blocked） | **没用** —— 状态是 `failed` 而不是 `halted`，本来也不让 resume |

好在这两类天然落在不同状态上：回落会被 `rolledBack` 判成 `failed`，
而 `failed` 按设计就不可恢复。**状态机自己把这条边界表达对了**，
不需要额外的守卫。

### 2.7 节点离线 / cordon 时批次怎么算

| 情形 | 行为 |
|---|---|
| 批内某节点**离线** | 等到 `batchTimeout`，然后判这批失败，错误信息指名是哪台没上报 |
| 节点被 **cordon** | **不进任何批次**，Rollout 结束后在 status 里列为「已跳过」 |

离线**不跳过**：跳过等于悄悄少升级一台机器，而那台机器回来之后会带着
旧版本继续跑——这正是「每条都验过、整张表没人看过」那类问题的多节点版。
宁可停下来让人看见。

cordon 则相反：它是**人明确说过**「别动这台」，跳过正是它的语义。
但要在 status 里显式列出来，否则「为什么这台还是旧版」会变成一次排查。

**`cordon` 因此纳入 M7**，虽然路线图原文没列它：它不只是个便利命令，
是 Rollout 分批**必须回答的一个输入**——不做的话这个问题只能靠假装它
不存在。`drain`（cordon + 停全部 workload）留到之后：它与 Rollout 无关。

## 3. 加入的完整路径

```
① mechctl node token create --node store-042 --ttl 30m
     → m7n_join_xxxxx（只显示一次）

② 目标机器上（三选一）
   有 SSH:  mechctl node bootstrap ssh://root@store-042 --token m7n_join_xxxxx
   离线:    拷二进制后 mechlet install --join https://mechd:8443 --token m7n_join_xxxxx
   预置:    镜像里放好二进制，cloud-init 执行 mechlet install --join …

③ mechlet 本机生成密钥对 → CSR（CN = 节点名）
④ 用 token 调 POST /api/v1/join（**唯一不需要既有身份的入口**）
⑤ mechd 校验 token（未过期、未用尽、未吊销、绑名匹配、名字未被占）
     → 用已有 CA 签这份 CSR，签出客户端证书（1 年）
     → 建 nodes 行，token 使用次数 +1，进审计
⑥ mechlet 落盘 /etc/mecharion/pki/{node.crt,node.key,ca.crt}
⑦ 之后一切走 mTLS：Register / Subscribe / Report / FetchBlob
```

**私钥不过网。** 第 ③ 步在节点本机生成密钥对，只把 CSR 发出去——mechd
签的是一份公钥，从头到尾看不到私钥。`mechd ca issue` 那条离线路径做不到
这件事（那台机器不可达，只能由 mechd 代生成），因此它是**次选**，
不是等价的另一条路。

### 3.1 Join 走 HTTP API，不是 gRPC

一度打算给它单开一个 gRPC service。改成 HTTP 的理由：

- 它是**一问一答**，不是流。gRPC 在这里买不到任何东西。
- gRPC 那个监听是 `RequireAndVerifyClientCert`——而 join 的整个前提就是
  「还没有证书」。要么再开一个端口，要么把它放松成
  `VerifyClientCertIfGiven`。后者会把「必须有证书」从**传输保证**降级成
  一句应用层检查，而那正是 ADR-0034 划分传输与应用两层时要避免的。
- HTTPS 监听已经在那里，已经有服务端证书，本来就不要求客户端证书。

### 3.2 先有鸡还是先有蛋：节点怎么信任 mechd 的证书

节点还没有 CA，却要先建立 TLS 连接才能拿到 CA。三条路：

| 做法 | 代价 |
|---|---|
| 运维把 ca.crt 拷过去 | 多一个文件要搬，而 join 存在的意义就是少搬东西 |
| TOFU（首次连接即信任） | [08-security §3.2](08-security.md) 明确不做——中间人在首次连接时无法被发现 |
| **token 里带 CA 公钥指纹** | 需要 token 的展示格式带上它 |

选第三条，与 kubeadm 的 `--discovery-token-ca-cert-hash` 是同一个做法。
它**不是 TOFU**：指纹是带外交付的（跟 token 一起），校验发生在第一次连接
之前，中间人换一张证书立刻就被发现。

因此 `node token create` 直接打印一条可以粘贴的完整命令：

```
mechlet install --join https://mechd-1:8443 \
    --token m7n_join_a1b2… \
    --ca-hash sha256:9f86d0818…
```

指纹取的是 CA 证书的 **SubjectPublicKeyInfo**，不是整张证书：CA 到期重签
时公钥可以不变，那时旧指纹仍然有效——而按整张证书算的话，所有还没加入的
token 会在重签那一刻集体失效。

## 4. Rollout 的完整路径（多节点）

```
mechctl component upgrade web --version 1.3.0
  ↓ mechd：改版本 → 重新渲染 → 新 digest（每个实例一份）
  ↓ 建 Rollout + 阶段 + 批次（此刻就算好，落 rollout_batches）
  ↓
  ├─ 阶段 1（角色 A，requires 拓扑序在前）
  │   ├─ 批次 1（canary，1 个实例）→ 下发 → 等门禁
  │   ├─ 批次 2（maxUnavailable 个）→ …
  │   └─ …
  └─ 阶段 2（角色 B）…
  ↓
Rollout succeeded / failed / paused
```

**批次在创建时一次算好并落盘**，不是边走边算：算好之后
`rollout status` 才能回答「一共几批、现在第几批」，而边走边算只能回答
「现在这批」。中途有节点上线/下线也不改已算好的批次——那会让
「一共几批」这个答案在执行过程中变化。

推进仍然由**上报驱动**，不设后台循环（M6 §2.6 的决定不变）。
`AdvanceRollout` 从「推进一条 Rollout」变成「推进当前批次；批次过了就
开下一批；阶段完了就进下一阶段」——**状态机的外形不变**，单机退化成
一个阶段、一个批次、一个目标。

| # | 场景 | 期望 |

| 2 | token 过期 / 用尽 / 已吊销 | 加入被拒，错误信息说清是哪一种 |
| 3 | 绑名 token 换别的名字 | 被拒 |

第 9、10 条是这个里程碑的核心。第 14 条同等重要：**多节点的代码不能让
单机形态变复杂**——单机是这个项目最主要的形态。

> **第 13 条原本写的是「设 2 被拒」，改了。** 那个旋钮在 **Component** 上，
> 而 quorum 在**角色**上：一个组件可以同时有仲裁角色和无状态角色，
> 为了前者拒掉整条设置，会让后者也用不上本来合法的并发度。
> 因此机制是**按角色压**（已实现），要补的是**让它可见**——
> 静默压掉等于把用户的意图丢了还不告诉他。

**第 5 行原来是假的**，值得记下来：它测的是「agent 没有证书时自己拒绝启动」
（判据是那句「读不到证书」）。一个**根本没启用 mTLS** 的 mechd 照样能让它
通过——客户端压根没走到握手。真正要验的是服务端：拿一个不带客户端证书的
连接去撞 8444，握手必须失败。

> 这条只能靠一个夹具二进制（`test/tlsprobe`）：容器里没有 openssl，
> 而集群的端口不对宿主发布。它与 `test/webapp` 是同一类东西——
> **验收需要的能力，用夹具补，不往被测镜像里装工具**。

**而补上的那条，第一版自己也是假的**，失效方式一模一样。

探针发的是 `GET / HTTP/1.0`，而 gRPC 认不出这个前导也会关连接。于是判据
「反正失败了」同时被两件事满足：TLS 拒了我，或者 gRPC 嫌请求不对。把
`RequireAndVerifyClientCert` 降级成 `VerifyClientCertIfGiven`——一次彻底的
mTLS 失效——测试**照样通过**。

分开它们的是错误的**来源**：

| 服务端配置 | 探针看到的 |
|---|---|
| `RequireAndVerifyClientCert` | `remote error: tls: certificate required`（TLS **告警**） |
| `VerifyClientCertIfGiven` | `EOF`（握手成功了，应用层才关的） |

判据因此钉在那个 TLS 告警上。

> 两次都栽在同一件事上：**「失败了」不是判据，「因为什么失败」才是。**
> 一个安全断言如果能被无关的原因满足，它保护的东西就是空的。

而这个里程碑的每一条判据都是「多台机器一起」才成立的。这与 M5 把
「周期调和」排第一是同一条理由：**先让要观察的现象能发生**。

### 6.1 多节点验收的驱动程序跑在宿主侧

单节点验收的测试二进制在**容器里**跑（`test/e2e`）。多节点做不到：
驱动要在三台机器上分别执行命令、比对三份状态，而节点镜像里既没有 docker
也没有 ssh——装上任一个都会毁掉那个镜像存在的理由（`test/node/Dockerfile`
靠「没有 curl」强制执行 hermetic 约束）。

因此 `test/multinode` 的二进制**在 WSL 宿主侧运行**，用 `docker exec`
驱动三台容器。被测系统仍然完整地跑在容器里：mechd、mechlet、systemd
一个都没打桩。挪到宿主的只有那双**观察的眼睛**——它本来就不能站在
任何一台被测机器上。

代价：这些测试不进 `go test ./...`（没有集群环境时整体 skip），入口是
`./hack/testenv.sh cluster test`。为此 `cmd_test` 里把 `test-multinode`
显式排除掉了——在容器里跑它只会 skip 然后打出一行 PASS，
而「一直在跳过」会被当成「一直在通过」。

### 6.2 第 1 步验的是什么

不是「`docker ps` 里有三行」——那种验收下一步就会失效。真正要成立的是
**控制面跨机可达**：站在 n2 上用 `mechctl` 连 n1 的 HTTPS API 拿到答案。
那一条命令同时把四件事验了，而它们各自都可能单独坏掉：

| | 坏掉时的症状 |
|---|---|
| 两个容器在同一个用户自定义网络上 | 连不上 |
| `m7n-n1` 这个名字解析得到（内嵌 DNS） | 解析失败 |
| 自签证书的 SAN 里有 `m7n-n1` | **一句 TLS 错误，看起来像网络问题** |
| CA 与 admin token 跨机之后仍可用 | 401 / 证书错误 |

第三条是最值得先验的：容器不设 `--hostname` 时主机名是容器 ID，证书 SAN
里就没有 `m7n-n1`，而失败信息是
`certificate is valid for localhost, 67a775ddd7be, not m7n-n1`——
等到第 3 步 join 时才撞上它，排查方向会先跑偏到网络上去。

还有一条反向断言：**不带 CA 必须失败**。少了它，上面那条说明不了什么
——客户端若根本没在校验证书，带不带 `--ca-file` 都能连上。

### 6.3 第 2 步落地时定的四件事

**① 两个 `grpc.Server`，不是一个。** 传输安全是整个 Server 的属性，一个
实例带不了两套（unix socket 明文 + TCP mTLS）。两者注册的是**同一个**
服务实现——协议只有一份，差别只在「对端是谁」怎么得出。

**② `--grpc` 默认开着（`0.0.0.0:8444`）。** 它要求客户端出示一张本机 CA
签过的证书，握手就把没有证书的人挡在门外；暴露面是一次 TLS 握手。默认
关掉的话，每套多节点部署都要先改一次配置，而**那一步出错时的症状是节点
连不上**——比这点暴露面贵得多。不需要时 `--grpc ""`。

**③ 传输形态由地址决定，不另设开关。** `unix://…` 走明文，其它走 mTLS。
一个 `--mtls` 之类的布尔量迟早会与地址对不上，而那种错配的症状是一句
连不上，看不出是配置问题。

**④ `internal/pki` 从 `mechdcmd/tls.go` 里拆出来。** 它有三个使用者：
mechd 启动时备服务端证书、`mechd ca issue` 手工签发、以及第 3 步的
Join RPC 自动签发。三处必须共用同一套签发逻辑——两套 x509 模板意味着
两套边界条件，而证书出错时症状都长得一样。

顺带补上了 `mechctl node add`：`Register` 一直拒绝不在册的节点并让用户去敲
这条命令，而**它在 M7 之前根本不存在**（§0）。登记与加入是两件事——
前者是控制面的管理动作，后者需要那台机器上有人——因此 `node add` 之后
节点状态是 `pending`，它还没出现过（这个值的由来见 §6.13）。

### 6.4 第 3 步落地时定的三件事

**① 服务端证书文件里带上 CA。** 自签根一般不必发给对端，这里发是因为
join 的指纹校验要在链里找到那张 CA。旧版本只写了叶子，因此
`serverCertUsable` 多了一条判据：**没有 CA 那一段就当成该重签了**
——重签是无损的，而缺链会让加入直接失败。

**② `internal/pki` 的每个函数都收 pki 目录，不收 conf 目录。**
原本 `EnsureServer` 收 confDir 而其余收 pkiDir，混着来会让调用方多传或
少传一层，而症状是「证书明明生成了却读不到」。这是被自己写的第一条
单元测试当场撞到的。

**③ 签发的 CN 由授权决定，不信 CSR 里写的。** CSR 是节点自己造的，
里面的 CN 与 token 的授权范围无关——信它的话，一张绑定了 `store-042` 的
token 能签出任何名字的证书，绑名就白绑了。CSR 的自签名**必须验**：
不验则任何人都能拿别人的公钥换一张证书，而那张证书的真正持有者是别人。

### 6.5 第 4 步落地时定的四件事

**① 集群镜像带 sshd，`test/node` 保持贫瘠。** `mechctl node bootstrap ssh://…`
的前提就是目标机器上有 sshd，而真实用户的机器本来也不是贫瘠的。
hermetic 约束由**单节点套件**强制执行（`test/node` 那个「没有 curl」的
镜像原样保留）——两处约束各在该在的地方，而不是靠一条写在错误位置的
断言假装还在保。

**② 推四个二进制，不是一个。** 设计文档早先写的「一次性推送单个静态
二进制」是个愿望：`mechlet install` 要求四个在同一目录，并且会明确拒绝
装一半——「装一半的 Mecharion 会在某个命令上突然缺失」。

**③ 暂存目录不放 /tmp。** 加固过的机器普遍把 /tmp 挂成 noexec（CIS 基线
就这么要求），推过去的二进制在那里根本执行不了，而症状是一个 126 退出码。
**这不是推演，是第一次跑就撞上的**——测试容器的 /tmp 正是 tmpfs+noexec。
改放安装根下面：那里如果也不可执行，Mecharion 本来就装不上，失败发生在
正确的地方。126 / 127 现在都翻译成可操作的下一步。

**④ 不校验 SSH 主机密钥，并把理由写下来。** bootstrap 是与一台素未谋面的
机器的第一次接触，本机没有它的 known_hosts 条目。真正的信任锚在下一步——
目标机器拿 `--ca-hash` 校验 mechd，而那个指纹是带外交付的：即便这条 SSH
被中间人接管，他也拿不到一张能通过指纹校验的 mechd 身份。**代价是**中间人
可以让「这台机器」变成他的机器；要排除这一点，请先自建 known_hosts。

顺带补上了 `mechctl node remove`：`Join` 的错误信息让用户去敲它，而它
**也不存在**（与 `node add` 同一个毛病）。仍有实例时默认拒绝——删掉一个
还跑着组件的节点，会让那些组件从中心的视图里消失，而它们仍在机器上跑。

### 6.6 第 5 步落地时定的四件事

**① 吊销的判据挂在身份收口处，不是另开一道检查。** `Server.nodeOf` 现在
回答两个问题——「你是谁」（传输层事实）与「你还能连吗」（控制面状态）。
合成一个会让「握手过了」被当成「获准了」，而应用层吊销的全部意义恰恰
是这两者可以不一致。**每个 RPC 都查**，因为被吊销的证书握手仍会成功。

**② `revoke` 与 `remove` 是两件事。** remove 把节点从册子上抹掉（换硬件、
退役），revoke 保留那一行但切断它——「这台机器被偷了，先断掉，但我还要
看它上面装过什么」。两者都在**已连接**的 agent 上立刻生效，不必等它重连。

**③ 换完证书不重启。** 拨号的 TLS 配置用 `GetClientCertificate` 每次握手
从盘上读当前证书。固化的话，换完必须重启 mechlet——而重启一个正在维持
一堆组件的 agent 只为了换张证书，是个没必要的风险。

**④ 过期了就别装作能自愈。** 过期的证书连不上 mechd，而续期本身要走
mTLS。这是个人必须介入的状态，因此**喊一声就安静**，并直接给出路
（用新 token 重新加入），而不是每轮重试一次把日志刷满。

> `mechd ca issue --validity` 是这一步顺带加的：短有效期是真实需求
> （高安全环境几天一换），也让「轮换」这件事能在几分钟内验一遍——
> 否则要等一年才知道它成不成立。

### 6.7 第 6 步落地时定的四件事

**① `cordoned` 是下发里的一个字段，而且它是状态不是动词。**
协议层有一条守卫测试（`TestAssignmentHasNoVerbs`）会拦住 `Assignment` 的
每一个新字段并要求说明理由——这次它真的拦了一次。`cordoned` 通过判据：
它说的是「这台机器现在是什么情况」，随全量一起重推，节点不需要记住任何
一次性指令。写成 `pause_reconcile` 那种动词的话，断连期间的语义就得由
节点自己猜。

**② `Handler.Apply` 改收一个结构体。** 参数表上已经有「规格」「是不是
全量」「有没有被 cordon」三件事，而它们是同一份状态快照的组成部分。
散成参数的话，加第四件时每个实现都要改签名。

**③ cordon 停的只有「往机器上落」这一件事。** 连接、上报、孤儿计算、
证书续期全都照常；**期望状态照常落盘**——那决定了 uncordon 之后能不能
立刻收敛，不落的话「恢复」就变成「等下一次变更」。回收也一起停：
它会删东西，而 cordon 说的是别动。

**④ 进入与解除都要有声音。** 进入那一声在调和循环里发（那时才确认真的
停了），解除必须在收到下发时发——恢复之后调和循环不再走那条分支，
没人会说话。运维 cordon 一台机器去调试，事后最想确认的就是
「它恢复了没有」。

> `node list` 把 cordon / revoke 并进状态列显示，但 JSON 输出里它们仍是
> 独立字段：一台机器可以既在线又被暂停调和，并成一列是给人看的，
> 脚本不该因此丢信息。

### 6.8 第 7 步落地时定的五件事

**① 批次不只是记下来，它得管住下发。**
这一步的验收写的是「`rollout status` 说得出第 2/4 批」，而那句话只是表面。
一个只把批次落盘、下发照旧全量的实现能说出同样漂亮的「第 1/3 批」——
而三批的机器早已全部升完。那**比没有分批更糟**：运维看着「第 1/3 批」
以为还来得及叫停。

门禁落在 `Backend.Assignment`：还没轮到的实例继续拿**起始版本**的规格。

**② 两次渲染，不是一次渲染再改改。**
解析管线是纯函数，同一份输入必然产出同样的 digest。想在一次渲染的结果上
「把版本号改回去」，得到的是一个从没被算出来过的规格——它的 digest 与
两边都对不上，节点会当成第三个版本反复物化。

代价照实说：混版期间每个实例看到的 `topology.…` 视图来自**它自己那一版**
的 Pack。新版实例眼里所有同伴都是新版布局，旧版实例眼里都是旧版布局。
要让两边看到同一份混合视图，就得让渲染依赖「别人现在是哪一版」——那会让
每台机器的规格随别人的进度变化，滚动过程中反复重算，比这个偏差糟得多。

**③ 先开 Rollout，再下发。**
这个顺序是被容器验收抓出来的：原本的 `Upgrade` 先 `applyComponentVersion`
（渲染、落库、唤醒节点）再 `startRollout`。节点被唤醒后立刻来拉规格，
而那时批次还不存在——三台在十几秒内一起换完，`rollout status` 随后才开始
说「第 1/3 批」。分批成了一个纯粹的观测构造。

宿主侧的单元测试**没抓到**这条：它们直接调 `Assignment`，而顺序问题只在
「唤醒 → 拉取」这条真实时序里暴露。这是「容器跑起来才算验收」的又一例。

**④ 收敛的定义要加一条：跑着目标版本。**
原来的判据是「digest 一致且健康」。分批期间还没轮到的实例拿的是旧版规格，
它与自己的期望**是对得上的**——于是 `component status` 在第一批还没放行时
就说「1.3.0 已收敛」，而三台机器上跑的全是 1.2.0。那是最坏的一种谎：
它出现在人专门去确认的地方。

同一件事在 `AdvanceRollout` 里也要防：`view.Converged` 为真不足以宣布成功，
还要**所有批次都做完**。少了这一条，第一批刚做完整次升级就被归档，
剩下两批再也不会被放行——而 `rollout history` 说这次升级成功了。

于是有了 `pendingVersion`：它说明这台**为什么**没收敛。「在排队」与
「出了问题」在收敛那一列里都是「否」，而一个只要等，一个要人去看。

**⑤ 成功的判据只有「每一批都做完了」，不叠加「整体已收敛」。**
这条是追一个存活的变异时发现的：把两者叠加，被 cordon 的机器会让升级
**永远不成功**——它们按定义就停在旧版，`Converged` 因此永远为假。于是
每一次「先 cordon 掉一台再升级」都会以超时失败收场，而那正是 cordon 最
常见的用法。

`done` 本身已经足够严：一批只有在它的目标**全部收敛到新版**时才进 Done。

> 顺序值得记一下：④ 把 `Converged` 收严，收严之后 ⑤ 才暴露出来。收严是
> 对的，但它把一个原本无害的叠加条件变成了缺陷——**改一条判据要回头看
> 所有用它的地方**。

**⑥ 被 cordon 的名单也落盘。**
只写日志是不够的：运维事后问的是「为什么这台还是旧版」，而那时日志已经
翻过去了。它存成一条 `seq=0` 的批次记录——`seq=0` 让它不进「第几/共几批」
的分母，因为它不是一批，是一份名单。

**⑦ `rollout pause` 从 M7 起也停批次队列。**
M6 时它只冻判定（单机只有一批，没什么可停），M7 起它还压住下一批的放行；
已经放行的那批照常跑完。单机验收里那条「冻结期间节点仍应照常收敛」因此
要改写——它编码的是 M6 的语义。

顺带把「abort 真的把机器退回来」挪到多节点验收：单机只有一批、pause 又
发生在放行之前，机器根本没动过，那条断言在单机上无从检验。

> 两个旋钮（`maxUnavailable` / `canary`）**只影响下一次变更**。批次在
> Rollout 创建时一次算好，半路重算会让「一共几批」这个答案在执行过程中
> 变化，而运维正是靠它判断还要多久。`set-rollout` 在有变更进行中时会
> 主动说这一句。

### 6.9 第 8 步落地时定的四件事

**① 判据从三条加到四条：重启计数。**
原设计的三条里，「稳定 30 秒」是唯一挡崩溃循环的那条，而它是个**有限窗口**
——一个每 40 秒崩一次的进程能从里面干干净净地溜过去，每次采样看到的都是
一个刚起来、还没崩的健康进程。重启计数不会漏：涨了就是崩过，与观察时机
无关。数据本来就在上报里（`WorkloadStatus.Restarts`），此前只是没落库。

**② 门禁自己判，不搭 `InstanceView.Converged` 的便车。**
那个字段服务的是 `component status`，它的定义会为了显示需要而调整——第 7
步就调过一次（加了「跑着目标版本」）。门禁跟着它走的话，下一次调整会
**悄悄改掉滚动升级的判据**，而那种改动在 code review 里看不出来。

**③ 失败之后门禁**继续**关着。**
这条是被验收测试抓出来的：`releaseStateOf` 原本查的是「进行中」那条
Rollout，而一条刚被判失败的 Rollout 不再是 active——于是门禁跟着消失，
剩下的批次在下一次心跳里**一起升上去**。正好是这道门禁存在的全部理由
的反面。改成看**最近一条**，并按状态决定它还管不管下发：

| 状态 | 管不管下发 |
|---|---|
| running / paused / **failed** | 管——没轮到的实例继续停在旧版 |
| succeeded | 不管（每一批都放行过了，管不管一个样） |
| aborted | 不管（它一定已经被更新的一条取代） |

同时，**失败那一批的机器算「已放行」**：它们上面已经装着新版了，把规格
抽回旧版等于替人做了一次「整体回滚」的决定，而 §2.6 说那是一次新的、
更大的变更，由人决定。何况被门禁拦下的机器多半正在崩，再给它一次版本
切换只会更糟。

**④ 全局 `RolloutTimeout` 在有批次时不生效。**
一次 4 批的升级合法地要花 4×（物化 + 稳定窗口），全局 10 分钟会在第三批
上误判——而且它给出的是「10 分钟内未收敛」这句说不出该看哪台机器的废话，
正好盖掉 `BatchTimeout` 那条指名道姓的。

> `checkGate` 里曾有一句「基线沿用窗口起点那一份」——追下去发现它
> **既多余又方向错误**——多余是
> 因为走到那里时两者本就相等，且 `saveGate` 在窗口期间根本不写盘；错误是
> 因为唯一会不相等的情况是 `systemctl reset-failed` 清了计数，那时守着一个
> 偏高的旧基线反而会掩盖之后真实的崩溃。删掉，并把那条测试换成一条走完整
> 链路的：**一次崩溃必须赔掉一整个 StableFor**，不能靠之前攒的时间过关。

### 6.10 第 9 步落地时定的四件事

**① 新状态 `halted`，不复用 `paused` 也不复用 `failed`。**
理由写在 §2.6。落地时多出一条：`ActiveRollout` 那条 SQL 要把 halted 算进
「进行中」，否则 `rollout resume` 根本找不到它——而 `AdvanceRollout` 又必须
对它早返回。**「算作进行中」与「还在推进」是两回事**，这两处很容易被写成
同一个判断。

**② 停下之后 mechd 要真的什么都不做。**
这条是追一个存活变异追出来的。摘掉 `AdvanceRollout` 里对 halted 的早返回，
所有测试照绿——因为 `advanceBatches` 遇到 failed 批次本来就会停。但它挡住的
不是推进，而是**上面那段自动回滚判定**：门禁停下之后，节点侧多半会对那个
起不来的 generation 自动回滚（M6 的节点自治），下一次上报就会把 halted 冲成
failed，**连同那句指名道姓的原因和续做的可能一起没了**。

> 教训与第 7 步那次同类：**一个"冗余"的守卫，冗余的往往只是它最显眼的那
> 层作用**。判断它能不能删，要看它挡住的所有路径，不是最先想到的那条。

**③ 哪些故障走 `halted`，哪些走 `failed`，取决于节点侧回没回滚。**

这条是容器验收白等了 13 分钟才看出来的。分界线是节点侧那条
（22-upgrade §2.2）：**软链切了没有**。

| 故障 | 节点侧 | Rollout 状态 |
|---|---|---|
| Start 失败 / 健康检查不过 | 软链已切 → **自动回滚** | `failed`（终态） |
| 资源 Apply 失败 / preUpgrade 失败 | 旧版还在跑，不回滚 | `halted` |
| 节点离线不上报 | 没动静 | `halted` |
| 物化很慢（大 blob、慢盘） | 还在做 | 收敛得了就正常走，收敛不了 `halted` |

第一行走 `failed` 是**对的**：那个 digest 在节点侧已经被 blocked，resume
推一遍也不会动（M6 的 blocked 语义）。它不可恢复不是缺陷，是那条已经记在
案的限制——「修好环境之后重试同一个版本」还没有出口。

> 验收因此不能拿「新版起不来」去造 halted：那条路走的是自动回滚。
> §2.7 第一行写的「节点离线」才是 `batchTimeout` 真正的用武之地，
> 也是这条验收该用的故障。

**④ `resume` 清门禁窗口这件事，绝大多数时候是空操作。**
批次失败时窗口一般已经被清零了（机器抖一下就清）。但有一条窄路径能让它
非零：机器抖到最后一刻才稳下来，窗口刚开就撞上批次超时。不清的话，续做
只需要补齐剩下的几秒——**故障之前攒的时间被算数了**，而稳定窗口的全部
意义就是「修好之后重新稳住这么久」。

那条缝只有 `StableFor` 那么宽，靠模拟抖动去碰它既慢又不确定；测试里改成
**把时钟直接对准它**。

### 6.11 一条假断言

第 2 步的「冒名必须被拒」原本是这么写的：

```go
out, err := run(n3, "timeout", "20", "mechlet", "agent", "--node", n1)
if err == nil { t.Fatal("冒名竟然成功了") }
```

**它永远不会失败**：agent 连不上时会一直重试而不是退出，`timeout` 包一层
之后退出码恒为非零。去掉 `nodeOf` 里那句比对，这条断言照样绿。

判据因此改成**日志内容**：必须出现「证书身份是 …」那条拒绝，且**绝不能**
出现「已注册到 mechd」。

> 教训不是「别用退出码」，而是**判据要选那个真正会因为缺陷而改变的东西**。
> 这里缺陷改变的是「注册成没成功」，而退出码在两种情况下都一样。

### 6.12 集群跨测试复用，前提要自己建立

第 3 步的测试把 n2 加进了集群，于是第 2 步那条「没有证书时连不上」当场
变红——它一直假设 n2 是干净的，而在它自己单独跑时那恰好成立。

修法不是给测试排序（那只会让下一个人再踩一次），而是让每条测试
**自己把前提建立起来**：`resetNode` 把机器擦回「还没加入」的样子。
集群跨测试复用是刻意的（起三台容器十几秒，每条测试重来一遍会让这个包
慢到没人愿意跑），代价就是每条测试都得自己声明前提。

**第 2 步在第 3 步之前**：先让传输与身份成立，再谈怎么发身份。反过来
会先写出一个「用 token 换一张没人验的证书」的中间状态。

### 6.13 `node list` 的 online 一直是个只进不出的门

M8 第 4 步把节点状态搬进 Web UI 之后，三台机器全显示 `online`，而其中
两台的 mechlet 早就不在了——最后一次上报是三个半小时前。

原因是 `status` 这个列**只有一条写入路径**：`Register` 时写 `online`，
`node add` 时写 `offline`（§6.3 里那句「它还没出现过」）。**没有人写回
`offline`**。掉线不是没被检测到，而是这个系统里压根没有「掉线」这件事。

这不是显示层的问题。CLI 的 `node list` 一直在说同样的假话，只是文本
输出里它混在一堆字段中间，没人盯着它看；UI 把它做成了一列带颜色的
标签，谎才变得刺眼。**「换个前端」不产生新缺陷，它只是换了个照明角度。**

#### 判据用连接，不用「最后上报时间」

两个候选：

| | 怎么判 | 问题 |
|---|---|---|
| A 上报新鲜度 | `now - last_report > 阈值` 即离线 | **一台没有实例的机器永远不上报**，会被判成离线；而且阈值要跟着 `ReportSeconds` 走，两处配置得对上 |
| B 长连接在不在 | Subscribe 流还挂着即在线 | 断电时流会挂死（见下） |

选 **B**。理由是 A 的失败模式落在「空闲节点」上——而一台刚加入、还没
分到任何组件的机器，恰恰是运维最需要在列表里确认它活着的时刻。

`protocol.Server.Connected(node)` 这个方法**早就写好了**，只有一个测试
用过，生产路径上从来没接上。它读的是当前的 session map，是一次可以反复
确认的状态检查，不是一个丢了就永远丢了的事件——这正是 §2.6 那条原则想
要的形态。

于是：**`status` 列不再是真相**。它退回去只表示「有没有出现过」，
在线与否由 `Connected` 在读的那一刻算出来：

```
从没连上来过          → pending  （node add 之后，还没人在那台机器上执行 join）
Connected == true    → online
否则                  → offline （来过，现在不在）
```

第三个值是必要的。「还没装」和「装了但死了」对运维是两件完全不同的事，
而合并成 `offline` 之后，唯一的区别只剩下「最后上报时间是不是空的」
——那要求看的人知道该去比对这个字段。

#### 代价：多一个状态值，M7 的验收行要跟着改

§5 第 1 行原本写「状态 online」，仍然成立。但 §6.3 那句「`node add`
之后节点状态是 `offline`」不再准确，改成 `pending`。已经写好的
`test/multinode` 里如果断言了 `offline`，会当场变红——这是对的，
它断言的正是被改掉的那个语义。

#### keepalive：否则断电的机器仍然显示在线

选了 B 就得处理它的失败模式：**拔电源不产生 TCP FIN**。服务端那条
Subscribe 流会一直等下去，Linux 默认的 TCP keepalive 是 **2 小时**才
开始探测——在此之前 `Connected` 会一口咬定那台机器在线。

因此 gRPC 服务端加上 keepalive 强制探测：60s 没有流量就发探测，20s
没有回应就断开。上限 80s 发现断电，与 `ReconcileSeconds`（60s）同量级。

同时给客户端配上 `PermitWithoutStream` 的下限，否则服务端的 keepalive
策略会把探测得太勤的客户端**主动踢掉**——gRPC 的默认 `EnforcementPolicy`
比多数人预期的严格（`MinTime` 默认 5 分钟），配错的症状是连接每隔几分钟
断一次而日志里只有一句 `too_many_pings`。

### 6.14 一条假测试：`docker network disconnect` 验不了 keepalive

§6.13 加了 keepalive 之后，给它配的第一条验收用 `docker network disconnect`
拔掉节点的网络，然后等状态变 offline。**它通过了，34 秒。**

34 秒这个数字本身就是答案：一次探测周期是 60s + 20s，任何早于它的结论
都不可能来自 keepalive。把 `ServerKeepalive` 里的
`KeepaliveParams` 整个删掉，那条测试照样通过，证实了这一点。拆掉 veth 会让服务端那一侧
的 socket 直接出错，测到的是内核，不是我们写的那几行。

改用 `docker pause`：容器里的进程被冻住，TCP 栈仍在内核里正常回 ACK，
但没有人再处理一个 HTTP/2 帧。这是**连 TCP keepalive 也救不了**的一类，
只有应用层探测能发现——正是这段代码存在的理由。改完之后 82 秒通过，
删掉探测则 173 秒超时失败。

这是同一条纪律的第三次出现：**「失败了」不是判据，「因为什么失败」
才是**（前两次见 §5 第 5 行的 TLS 告警、以及摘要比较那条）。因此这条
测试同时卡**下限**：早于一次探测超时就变 offline 的，判定为「发现它的
不是 keepalive」。一个只卡上限的断言在这里是无效的。

### 6.15 `node add` 之后没法 join——两条路互斥

被 §6.13 的验收测试当场撞到：先 `mechctl node add n2`（状态 pending），
再在 n2 上 `mechlet install --join`，得到

```
错误: 加入集群: 加入被拒: 节点 m7n-n2 已在册。
      要换一台机器顶替它，请先 mechctl node remove m7n-n2
```

`join.go` 的守卫拒绝**任何**已在册的名字，而 §6.3 写的是「登记与加入是
两件事……`node add` 之后节点状态是 pending，它还没出现过」。两句话里
只有一句能成立。

那条守卫的理由（「在册意味着它可能正在跑着组件，一张新证书会让另一台
机器开始以它的身份上报」）对 `pending` 恰好**不成立**：pending 的定义
就是没人连上来过、没有实例、没跑任何东西。

**这一步不改它。** 它是一道身份接管的闸门，放松它要先回答「已经通过
`mechd ca issue` 拿到证书、但还没连上来过的节点算不算 pending」——
证书签发目前没有独立记录，仅凭 `Seen()` 放行会让那条离线路径上的身份
可被顶替。这个问题该在它自己的位置上定，不该作为一次 UI 步骤的副作用
被顺手改掉。

暂时的影响面：**批量预置那条路走不通**——「先把 20 台机器的名字登记好，
再让它们各自用不绑名的 token 认领」正是 §2.1 给 cloud-init 场景留的口子。
现在只有「不预先登记、名字先到先得」这一种批量方式可用。

### 6.16 补第三个状态值,把 §6.15 的问题接上

§6.15 留下的问题是：「已经通过 `mechd ca issue` 拿到证书、但还没连上来过
的节点算不算 pending」。答案
是：**不算——把它们拆成两个不同的状态值，而不是靠 `Seen()` 一刀切。**

```
node add 登记、还没人执行过 join   → reserved（新）
join（或 standalone 安装）已发证书、还没连上来过 → pending
连上来过                          → seen（不变，一旦置上不再变回去）
```

`reserved` 与 `pending` 的区别只有一件事：**有没有签发过证书**。这正是
§6.15 那道守卫在防的东西（「一张新证书会让另一台机器开始以它的身份
上报」）——对 `reserved` 不成立（压根没证书），对 `pending`（已经拿到过
一张）成立。守卫因此只需要认得这一个新状态：

- `Join` 撞见一个 `reserved` 且未被吊销的同名行时，**放行**，把它当成
  「认领预登记的位置」——走的仍然是 `ClaimNode` 那个原子事务，
  只是从「插入新行」换成「原地把 reserved 改成 pending、换上新地址」，
  两条路径共用同一次 token 消耗，避免重新引入两步操作之间的竞态。
- 撞见任何其它状态（`pending` 已发证书、`seen`、或被吊销）时，**维持
  §6.15 原来的拒绝**——「已在册，先 `node remove`」。

这条规则不区分绑名/不绑名的 token：`Join` 在到达这一步之前已经用
`t.NodeName` 决定了最终要认领的名字（绑名 token 换名字会在更早处被拒），
认领 `reserved` 行时不需要再检查一遍谁绑了什么名——`ClaimNode` 只关心
「这个名字现在能不能被认领」，不关心「是通过哪种 token 到达这里的」。
这正是 §2.1 给 cloud-init 留的口子：`node add` 批量登记 20 个名字，配一张
不绑名、`max_uses=20` 的 token，每台机器开机时用 `--node <自己的名字>`
认领自己那一行；也支持绑名 token 对应单台预登记机器的场景。

`node list` 的显示层不跟着加第四个值：`nodeStatus()` 只看 `Seen()`，
`reserved` 与「已发证书未连接」的 `pending` 对运维呈现的都是同一句
「pending」——两者从外面看确实是同一件事「还没起来」，区分它们是
`Join` 内部的身份把关，不是给人看的状态。
