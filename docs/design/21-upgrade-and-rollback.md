# 升级、自动回滚与 Rollout

M6 的设计。模型见 [06-state-and-drift §5–6](06-state-and-drift.md#5-升级与回滚)，
generation 的形态见 [04-paths-and-storage §2](04-paths-and-storage.md#2-generation)。

> **这个里程碑的判据只有一句：升级失败时自动切回，服务不丢。**
>
> 「服务不丢」现在**不成立**。切换路径是 `stop → 切软链 → start`，
> 而 `start` 失败或健康检查不过时，代码直接返回错误——**旧版已经被停掉、
> 软链已经指向新的**，机器上什么都没在跑，而且没有任何东西会把它切回来。
>
> M6 要补的就是第 8 步：**失败 → 切回旧软链 → 起旧版 → 上报**。

---

## 1. 已经有的，不重做

| 已有 | 在哪 |
|---|---|
| generation 目录、序号固化、原子软链切换 | `internal/reconcile/generation.go` |
| 三条 generation 判定（复用 / 命中历史 / 新建） | `planGeneration` |
| `retainGenerations` 与目录回收 | `pruneGenerations` |
| 失败的 generation 记为 `failed`（保留一个供诊断） | `recordFailure` |
| 健康检查与 `startupGrace` | `internal/health` |
| 参数的 `restartRequired` / `reloadRequired` → notify | mechd 渲染阶段 |
| `rollouts` / `rollout_batches` 表 | `00001_init.sql`（**建了但没用过**） |

**回滚在数据结构上早就可行**——旧目录还在，切一次软链就回去了。缺的是
**触发它的那条路径**，以及回滚需要的那份旧规格。

## 2. 六个要定的问题

### 2.1 自动回滚需要旧规格，而节点上原本没有 ★

切回旧软链**不够**。unit 文件、渲染出的配置、容器的 env 与挂载，都是
上一次 `Materialize` 按**新规格**写的：只切软链会得到「旧的二进制配上新的
unit」——一个从来没被测试过的组合。

好在 [ADR-0033](../adr/0033-mechlet-local-desired-state.md) 已经把期望状态
落到了本机。M6 再留一份**上一版**：

```
<data-dir>/desired/<key>.json            当前期望
<data-dir>/desired/<key>.applied.json    最后一次**成功应用**的规格（回滚用）
```

**不叫 `.prev.json`（上一版）是实现时改的，理由值得记下来。** 「上一个不同
的规格」与「最后一次成功应用的规格」在正常路径上一样，一旦出过错就分道扬镳：

```
v1 成功 → v2 失败 → 用户改参数成 v3 → v3 也失败
  上一版        = v2   ← **从来没成功过**，回滚到它等于回滚到另一个坏版本
  最后成功应用的 = v1   ← 这才是能落脚的地方
```

因此它只在**调和成功之后**写。

> 这是 M5 那个决定的意外回报。当时选 C 是为了「断连 + 重启也能自愈」，
> 而自动回滚需要的恰好是同一样东西——节点上有一份自足的期望状态。

密钥同理：旧规格引用的 secret id 可能已经被轮换掉。`Keep` 的收敛集合因此
要把**回滚点引用的 id 也算进去**——只按当前规格收敛的话，旧 id 当场被清，
而回滚要重新渲染配置文件，那时解不出明文，**回滚本身失败**。
那是最不该失败的一步。

### 2.2 判据：什么算「升级失败」

| 情形 | 旧版还在跑吗 | 要不要回滚 |
|---|---|---|
| 资源 Apply 失败 | **在**（还没切换） | 不要。中止即可，机器仍是旧状态 |
| `preUpgrade` hook 失败 | **在** | 不要，同上 |
| `Runtime.Start` 失败 | 不在 | **要** |
| 健康检查在 `startupGrace` 内没通过 | 不在（或在跑但不健康） | **要** |
| `postStart` hook 失败 | 在跑 | **不要**——服务已经起来了，替用户决定停机不是引擎的职责（18-hooks §4） |

**分界线是「软链切了没有」。** 切之前失败是安全的，切之后失败才需要把
世界推回去。

### 2.3 台账的顺序错了 ★

当前顺序是：切换 → **写台账（标记新 generation 为 active）** → 健康检查。

于是一个健康检查没过的 generation **已经被记成 active**。下一轮调和读到
「当前 generation 的 digest == 期望 digest」，判定为复用，**不再切换、
不再重试**——机器停在一个坏掉的版本上，而台账说一切正常。

M6 把健康检查移到标记 active **之前**：只有健康的 generation 才是 active。

### 2.4 回滚本身失败了怎么办

回滚也可能失败（旧目录被人删了、旧镜像被清了、端口被别的东西占了）。
此时**不能继续每 60 秒重试整个升级**——那会在两个坏状态之间反复横跳，
每次都停一次服务。

做法：把这次失败**记进台账**（`GenFailed` + 失败的 digest），调和器遇到
**同一个 digest、上次失败过、且有一个旧版本可以停留**时不再自动切换，
只上报并等人处理。新的 digest（用户改了参数、换了版本）解除这个锁。

**「有旧版本可以停留」这个条件不能省。** 只判 GenFailed 的话，首次安装时
一次瞬时的健康检查失败（依赖服务还没起来、端口刚好被占、别的操作正在停
这个服务）会把组件**永久卡死**——而首装根本没有服务可丢，重试是完全正确
的。锁要防的是「反复停机」，而首装时没有机可停。

> 这条不是推演出来的：实现之后第一次全量测试就撞上了。一次部署当中的
> 瞬时健康失败让整个组件再也起不来，日志里是每三秒一条「不再自动重试」。

> 这条与「持续调和」不冲突：漂移照常检测与处理，只有**切换 generation**
> 这个动作被锁住。区别在于漂移是幂等的，而反复的升级尝试每次都要停机。

**被锁住之后，机器仍然按最后一次成功的规格被维持。** agent 拿到 `Blocked`
之后会照常调和一轮那份规格——否则「漂移照常处理」这句承诺在被锁期间就是
空的。这一轮里机器一步没动过。

于是同一个动作有两种含义，必须分开：

| | 触发 | 机器动了吗 | 是什么 |
|---|---|---|---|
| 回滚 | 新版刚失败，软链已切过去 | 动了，要推回来 | 一次**事件** |
| 维持 | 这一版早被锁住，本轮连试都没试 | 没动 | 一条**状态** |

分界线是 `Switched`——被锁的那一轮它必然为 false。

> **这不是洁癖，是第 8 步整表验收抓到的实际缺陷。** 混在一起时，一台稳定
> 停在旧版等人处理的机器每 3 秒报一次「已回滚」，20 秒里回滚计数从 2 涨到 8。
> 真正发生的那一次回滚因此**永远找不回来**——而它恰恰是运维最需要的那一条。
>
> 这与 M5 那次是同一条反过来：那次是把状态当事件发（丢一次就没了），
> 这次是把状态当事件反复播报（真事件被淹掉）。
>
> 日志的分工也因此定下来：**进入**这个状态时 agent 喊一声 WARN（只有它
> 知道上一轮是什么样），停留期间保持安静；「现在停在这里」由报告与
> `component status` 长期可见。`RolledBackFrom` 两种情形都要带——它回答的是
> 「为什么这台机器不在期望的版本上」，那是持续为真的事实，mechd 的
> Rollout 判定读的正是它。

### 2.5 三个 Runtime 的回滚各是什么

| | 回滚动作 | 需要什么还在 |
|---|---|---|
| systemd | 写回旧 unit + 切软链 + start | 旧 generation 目录 |
| docker | 按旧规格重建容器 | 旧 generation 目录 + **旧镜像** |
| compose | 按旧 compose 文件重新 up | 同上，且 override 文件在旧 generation 目录里 |

**镜像回收因此不能只看 generation 目录。** M4 把镜像回收推迟到 M6
（19-container-runtime §6.5），现在要定：**保留的 generation 引用的镜像
一律不删**。判据来自它们各自的规格里的 `imageBlob` → blob 摘要 → 镜像。

blob 同理：`retainGenerations` 保留几代，那几代引用的 blob 就不能回收。

落地时有三件事必须先定下来：

**① 引用关系存在哪里。** generation 台账里只有 seq / digest / 目录，
没有它引用了哪些 blob 与镜像。

第一个想到的方案是**每代归档一份规格**，让回收时去读它——存来源总比
存派生物稳。但它对镜像不成立：**规格里只有 blob 名，镜像引用是
`docker load` 的输出**（`Loaded image: repo:tag`），不是规格的函数。
一份归档的规格能回答「引用了哪个 blob」，回答不了「那是哪个镜像」。

所以在台账里多存两个列表：`Generation.Blobs`（摘要）与
`Generation.Images`（镜像引用），都在物化那一刻写下——**镜像引用只有
在那一刻才存在**。

**② 被回收的引用要落成状态，不能只是一个事件。**
prune 掉一代之后，它引用的镜像才成为回收候选。若把这件事当成
「prune 返回一个列表、agent 顺手删掉」，那么 agent 在这两步之间重启一次，
这些镜像就**永远**不会再被任何人想起——磁盘上多出几百 MB 且没有线索。

这与 M5 那次的教训是同一条：**状态可以重复确认，事件丢一次就永远丢了**
（`WorkloadAction` 从事件改成带时间戳的状态，正是因为这个）。因此 prune
把候选写进节点级的回收清单，GC 从清单里取；删成功才从清单划掉。

**③ 判据是全局的，而 generation 目录的回收是局部的。**
一个 blob 可以被多个实例、多个组件共用（内容寻址的直接后果），镜像更是
如此。因此「谁还在引用它」这个问题，**单个实例的调和器回答不了**。

于是分成两层：generation 目录仍由调和器按 `retainGenerations` 就地回收；
blob 与镜像的回收上移到 agent——扫描**全部**实例的全部保留 generation，
取引用集的并集，候选不在并集里才真的删。

**④ 只删我们放进去的。** 镜像没有标签可依（容器有 `managed-by`，镜像
没有），因此判据不能是「`docker images` 里多出来的」。只有**曾经被我们
物化过、并因此记进某一代台账**的镜像才会进回收清单——别人拉的镜像不在
任何一代台账里，因此永远不会成为候选。

> 并发下的取舍：agent 的实例锁是 skip 不是 queue，因此回收开始时可能还有
> 上一轮的调和在跑。**有实例在忙就整轮跳过回收**——回收可以推迟，
> 删错不可逆。

**⑤ `docker image rm` 不加 `--force`。** 带 force 会把还有容器在用的镜像
也删掉，而「还有容器在用」恰恰说明上面那套引用判据算错了。让它以
「image is being used」失败，那条错误信息本身就是诊断——这是第二道防线，
与我们自己的引用集彼此独立。

> 代价要说清楚：**两道防线独立，就意味着 e2e 无法单独钉住第一道**。
> 把引用判据改坏，dockerd 仍会拒绝删除运行中的镜像，端到端测试照样绿。
> 引用判据本身因此在 `internal/reclaim` 的单元验收里钉住；e2e 里那条断言
> 留着，是为了「两道防线一起塌」时有人喊。

mechd 侧的 blob 回收（Pack 版本淘汰之后）不在 M6 范围内：那需要先有
「Pack 可以被删除」这件事，而 `mechctl pack` 目前只查询不删除。

### 2.6 Rollout 在单机是什么

单机只有一个实例，「分批」退化成一批。但 Rollout 不只是分批：

```
pending → running → succeeded
                 ↘ failed（自动回滚后停在这里）
                 ↘ paused（人工介入）
```

M6 把**状态机与命令面**立起来（`rollout list/show/pause/resume/abort`），
分批与健康门禁的多节点语义留给 M7。这样 M7 加的是「一批变多批」，
而不是从零长出一套编排。

> 排在这里而不是 M7，理由与 M4 把 docker 提前一样：**让第二个使用者出现
> 之前，先有一个能用的抽象**。一个只服务单机的 Rollout 若长得不对，
> M7 加多节点时会推倒重来。

落地时四处与上面的草图不同，都记在这里（`internal/mechd/rollout.go`）：

**没有 `pending`。** 建记录时规格已经推出去了，`pending` 从来不会被任何人
观测到——一个只在数据库里存在半毫秒的状态，只会让 `rollout status` 的
判读多一种可能。起始状态直接是 `running`。

**多出 `aborted`。** `failed` 是「系统判定它没成功」，`aborted` 是
「人叫停了」。合成一个会让事后复盘无法回答最重要的那个问题：
这次是自己挂的，还是有人拦下来的。

**由上报推进，不设后台循环。** 判据取自实例上报的 digest 与版本，
而不是「mechd 发过什么」——**状态可以重复确认，事件丢一次就永远丢了**
（与 digest 作为收敛判据同一条理由）。上报本身是 15 秒一次的心跳，
正好是推进 Rollout 的天然节拍；一条独立的后台循环只会多一个需要
自己处理并发与重启的东西。超时判定（`RolloutTimeout`，10 分钟）
因此也在上报路径上做。

**`pause` 冻的是判定，不是部署。** 暂停期间节点照常调和、照常收敛；
被冻住的只是 mechd 那句「这次算成功/失败」。人敲 `pause` 是因为要去看
现场，而状态在他看的过程中自己往前走，等于没有暂停——`abort` 也就
不再有对象可中止。

**`abort` 真的回退**，不只是把记录标成中止。一条只改状态字段的 abort
会让运维以为世界回到了升级前，而机器上跑的还是新版——那比没有这个
命令更糟。它走的是与 `component rollback` 完全相同的那条路径。

## 3. 升级的完整路径

```
mechctl component upgrade web --version 1.3.0
  ↓ mechd：改 Pack 版本 → 重新渲染 → 新 digest
  ↓ 建 Rollout（单机=一批）
  ↓ 推送
mechlet：
  ② 物化新 generation（旧的完整保留）
  ③ preUpgrade hook          ← 失败：中止，旧版没被动过
  ④ 资源 Apply               ← 失败：中止，同上
  ⑤ Stop → 切软链 → Start    ← 从这里开始，失败要回滚
  ⑥ 健康检查（startupGrace）  ← 失败：回滚
  ⑦ 标记新 generation 为 active，写台账
  ⑧ postUpgrade hook
  ↓ 上报
mechd：Rollout succeeded / failed
```

回滚（⑤⑥ 失败时）：

```
  载入 <key>.applied.json（最后一次成功应用的规格）
  → 按它重新物化（unit / 配置 / 容器都回到旧版）
  → 切回旧软链 → Start
  → 记 GenFailed(新 digest)，锁住这个 digest 不再自动重试
  → 上报「已回滚」
```

## 4. 验收判据具体化

| # | 场景 | 期望 | systemd | docker | compose |
|---|---|---|:--:|:--:|:--:|
| 1 | 正常升级 | 新版在跑，旧 generation 保留 | ✓ | ✓ | ✓ |
| 2 | 新版**起不来** | 自动切回旧版，**服务不丢** | ✓ | ✓ | ✓ |
| 3 | 新版起来了但**健康检查不过** | 同上 | ✓ | ✓ | ✓ |

> **崩溃重启循环曾经被报成 `ok`。** systemd 的 `Restart=on-failure` 让状态
> 一直停在 `Starting`，调和器按「Runtime 正在自行恢复」让路（M5 §2.2），
> 健康检查又按「没在跑就不必探」跳过——于是一个永远起不来的新版本
> **既不被纠正也不被探测**，中心看到升级成功，自动回滚永不触发。
>
> 「没在跑就不探」这条本身是错的：**它让「没起来」与「健康」不可区分**。
> 现在探针照常跑，`startupGrace` 既是「刚起来还没就绪」的宽限，
> 也是「一直起不来」的上界；错误信息里带上工作负载状态，
> 真正的原因不会被盖住。
| 4 | 回滚之后再调和一轮 | **不反复重试**，停在旧版并上报 | ✓ | ✓ | ✓ |
| 5 | 手工 `component rollback` | 秒级切回，不重新解压 | ✓ | ✓ | ✓ |

> 「秒级」不是靠一条特殊路径实现的，而是**解析是纯函数**的直接结果：
> 回到旧版本必然产出与当年一模一样的 digest，节点因此命中已保留的
> generation，只需切一次软链。验收里直接断言这两个 digest 相等——
> 对不上就说明纯函数这条性质破了，而那会让每次回滚退化成完整重新物化。
| 6 | 升级过程中数据目录 | **一个字节都没动** | ✓ | ✓ | ✓ |
| 7 | `retainGenerations` 之外的旧版 | 目录与镜像一并回收 | ✓ | ✓ | ✓ |
| 8 | 保留中的旧版所引用的镜像 | **不被回收** | — | ✓ | ✓ |

第 2、3 条是这个里程碑的全部意义。**「服务不丢」要用真实判据核对**：
升级过程中持续打 HTTP，中断窗口必须是有界的一次重启，而不是「再也没起来」。

**这张表由 `test/e2e/upgradematrix_linux_test.go` 整张过一遍**，三个 Runtime
共用同一段断言、只换夹具（第 3 行在 `rollback_linux_test.go`，镜像那两格在
`imagegc_linux_test.go`）。收成一张表而不是散在各步里，是因为里程碑承诺的是
**一整套性质在三种运行形态下都成立**，不是九个孤立的断言——「每条都验过、
整张表没人看过」正是它要防的。

判据一律取「端口上有没有人应答」：unit active、容器 running、project up
各说各话，只有这一条在三个 Runtime 上是同一件事。

> 整张表第一次跑起来就抓到一处：第 4 行**没有成立**。锁本身是好的——
> 坏版本再没被试过，服务一次都没掉——但机器每 3 秒被报一次「已回滚」。
> 那是把一条稳定状态当成反复发生的事件播报，真正发生的那一次回滚因此
> 淹没在噪声里。修法见 §2.4 的补充。

## 5. 实施顺序

| # | 内容 | 可验证的成果 |
|---|---|---|
| 1 | 台账顺序修正：健康检查先于标记 active | 健康失败的 generation 不会被当成 active |
| 2 | `<key>.applied.json` + 密钥保留 | 节点上有一份可用于回滚的旧规格 |
| 3 | 自动回滚：切回 + 起旧版 + 上报 | 新版起不来时服务不丢（三个 runtime） |
| 4 | 失败 digest 锁：不反复重试 | 回滚之后稳定停在旧版 |
| 5 | `component upgrade` / `rollback` | 端到端升级与手工回滚 |
| 6 | Rollout 状态机 + `mechctl rollout` | 升级过程可见、可暂停、可中止 |
| 7 | generation 与镜像/blob 回收 | 保留中的版本引用的镜像不被删 |
| 8 | 三个 Runtime 的升级/回滚 e2e | 验收表整张过 |

第 1 步先行：它是个**已经存在的错误**，而后面每一步都建立在「台账是可信的」
之上——不先修，第 3 步的回滚会与一个错误的 active 记录打架。

## 6. M6 收尾时明确留下的缺口

| 缺口 | 现在的行为 | 留到 |
|---|---|---|
| **原样重试同一个版本** | 没有入口 | M7 |
| mechd 侧的 blob 回收 | 只回收节点侧 | Pack 可删之后 |
| Rollout 分批与健康门禁 | 单机=一批 | M7 |

第一条要说清楚，因为它是 §2.4 那把锁的**直接代价**：

> 环境问题修好了（依赖服务起来了、端口让出来了），运维想原样再试一次
> **同一个版本**——现在做不到。解锁只认「新的 digest」，而改一个参数
> 才会产生新的 digest。`mechctl component upgrade --version <同一个>`
> 算出来的仍是被锁的那一个。
>
> 不在 M6 顺手加一个 `--force`：那个动作会绕过锁**立即停机重试**，
> 而锁存在的全部理由就是防止反复停机。它需要的是一个想清楚的语义
> （清掉失败记录？只解锁一次？要不要二次确认？），不是一个开关。
> 现在的出路是改一个无关紧要的参数——难看，但不会伤人。
