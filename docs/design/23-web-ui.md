# 24. Web UI（M8）

> 目标：**由 params schema 自动生成配置表单**，让不写 YAML 的人也能部署与
> 运维。这是 Cloudera Manager 可用性的核心来源，也是当初选自定义 params
> 类型子集而不是 JSON Schema 的**第二个理由**（[ADR-0007](../adr/0007-params-custom-subset.md)）。

## 0. 现状：承诺画在架构图里，但一行都没写

[01-architecture §36](01-architecture.md) 的图里画着 `浏览器 ──HTTPS──> mechd`，
[00-overview §125](00-overview.md) 写着「Web UI 源码位于核心仓 `webui/`，
通过 `go:embed` 打进 `mechd`」。

实际上：

- `webui/` **不存在**
- mechd 只有 JSON API（`/api/v1/…`，24 条路由）
- 仓库里**没有任何前端工具链**，CI 是纯 Go 的四个 job
- 认证只有一个 admin token（`Bearer`），没有用户、没有会话
- RBAC 在 [08-security §4](08-security.md) 只有三行草稿（`viewer` / `operator` /
  `admin`，授权到 Site 级），**没有实现**

所以 M8 的起点是「**从零开始，但 API 已经齐了**」——这与 M7 起点
（「第二台机器真的加不进来」）不同：那时缺的是能力，这次缺的是**表面**。

## 1. 已经定过的，不重做

| 决定 | 出处 |
|---|---|
| UI 源码在核心仓 `webui/`，`go:embed` 进 mechd | [00-overview §125](00-overview.md) |
| **单机与多节点是同一个 UI**，不做功能子集 | [ADR-0026](../adr/0026-standalone-runs-mechd.md) · [01-architecture §30](01-architecture.md) |
| params schema 就是表单的**唯一真相来源** | [ADR-0007](../adr/0007-params-custom-subset.md) |
| `sensitive` / `secret` 参数在 API 响应与 UI 中一律脱敏 | [08-security §5](08-security.md) |
| mechd 默认 `0.0.0.0:8443` + HTTPS（自签，长有效期，可轮换） | [08-security §3.2](08-security.md) |
| 部署时零外部依赖：**不允许 CDN、不允许运行时拉包** | [ADR-0015](../adr/0015-offline-first-hermetic.md) |

params schema 已经带齐了生成表单所需的全部元数据，**这一步不需要给 pack/v1
加任何字段**：

| 字段 | 表单里怎么用 |
|---|---|
| `type`（12 种） | 控件选型：`bool`→开关，`enum`→下拉，`path`→路径输入，`secret`→密码框 |
| `description` | 字段说明 |
| `unit` | 输入框后缀 |
| `group` | 分组（缺省「常规」） |
| `advanced` | 默认折叠 |
| `min` / `max` / `pattern` / `values` | 前端即时校验（**服务端仍然要校验**） |
| `required` | 必填标记 |
| `sensitive` | 不回显、不进日志 |
| `immutable` | 已部署的 Component 上置灰，提示需重建 |
| `restartRequired` / `reloadRequired` | **保存前告诉用户会发生什么** |
| `from` | 只读展示——它是客观事实，用户不可填 |
| `defaultFrom` | 显示算出来的建议值，允许覆盖 |
| `generate` | 不显示输入框，显示「由引擎生成」 |

> 最后四行是这套 schema 真正的价值所在。一个只认 `type` 的表单生成器，
> 任何 JSON Schema 都能做；而「改这个参数会重启服务」「这个值是推导出来的
> 你改不了」——那是 Cloudera Manager 的界面好用的原因，也是当初不用
> JSON Schema 的原因。

## 2. 要定的问题

### 2.1 前端技术栈

**调研过的做法：**

| 项目 | 做法 | 代价 |
|---|---|---|
| **Cockpit**（Red Hat） | 原生 JS + PatternFly，无打包器起家 | 与本项目场景最像（Web 管 Linux 机器）；后期仍引入了构建链 |
| **Syncthing** | 单页 + 老 Angular，产物随二进制发布 | 「零构建依赖」曾是优点，后来框架老化成了负债 |
| **Prometheus** | 原生 JS → React（npm） | 迁移后贡献门槛明显上升 |
| **Grafana** | React + 自建构建链 | 前端体量超过后端，非前端贡献者进不去 |
| **Traefik** / **Portainer** | Vue / Angular + npm，产物 embed | 同上 |
| **Gitea** | 服务端模板为主，交互处增量加 JS | 贡献门槛低；复杂交互写起来笨 |
| **htmx 一类** | 服务端渲染 HTML 片段，前端几乎无状态 | 表单生成场景很合适；实时更新要另想办法 |

共同点：**所有引入 npm 的项目，前端最终都长成了另一个项目**。而分歧点是
「这个界面有多少客户端状态」。

Mecharion 的界面有多少客户端状态？表单生成是**一次性渲染**（拿到 schema 画
表单），状态页是**周期刷新**，Rollout 进度是**流式追加**。没有富交互、
没有画布、没有拖拽。

**代价必须写清楚**：不管选哪个，产物都要 `go:embed` 进 mechd，而 mechd 现在
是 17.9 MB。一套 React 产物大约再加 1–3 MB（gzip 后），原生方案几十 KB。
边缘机器上这点差别不致命，但它是**每台机器**都要装的。

**决定：Vue 3 + Element Plus + UnoCSS，Vite 构建；产物由 `go generate`
生成，不进仓库**（[ADR-0036](../adr/0036-webui-vue-and-generated-dist.md)）。

选 Vue 而不是原生：表单生成是**数据驱动的动态渲染**（12 种类型 × 分组 ×
折叠 × `from` 只读 × `immutable` 禁用 × ConfigGroup 层级），原生 JS 写这个会
很快变成手搓的 DOM 拼接。这一块正是 M8 的核心价值，值得用成熟的渲染层。

- **Element Plus**：表单控件、表格、抽屉、消息提示现成。表单生成要的控件
  它全都有，自己写一套没有意义
- **UnoCSS**（Tailwind 语法）：布局与间距用原子类，几乎不写 CSS 文件

### 构建与目录

```
webui/                      ← Vue 源码（npm 项目）
  package.json  src/  vite.config.ts
internal/webui/
  embed.go                  ← //go:embed all:dist
  gen.go                    ← //go:generate（npm build 并拷进 dist/）
  dist/
    .gitkeep                ← 仓库里只有这一个文件
```

- `.gitignore` 忽略 `internal/webui/dist/*`，只留 `.gitkeep`
- **`//go:embed all:dist`**——`all:` 前缀让 embed 收下点号开头的文件，
  因此**空仓库也编译得过**。少了它，一次干净 clone 直接编译失败
- 开发期 `npm run dev`，Vite 开发服务器反代到 mechd，不必每次全量构建
- `make webui` = `go generate ./internal/webui/...`

### 没构建时要**吵**

一个没跑过 `go generate` 的 mechd，`dist/` 里只有 `.gitkeep`。此时
**不能返回 404**——那看起来像路由坏了。必须给一页明确的说明：

> Web UI 尚未构建。在有 Node 的机器上执行 `make webui` 后重新构建 mechd。

代价照实写：

- **「拿到源码就能 `go build` 出完整产物」这条性质到此为止**：没有 node 的
  机器构建出的 mechd 没有 UI。这与 `sqlcgen`/`agentpb` 的既有纪律**不一致**，
  是一次刻意的例外——前端产物的体量与变更频率跟那两者不是一个量级
- **发布必须经过带 node 的环境**；构建可复现要靠 `package-lock.json` 锁死
- Element Plus 会让产物明显变大。对策是**按需引入 + embed 前预压缩 +
  `Content-Encoding: gzip` 直出**——把该做的都做到，但**不设体积硬指标**：
  为了凑一个数字去砍功能，换来的是更差的界面
- 非前端贡献者进不去 `webui/src/`；框架五年后多半要重写一次

### 2.2 浏览器怎么认证

现在只有一个 admin token（`Authorization: Bearer`）。浏览器没有地方放它。

**调研过的做法：**

| 项目 | 做法 | 代价 |
|---|---|---|
| **Prometheus** / **Traefik dashboard** | 不做认证，要求前面挡反向代理 | 边缘门店没有反代；等于默认裸奔 |
| **Syncthing** | 可选 basic auth，默认无 | 同上 |
| **Cockpit** | PAM，登录**系统用户** | 与「不建 mecharion 用户」的既有决定冲突；且多节点下 mechd 那台的系统用户不代表集群权限 |
| **Portainer** | 自建用户体系 + JWT | 要做用户表、口令哈希、找回流程 |
| **Grafana** | 自建用户体系 + session cookie（+ 可选 OIDC） | 同上，更重 |
| **k3s / Talos** | 不做 Web UI | 回避了这个问题 |

**决定：做用户体系，但只做最简的一层。**

| 做 | 不做 |
|---|---|
| 用户名 + 口令登录 | Site 级授权 |
| **图形验证码** | 角色划分（viewer / operator / admin） |
| HttpOnly session cookie | OIDC / LDAP / SSO |
| 审计 actor 记到人 | 口令找回、邮箱、多因素 |

**登录即全权**：现阶段所有用户等价于管理员。08-security §4 那三个角色
**留到后续里程碑**——它们要跟 Site 模型一起想清楚，而 Site 级授权是那里面
最难的一半。现在把角色字段先建出来但只有一个取值，等于替将来挖坑：
到时候真要分角色，表结构、接口、审计都得重来一遍。**不如现在不建。**

> 这是一条要写清楚的**限制**，不是疏漏：M8 之后，任何能登录 UI 的人都能做
> 任何操作。多人协作且需要权限隔离的场景，**在角色做出来之前不要开放 UI**。

#### 验证码：PoW + 滑块，不做传统图形验证码

**传统图形验证码现在挡不住机器。** 2026 年商用求解服务对图像验证码
**亚秒级、成功率约 99%**，文字扭曲类已经失效，Cloudflare Turnstile 干脆
放弃了图像挑战。自绘一个扭曲文字验证码，等于做一个只挡住人、挡不住机器的门。

调研过的离线自托管方案：

| 方案 | 机制 | 结论 |
|---|---|---|
| **ALTCHA** | PoW，Argon2/Scrypt **内存硬**，压制 GPU/ASIC | 协议简单可自实现，选它的思路 |
| **Cap** | PoW，SHA-256 | SHA-256 对 GPU 友好，成本压制弱于内存硬 |
| **mCaptcha** | PoW，可变难度 | **AGPL**，与本项目 Apache-2.0 嵌入有摩擦 |
| **Anubis** | 反代层 PoW 挡 AI 爬虫 | 不是表单验证码，形态不对 |
| 滑块拼图 | 轨迹行为 | ML + 轨迹重放可破 |
| 传统图形 | 文字扭曲 | 对自动化基本无效，且排除视障用户 |

**决定：PoW 做防护，滑块做可见的人机信号。** 分工必须写清楚，否则会高估
整体强度：

| 层 | 提供什么 | **不**提供什么 |
|---|---|---|
| **PoW**（Argon2 内存硬） | 给每次尝试标价；不参与 AI 军备竞赛 | 不证明「你是人」 |
| **滑块** | 熟悉的交互、看得见的验证 | **不提供安全性**，ML 可破 |
| **按用户/IP 限流** | 挡慢速撞库 | 挡不住分布式低频 |
| **argon2id 口令哈希** | 库泄露后的离线爆破成本 | 挡不住弱口令 |

不用 reCAPTCHA / hCaptcha：它们要连 Google / Cloudflare，而部署时零外部依赖
是这个项目的底线（[ADR-0015](../adr/0015-offline-first-hermetic.md)）——
边缘门店那台机器很可能根本不出网。

### 2.3 自签证书的浏览器体验

mechd 默认 `0.0.0.0:8443` + **自签**证书。浏览器会红屏警告，而边缘场景恰恰是
「拿笔记本连门店那台机看 UI」——每次都点「继续访问」是很差的体验，更糟的是
**它训练用户忽略证书警告**。

**调研过的做法：**

| 做法 | 谁在用 | 代价 |
|---|---|---|
| 自签 + 让用户点过去 | Syncthing、Cockpit 默认 | 训练用户忽略警告 |
| 自签 + **把 CA 给用户装** | 企业内网常见 | 多一步，但只做一次；我们**本来就有 CA**（M7 的节点 CA） |
| 只监听回环 + 要用户自己开隧道 | 部分 | 与「默认 0.0.0.0」的既有决定冲突 |
| 要求用户提供真证书 | 生产级部署 | 边缘门店拿不到 |

**倾向**：保持自签，但把「取 CA 并信任它」做成一条明确的、文档化的一步
（`mechctl ca export` 之类），并在首次访问时给出说明页。**不做**「生成一个
浏览器天然信任的证书」——那不存在。

### 2.4 UI 的范围：只读还是可写

这是影响 M8 大小最多的一个决定。

| 范围 | 包含 | 风险 |
|---|---|---|
| **只读** | 组件/节点/状态/漂移/Rollout 进度/事件/审计 | 低。但「自动生成表单」这个 M8 的核心目标做不了 |
| **可写（配置）** | 上面 + 改参数、部署、升级、rollout 控制 | 表单生成是核心价值；但每个写操作都要想清楚确认与权限 |
| **全功能** | 上面 + 节点加入、token 管理、Pack 上传 | token 与 Pack 上传涉及凭据与供应链，风险最高 |

**决定：全功能**——查询、改配置、升级与 Rollout 控制、节点加入引导、
join token 管理、Pack 上传。

**写操作沿用 CLI 已有的那套语义**：同一个 API、同一套确认要求。UI 不发明
新的动作，它只是那些动作的另一个入口。一个「只有 UI 才能做的事」会让 CLI
与 UI 的能力集分叉，而那意味着自动化脚本迟早要去解析 HTML。

**一处例外，要说清楚**：`node bootstrap` 在 UI 里做成**引导**而不是代执行。

`mechctl node bootstrap ssh://…` 是从**敲命令的那台机器**发起 SSH。若 UI 上
点一下就让 mechd 去 SSH，mechd 就得持有 SSH 私钥——而 M7 的一条主要收益正是
「长期暴露面从 SSH 常开降为零入站端口」（[08-security §3.6](08-security.md)）。
让控制面常备一把能登录所有节点的钥匙，等于把那个收益还回去。

因此 UI 做的是：生成 token、算好 CA 指纹、**把那条命令拼好让人复制**。
价值（不用记参数、不用手抄指纹）拿到了，钥匙不进 mechd。

### 2.5 实时性

Rollout 进行中「第 2/3 批」需要动起来；状态页需要周期刷新。

| 做法 | 代价 |
|---|---|
| 轮询（3–5s） | 最简单；100 台机器的集群里，一个开着的页面每秒几次查询 |
| **SSE**（`text/event-stream`） | 单向、走普通 HTTP、浏览器自带重连；与我们已有的 `/events` 天然契合 |
| WebSocket | 双向，但这里**不需要**双向——所有写操作都是普通 POST |

**倾向：SSE**。理由与协议层选服务端流是同一条（[ADR-0029](../adr/0029-push-over-server-stream.md)）：
下行推送、上行独立，不需要全双工。轮询作为兜底（SSE 断了自动退化）。

### 2.6 表单生成到什么程度

不打算做的（要写清楚，否则会被当成疏漏）：

- **不做「表单即真相」**：UI 生成的仍然是那份 `params` 覆盖，与 CLI 写 YAML
  等价。UI 不引入第二种配置来源
- **前端校验不是校验**：`min`/`max`/`pattern` 在前端只是即时反馈，
  **服务端必须原样再校验一遍**。少了这条，一个绕开 UI 的请求就能写进非法值
- **`secret` 永不回显**：编辑时显示「已设置」而不是掩码后的原值——掩码会让人
  以为改一个字符就能改口令

### 2.7 Pack 上传：唯一一处新增的供应链入口

其余写操作都只是既有 API 的另一个入口，Pack 上传不是——它让**一份新的
可执行内容**从浏览器进到 mechd。

规则：

- 只接受 `.mpack`，**上传即走与 `mechpack lint --hermetic --strict` 同一套校验**，
  不通过就拒绝，不落盘
- 校验在**落进 Pack 集合之前**做。先落盘再校验的话，一次失败的上传会留下
  一个半截 Pack，而放置阶段会看见它
- 上传进审计，记明是谁传的、摘要是多少
- **不做「上传即部署」**：上传只是把它放进本地 Pack 集合，部署仍是单独一步

> 这与 [ADR-0015](../adr/0015-offline-first-hermetic.md) 不冲突：那条禁的是
> **部署时联网获取**，而这里是人主动把包送进来——正是离线环境里 Pack 的
> 正常流转方式（U 盘拷进内网，再从浏览器传上去）。

## 3. 登录与会话

```
浏览器  ──GET  /api/v1/challenge   →  PoW 难题 + 滑块图（一个 challenge id）
        │                            ↓ 浏览器后台算 PoW，用户拖滑块
        ──POST /api/v1/session     →  用户名 + 口令 + PoW 解 + 滑块位移
                                      ↓ 难题一次性核销、argon2id 比对
        ←── Set-Cookie: m7n_session (HttpOnly; Secure; SameSite=Strict)
        ──其余请求带 cookie
```

**难题一次性核销**：同一个 challenge id 用过就作废，且有 TTL。
少了这条，攻击者算一次 PoW 就能重放无数次登录尝试——PoW 的成本压制归零。

**出题本身也要限流，而且要与登录失败锁定分开算。** `GET /api/v1/challenge`
不需要任何凭据就能触发，而每次出题都要服务端真算一次 Argon2、画两张滑块
图——此前只有登录失败锁定（`authn.Limiter`）挡在这条路径上，
它只问「这个来源有没有因为登录失败被锁定」，出题本身从不记录：不失败、
只是拼命出题一样能把 CPU 吃满。修复加了一层独立的 `authn.ChallengeLimiter`
——单 IP 每分钟 10 次、全局每分钟 200 次的滑动窗口，两个都查完才真正出题；
另外给内存里未核销的挑战数设了一个独立的硬上限（`MaxPendingChallenges`），
不依赖限流参数今天恰好配得保守。

**cookie 而不是把 token 存在 localStorage**：`HttpOnly` 让脚本读不到它，
一次 XSS 就偷不走会话。代价是要防 CSRF——靠 `SameSite=Strict` 加上写操作
校验一个自定义头（浏览器跨站发不出自定义头）。

**会话落 SQLite，不放内存**：放内存的话 mechd 一重启所有人被登出。这与
「状态可以重复确认」是同一条——重启前后应当看到同一个答案。

**Bearer token 不删**：CLI 与脚本继续用它。两条认证路径并存，在
`API.guard` 一处收口——散开的话，「某个接口忘了检查会话」就是一个洞。

### 3.1 只有一个 admin，首次访问 UI 时设定口令

**账号是固定的 `admin`，不支持增加账户。** 初始化页与登录页都把用户名显示成
不可编辑的 `admin`，并说明「这台机器只有一个管理员账号」。

第一个（也是唯一一个）用户**在首次访问 UI 时创建**：

```
浏览器首次打开  ──GET  /api/v1/auth/state    →  {"initialized": false}
                └─ 渲染初始化页：用户名固定 admin，只让设口令 + 初始化令牌
                ──POST /api/v1/auth/bootstrap →  口令 + 令牌
                                                 ↓ 令牌对得上才继续；一次性：之后永久 409
                └─ 转到登录页
```

**为什么不是 `mechctl user create`。** 目标是**无人值守部署**：离线场景下
部署脚本自动完成「装工具 + 装组件包」，人只在最后打开一次浏览器就拿到管理
能力。要求先 SSH 上去敲一条命令，等于把那条自动化链断在最后一步。

**因此也不需要纠结「生成的口令怎么送达」**——口令由本人在初始化时输入，
既不进安装输出，也不进任何日志。

#### 代价：初始化之前存在一个抢注窗口——用一次性令牌关严

mechd 默认监听 `0.0.0.0:8443`。从装完到有人完成初始化之间，如果初始化页
只认口令，那就是「谁先提交谁就成为管理员」。

**关严它的做法是一次性 admin token 门禁，不是 PoW/滑块**（[ADR-0039](../adr/0039-bootstrap-token-gate.md)）：初始化抢注是一次性竞赛，PoW
只让「反复尝试」变贵，对唯一有意义的那次提交没有帮助——早期版本确实按
登录页那一套接了 PoW/滑块，但从未真正接到服务端，补上之后也验不动真正的风险，因此整个撤掉，换成复用
mechd 首次启动就打印过的那个 admin token。不知道它的人，无论提交多快
都赢不了这场竞赛——窗口因此是**真正关严**，不是「记录下来但关不严」。

配套的其它手段仍然保留，作为这道门之外的纵深：

| 手段 | 作用 |
|---|---|
| **令牌门禁**：没有 admin token 就完不成初始化 | 关严抢注窗口本身（ADR-0039） |
| **一次性**：初始化过一次之后端点永久关闭（409），且这条判据排在令牌校验之前 | 「已经做过了」对谁都是同一个答案，不因为没带令牌就变成别的错误 |
| **启动即喊**：未初始化时 mechd 每次启动都打一条 WARN | 让「窗口还开着」看得见 |
| **审计记来源 IP** | 事后能回答「是谁初始化的」 |
| **限流**：与登录共用同一套 IP 失败锁定 | 令牌熵大到暴力破解不现实，限流是纵深，不是承重件 |

**不做超时锁定**（Portainer 那种）：部署脚本装完到人去访问可能隔几个小时，
超时会把正常流程锁死，而那时唯一的出路是回到服务器上敲命令——正好是这个
方案要避免的事。

#### 服务器侧的补救通道

口令忘了、或者要把机器交还给下一任，仍然要有出路。这些走 CLI，用 admin
token 认证：

```bash
mechctl user show          # 是否已初始化、口令上次何时改的
mechctl user passwd        # 重设口令（交互式或 --password-file）
mechctl user reset -y      # 抹掉 admin，**重新打开初始化窗口**
```

**没有 `user create`、没有 `user list`、没有 `user delete <name>`**——
只有一个账号，那些动词没有意义。

**口令不走命令行参数**——命令行会进 shell history 与 `ps`。这与 `secret`
类型参数禁止 `--set` 明文是同一条纪律（[16-secrets](16-secrets.md)）。

> **多用户为什么不做**：没有角色划分的多用户，在**权限隔离**上等于零
> （所有人都是全权）；它真正能提供的是**问责**（审计记到人）与**凭据
> 生命周期**（离职删一个人）。这两项的价值要等角色做出来之后才成立，
> 现在做等于先付复杂度、后拿收益。

## 4. 表单生成

一个参数 → 一个控件，全部信息来自 params schema（§1 的表）。

**必须做对的四件事**（它们是这套 schema 存在的理由）：

1. `from` 的参数**只读展示**，不给输入框——它是推导出来的客观事实
2. `immutable` 的参数在**已部署**的 Component 上禁用，并说明需重建
3. `restartRequired` / `reloadRequired` 的改动，**保存前**告诉用户会发生什么
4. `secret` **永不回显**：显示「已设置」而不是掩码后的原值——掩码会让人
   以为改一个字符就能改口令

### 4.1 表单挂在哪一层：ConfigGroup

路线图把「ConfigGroup 的 UI 呈现」明确挂在 M8（[25-roadmap](25-roadmap.md)），
它不是锦上添花——**参数覆盖本来就是按组走的**，不是全局的
（[ADR-0021](../adr/0021-config-group.md)）：

```
Component
└─ Role
   ├─ params          对该 Role 全部实例生效（隐式 default 组）
   └─ ConfigGroup[]   具名子集，覆盖 Role 级取值
        └─ RoleInstance
```

于是表单必须回答两个问题，而它们很容易被做成一个：

| 问题 | 界面上是什么 |
|---|---|
| 这个值**从哪来**？ | Pack 默认 / Role 级 / 本组覆盖——三层要能看出区别 |
| 我改的是**谁**？ | 当前编辑的是哪个组，影响哪几台机器 |

**做法**：表单顶部选组（缺省是 Role 级那个隐式组），每个字段标出它此刻的
取值来自哪一层；改动落在当前选中的组上。

**不显示来源层的话，最常见的一类误操作就没法避免**：运维以为在改一台机器，
实际改的是 Role 级——那会波及该角色的全部实例。这与 CLI 里
`--role` / `--node` 要显式指定是同一件事，只是界面上更容易含混。

> 「合并同配置组」那条辅助命令（路线图同一行）**不在 M8**：它是 CLI 的
> 便利，与表单生成无关，且需要先有真实的多组使用经验才知道该怎么合。

**不做的**：

- **不做「表单即真相」**：UI 产出的仍是那份 `params` 覆盖，与 CLI 写 YAML
  等价。不引入第二种配置来源
- **前端校验不是校验**：`min`/`max`/`pattern` 在前端只是即时反馈，
  服务端必须原样再校验一遍。少了这条，一个绕开 UI 的请求就能写进非法值

### 4.2 第 5 步开工前要定的五件事

到第 5 步为止，**这套表单需要的接口一个都不存在**。已有的 24 条路由里
没有任何一条回答「这个 Pack 声明了哪些参数」「这个值现在是多少」
「它来自哪一层」。所以第 5 步的主体是后端，前端反而是它的消费者。

**① 声明合并与来源层由 `render` 导出，mechd 不重写一遍。**

两件事都已经在 `internal/render/params.go` 里：`paramDecls` 做三层声明
合并（Pack 顶层 → `roles[].params` → `profiles[].params`，且 profile 层是
**逐字段覆盖**不是整体替换），`userSet` 按 组 → 角色 → 组件 的优先级找值。

在 mechd 里照着再写一遍是最省事的做法，也是最坏的：**两处各自决定优先级，
而它们只会在某个取值不对时才被发现，那时没人会想到去比对两份实现。**
因此从 `render` 导出一个只解析参数、不渲染资源的入口，两边共用同一段
判断。

> 代价：`render` 的导出面多一个函数，而它此前只有一个入口（`Render`）。
> 一个包的导出面越小越好，但「同一条规则只有一份实现」比它更重要。

**② `from` 的值要真算出来，因此表单走完整管线。**

`from` 参数是只读展示（§4 第 1 条），但**展示需要值**——而 `from` 的求值
依赖拓扑（provider 的 exports 先算完）与放置结果。因此已部署组件的表单
跑一次真正的解析，不走捷径。

未部署的 Pack（第 6 步的「新建部署」表单）上没有放置结果，`from` 算不出来。
那里显示「**部署后确定**」，不显示空值——空值看起来像「没配」，而它是
「还没到能知道的时候」。

**③ `secret` 只回一个布尔，不回值，也不回长度。**

验收表第 12 条要的是「不回显」。长度也是信息：它把爆破空间从「所有口令」
缩到「12 位的口令」。因此响应里只有 `set: true|false`。

来源层照常回——「这个口令是在组一级设的」不泄漏口令本身，而它恰恰是
运维要知道的：改错层会波及整个角色。

**④ 字段顺序按 `(group, advanced, name)` 排，Pack 作者写的顺序保不住。**

`pack.Pack.Params` 是 `map[string]Param`，YAML 里的书写顺序在解码时就丢了。
不排序的话更糟：Go 的 map 遍历顺序是随机的，**表单每次轮询都会重新洗牌**。

代价照实写：一个 Pack 作者精心安排的「先填连接串再填线程池」表达不出来，
只能靠 `group` 把相关的圈到一起，组内按字母序。要恢复书写顺序得让
`pack` 包换成保序解码——那会动到 Pack 的解析路径，不在第 5 步做。

**⑤ 表单挂在 `role` + `configGroup` 上，缺省是角色级那个隐式组。**

§4.1 已经定了要显示「我改的是谁」。落到接口上就是这两个参数：不给
`configGroup` 时编辑的是角色级取值（影响该角色全部实例），给了就是那个组。

**这一步只读。** 写回（PATCH）是第 6 步。把「能看见正确的表单」与
「能存进去」分开，是因为前者的判据是**渲染对不对**，后者的判据是
**落库与下发对不对**——混在一步里，一次失败要查两层。

## 4.3 第 6 步开工前要定的六件事

### ① 改配置**不能**走 `deploy --update`

这是开工前查出来的一个雷。CLI 现在唯一能改已部署组件参数的路径是
`component deploy <pack> --update --set k=v`，而 `Deploy` 会**重算放置**：

```go
// resolve.go:213
if len(req.Nodes) == 0 {
    return nil, fmt.Errorf("必须指定节点：用 --nodes 或 --role <角色>=<节点列表>")
}
```

也就是说，一次「只想把日志级别从 info 改成 debug」的操作，**被迫重述整个
拓扑**。而重述拓扑时少写一个节点名就是一次缩容。`--allow-remove` 会拦住它
（[14-placement §6](14-placement.md)），但那道闸门是给「确实要缩容」准备的
——让日常改配置反复去撞它，迟早会有人习惯性地加上 `--allow-remove`。

**决定：新增 `PATCH /api/v1/components/{name}/params`，只改参数，不碰放置。**
`13-mechd §3.1` 的接口草图里本来就写着 `PATCH /api/v1/components/{name}`，
只是一直没实现。

> 代价：`deploy --update --set` 这条路仍然保留（它对「同时改拓扑与参数」
> 是对的），于是改参数有两条路。文档要说清楚**默认用哪条**：
> 日常改配置用 `config set`，只有确实要动拓扑时才用 `deploy --update`。

### ② 同一步补上 `mechctl config get / set / explain`

[§2.4](#24-ui-的范围只读还是可写) 的纪律是「UI 不发明 CLI 没有的动作」。
若只加 `PATCH` 给 UI 用，就等于在 UI 里做出了一个 CLI 做不到的事——
这正是第 7 步把 ConfigGroup 整个推迟的理由，不能在第 6 步自己犯。

因此第 6 步的 CLI 面：

```bash
mechctl config get     -c <component> [-r <role>]
mechctl config set     -c <component> [-r <role>] k=v [--set-file k=@path]
mechctl config explain <param> -c <component>
```

`--node`、`config group *`、`config diff` 留给第 7 步——它们全都要 ConfigGroup。

**`config explain` 与表单的「来源」列是同一份实现**（`render.Form`）。
ADR-0021 把 explain 称为「多出一层解析后的**必要补偿**」，而第 5 步已经把
那份补偿做成了 UI 的一列；CLI 这一侧只是换个渲染方式。

### ③ `secret` 在浏览器里就是密码框，这与 CLI 的禁令不矛盾

CLI 禁止 `--set` 明文传 secret，理由是**命令行会出现在同机任何用户的
`ps` 输出里，也会进 shell 历史**（spec §7.7）。这两条暴露路径在浏览器里
都不存在：POST body 不进浏览器历史，不出现在任何进程的 argv 里。

**决定：UI 用 `<input type=password>`，值走 HTTPS 的 POST body。**

它依赖两条前提，必须一起成立，否则这个决定不成立：

- **请求体绝不进日志**。`sensitive` / `secret` 参数在服务端日志、审计事件、
  错误信息里一律不得出现原值（[08-security §5](08-security.md)）
- **传输必须是 HTTPS**。`--insecure-http` 只供本机调试，那个模式下
  已经有一条启动 WARN

> 不做「上传口令文件」那种 UI：它是把 CLI 的 `--set-file` 照搬过来，
> 而 `--set-file` 存在的唯一理由是绕开 argv，浏览器里没有这个问题。
> 照搬只会多一个更难用的控件。

### ④ 保存前的预览就是 dry-run，不另写一套

验收表第 11 条要求「改 `restartRequired` 参数，保存前告知会重启」。
第 5 步已经把这些标志渲染在字段上了，但那只回答「这个参数会不会重启」，
不回答「**我这次改了哪些、合起来会发生什么**」。

**决定：保存前调一次 `dryRun`，把结果摆出来**——哪些实例的 digest 变了、
会重启还是 reload、影响几台机器。复用 `DeployRequest.DryRun` 与 `/diff`
背后那条管线，不另写预演逻辑：**同一条管线少走最后两步**，这是 13-mechd
已经定过的做法。

### ⑤ 确认分三档，与 CLI 对齐

[10-cli §7](10-cli.md) 的三档在 UI 里各自对应什么：

| 档 | CLI | UI |
|---|---|---|
| 一档 y/N | `-y` | 一个确认弹窗 |
| 二档 输入组件名 | 输入 Component 名 | 输入框，要打对名字才能点确定 |
| 三档 输入 `purge-all` | 同名 | 同左 |

落到具体动作：改参数（不重启）不确认；**改动会重启或 reload 的**走一档；
升级 / 回滚走一档且必须先看 dry-run；删除组件走二档。

**一档不能省。** 一个「点了就生效」的配置页，与 CLI 那条要敲 `-y` 的命令
是同一个动作的两个入口，而两个入口的危险程度不该不同。

### ⑥ 部署新组件需要一个 Pack 列表接口

现在没有任何接口能回答「本地有哪些 Pack、各有哪些版本与形态」——
`packindex` 只在 mechd 进程内被用。新增 `GET /api/v1/packs`。

未部署的 Pack 上表单仍然可用（第 5 步的 `Derived` 为空 → `from` 标
`pending`），因此「先看看这个 Pack 要配什么」在部署之前就能做。

## 4.4 第 7 步：ConfigGroup 全链路

[ADR-0021](../adr/0021-config-group.md) 在 2026-08-02 就定了具名 ConfigGroup，
表从 `00001_init.sql` 起就在，解析链、渲染路径、多盘绑定的求值代码**全都
已经写好**。缺的只有一件事：**没有任何创建入口**。

`ConfigGroups().Upsert` 在生产代码里一次都没被调过（只有 `repo_test.go`
用它），`mechctl config group *` 一行代码没有，`pathBindingsFor` 是个
`return nil` 的桩，`store.ConfigGroup` 连 `Paths` 字段都没有。

后果是 ADR-0021 的**原始动机场景做不到**：

```yaml
# spec §8.6 里那个例子——12 盘机器绑两块盘
configGroups:
  - name: 12-disk-nodes
    nodes: [node-7, node-8]
    paths:
      dataDirs: [data1, data2]
```

第 7 步把这条链路补齐。它**不是「给 UI 加个按钮」**：按
[§2.4](#24-ui-的范围只读还是可写) 的纪律，UI 不发明 CLI 没有的动作，
因此 CLI 与 UI 一起做。

### 4.4.1 成员用显式节点名单，不用标签选择器

**调研过的做法：**

| 系统 | 成员怎么定 | 代价 |
|---|---|---|
| Cloudera Manager Role Config Group | 显式挑 Role Instance | 加机器要手动挪组 |
| Ambari Config Group | 显式主机名单 | 同上 |
| Kubernetes | 标签选择器（selector） | 成员随标签变化**自动**变，而那次变化没有操作记录 |
| Ansible inventory group | 静态清单（可动态生成） | 动态清单的变化同样不留痕 |

**决定：显式节点名单。**

理由不是「简单」，是**组成员变更会触发重渲染与可能的重启**（ADR-0021 的
「代价」一节点过这条）。标签选择器意味着「给节点打个标签」这个看上去
人畜无害的动作会**悄悄重启一批服务**——而打标签的人多半不知道有个组正
按那个标签选成员。

代价照实写：加一台机器要显式 `config group move`，不能靠打标签自动归组。
在几百台的规模上这是真实的负担，但它换来的是「每一次重启都有一条对应的
操作记录」。

### 4.4.2 一个实例只属于一个组，重叠在**写入时**拒绝

模型上「每个 RoleInstance 属于且仅属于一个组」（ADR-0021）。落到实现有
两种守法：写入时拒绝重叠，或读取时按某种优先级挑一个。

**决定：写入时拒绝。** 读取时挑选意味着「这台机器到底用哪个组的配置」
取决于一条没人记得的优先级规则，而症状是「我明明改了 A 组，那台机器没变」。

因此 `config group create` / `move` 发现节点已属于本角色下的另一个组时
**直接拒绝并说清它在哪个组**，让用户显式 `move`。

### 4.4.3 建组不动 ordinal

[ADR-0028](../adr/0028-stable-ordinals.md)：ordinal 一次分配后固化，
永不重算。建组、改成员、删组**都不重新分配 ordinal**——它是实例的身份
（ZooKeeper 的 myid、Kafka 的 node.id），跟着分组走会让一次「把两台机器
归到一个组」变成一次集群身份错乱。

组只影响**取值**，不影响身份。这条要写进代码注释，因为「顺手按组重排一下
ordinal 让它们连号」是一个看起来很合理的改动。

### 4.4.4 删组是一次真实变更，不是清理

删组之后成员回落到角色级取值。**那是一次真实的配置变更**：这些机器上的
配置文件会变、digest 会变、声明了 `restartRequired` 的参数会重启服务。

因此 `config group remove` 与 `config set` 走同一套：先 dryRun 算出影响面
与 restart/reload 结论，再确认。把它做成一个「清理」动作（无提示直接删）
是最危险的形态——用户以为在整理组织结构，实际在重启生产服务。

### 4.4.5 `config set --node n7` 自动建组

ADR-0021 用它抵消「强制建组」的摩擦：用户的操作步数与无名覆盖完全相同，
但结果是具名、可枚举、可 diff 的。

组名 `node-<节点名>`。**要提示**，不能静默：

```
已创建配置组 node-n7（成员：n7）
  这是一个只含一台机器的组。若还有别的机器要用同样的配置，
  用 mechctl config group move <节点> --to node-n7 把它们并进来。
```

ADR 的「代价」一节点名了这条的后果：**一个 200 节点集群若被逐台微调，
会出现 200 个 `node-*` 组**。这在模型上是正确的（差异确实存在），
对策是 UI 要能折叠展示——「合并同配置的组」那条辅助命令仍然不在这一步，
它需要真实的多组使用经验才知道该怎么合。

### 4.4.6 `paths` 绑定按卷名，卷不存在时**拒绝**

`store.ConfigGroup` 加一个 `Paths map[string][]string`（路径名 → 卷名列表），
`pathBindingsFor` 从桩变成真实实现。求值代码（`render/paths.go` 的
`resolveOnePath`）**已经写好了**，包括「节点没声明该卷」时的报错。

要补的判断在写入侧：建组时就校验每个成员节点都声明了被绑定的卷。
留到渲染时才报错的话，症状是「组建好了，下一次调和整个组失败」——
而那时用户已经离开了建组的上下文。

### 4.4.7 前端引入 vitest

第 6 步留下的缺口（§6.7 末尾）在这一步补上。ConfigGroup 让前端的状态
更复杂了：组的选择、成员编辑、「改的是哪一层」的判断——这些逻辑错了
会让用户改错机器，而那是 ADR-0021 想要消除的正是同一类问题。

范围限定在**纯逻辑与组件行为**，不做端到端（那是容器套件的活）。

## 4.5 第 8 步：SSE 推的是**状态快照**，不是事件流

[§2.5](#25-实时性) 定了用 SSE。开工前要定的是**推什么**，而这个问题只有
一个答案与这个项目的核心纪律一致。

### 4.5.1 推快照，不推增量

「SSE」听起来天然是事件流：发生什么推什么。但这个项目从 M4 起就在守
一条纪律——**状态可以重复确认，事件丢一次就永远丢了**
（[20-continuous-reconcile](20-continuous-reconcile.md)）。

推增量的代价具体是这样的：

| | 推增量 | 推快照 |
|---|---|---|
| 客户端漏掉一条 | **永远错下去**，除非重放 | 下一条就修正了 |
| 断线重连 | 要 `Last-Event-ID` + 服务端保留历史 + 客户端游标 | **重连本身就是修复** |
| 客户端逻辑 | 按类型套用 patch | `data = 收到的` |
| 每条消息 | 小 | 一个 rollout 快照几百字节 |

**决定：每条消息带完整的当前状态。** 一个正确的重放协议比多传几百字节
贵得多——而它贵在哪里，要到某次漏推之后才看得见。

这条同时把验收表第 15 条（「SSE 断开 → 自动重连；重连后状态正确」）
变成了**不需要专门实现的性质**：浏览器的 `EventSource` 自带重连，
而重连后的第一条推送就是完整状态。

### 4.5.2 事件只用来「催一下」，不承载内容

服务端不能每 2 秒无条件重算一次快照——`Status()` 会跑一遍完整的解析
管线，一个几十实例的组件上那不便宜。

因此做成两层：

```
mechlet 上报 / rollout 推进  ──bump──>  Hub  ──唤醒──>  SSE 循环
                                                        ↓
                                              算一次快照，与上次比
                                                        ↓
                                                  变了才推
```

**bump 丢了也不要紧**：SSE 循环有一个兜底的定时唤醒（5s）。它慢一点，
但不会停在错误的状态上——这正是「事件只是提示，状态才是真相」的形态。

> 反过来做（bump 里带上变化内容、SSE 直接转发）会让 bump 变成不能丢的
> 东西，于是要给它加缓冲、加重试、加背压。那是把一条纪律换成一堆机制。

### 4.5.3 只给组件详情页开流，列表页继续轮询

验收表第 14 条说的是「Rollout 进行中，第 N/M 批自动更新」。那是秒级变化
的东西，值得一条流。

组件列表、节点列表不是：它们分钟级变化，轮询（5s）足够，而每个页面一条
SSE 意味着 mechd 要维护 N 条长连接与 N 份快照计算。

**范围：`GET /api/v1/components/{name}/watch`**，推该组件的 status + rollout。

### 4.5.4 认证只能靠 cookie

`EventSource` **不能设请求头**——这是浏览器 API 的硬限制，不是我们的选择。
因此 SSE 只对 session cookie 认证的浏览器可用；拿 Bearer token 的 CLI
用不了它，那是对的（CLI 有 `rollout status`，它要的是一次性答案）。

现有的 guard 对 GET 不要求 CSRF 头（[§6.4](#64-第-3-步落地时定的五件事)），
因此不需要为 SSE 开任何口子。**这一点要写下来**：将来若有人把 CSRF 检查
从「写操作」放宽成「所有请求」，SSE 会当场断掉而原因难查。

### 4.5.5 心跳与超时

两件事必须做，否则连接会在看起来正常的情况下悄悄断掉：

- **定期发注释行**（`: ping`，15s）。反向代理与负载均衡普遍在 30–60 秒
  空闲后关连接，而一个没有 rollout 在跑的组件可能几十分钟没有推送
- **`http.Server.WriteTimeout` 对 SSE 是致命的**。mechd 的 HTTP server 现在
  只设了 `ReadHeaderTimeout`，因此没问题——但这是巧合而不是设计，
  要在代码里写清楚，免得有人「顺手补个 WriteTimeout」

### 4.5.6 前端：SSE 接上就停轮询，断了就退回去

`usePolled` 已经有 `stop()` / `start()`（第 6 步为「有未保存改动」加的）。
`useLive` 在它之上：SSE 一收到第一条消息就 `stop()` 轮询，`onerror` 时
`start()` 回去。

**轮询代码不删。** 验收表第 15 条明写了「退化到轮询也算通过」——那不是
妥协，是让实时性成为一个**优化**而不是一个依赖。任何一天 SSE 被反向代理
吃掉，界面仍然是对的，只是慢一点。

## 4.6 第 9 步：加入引导与 token 管理

后端在 M7 就齐了：token 存哈希、明文只在创建时回一次、`JoinCommand`
里带着 CA 公钥指纹。第 9 步基本是 UI，但有四件事要先定。

### 4.6.1 主机名由**浏览器**填，不由服务端填

服务端生成的命令里是一个占位符：

```
mechlet install --join https://<mechd-host>:8443 --token … --ca-hash …
```

那不是「可复制的完整命令」（验收表第 18 条要的正是这个）。

**为什么服务端填不了**：mechd 绑 `0.0.0.0`，它不知道自己对外是什么地址。
`Host` 头能拿到，但那是客户端可以随便写的东西——把它拼进一条要在别的
机器上执行的命令里，等于让请求方决定新节点去连谁。

**浏览器知道**：它此刻正连着那个地址。因此 UI 用 `window.location.host`
替换占位符，服务端那份保持原样（CLI 用户看到占位符是对的——他敲命令的
那台机器与 mechd 的关系，只有他知道）。

> 代价：如果用户通过一个只有他能访问的地址（SSH 隧道、`localhost`）打开
> UI，生成的命令会带上那个地址而新节点连不上。因此命令旁边要写一句
> 「确认这个地址是**新节点**能访问到的」。

### 4.6.2 明文 token 只显示这一次

存的是哈希，创建响应之后再也拿不到明文。UI 上的表现必须与这个事实一致：

- 创建成功后弹一个对话框，里面是完整命令
- **关掉就没了**——对话框上明写这一点，并给复制按钮
- 列表页显示 token 的元数据（绑定的节点名、有效期、用了几次、可用与否），
  **永远不显示明文**

一个「重新查看 token」的按钮会让人以为它存着——那要么是假的，要么意味着
明文落库了。两者都不能有。

### 4.6.3 不代执行 SSH（[§2.4](#24-ui-的范围只读还是可写) 的那条例外）

再说一遍是因为它容易被当成缺失的功能：UI 上没有「帮我装到那台机器上」
的按钮，是**刻意的**。点一下就让 mechd 去 SSH，mechd 就得持有能登录所有
节点的私钥——而 M7 的一条主要收益正是「长期暴露面从 SSH 常开降为零入站
端口」（[08-security §3.6](08-security.md)）。

`mechctl node bootstrap ssh://…` 仍然可用：它是从**敲命令的那台机器**
发起的，私钥在运维手上。

### 4.6.4 节点动作的确认分档，与 CLI 对齐

| 动作 | CLI | UI |
|---|---|---|
| cordon / uncordon | 无确认 | 无确认——它可逆，且 `node list` 上看得见 |
| revoke | 一档 y/N | 确认弹窗，并说明「握手仍会成功，但 RPC 全被拒」 |
| remove | **二档**（输入节点名） | 输入节点名才能点确定 |
| token revoke | 一档 | 确认弹窗 |

`remove` 是二档的理由要写进界面：**它不会去那台机器上卸载任何东西**。
删掉一个还跑着组件的节点，那些组件会从中心的视图里消失而仍在机器上跑
——那是最难清理的一类状态。

## 4.7 第 10 步：`.mpack` 这个格式此前一行实现都没有

开工前查出来的：[§2.7](#27-pack-上传唯一一处新增的供应链入口) 写的是
「只接受 `.mpack`」，而全仓库搜 `mpack` 只有一处——`mechpack init` 生成的
`.gitignore` 里那行 `*.mpack`。

规范把它定得很清楚（[pack-v1 §3](../spec/pack-v1.md)）：

```
<name>-<version>-<revision>.mpack     # tar + zstd
归档要求：条目按路径排序、时间戳归零、uid/gid 归零、
         不含符号链接、不含绝对路径与 ..
```

`mechpack bundle` / `push` 在 [03-pack §2](03-pack.md) 与规范里都写了，
代码里没有；`mechpack` 只有 `init` / `assemble` / `lint` / `inspect`。

**因此第 10 步是三件事，不是一件：**

| | |
|---|---|
| `internal/pack` 里 `.mpack` 的读写 | tar + zstd，四条可复现要求 |
| `mechpack bundle` | 从 assemble 出来的目录产出 `.mpack` |
| 上传接口 | 校验 → **通过才落盘** → 审计 |

### 4.7.1 压缩用 zstd，加一个纯 Go 依赖

规范写的是 zstd，标准库没有。选 `klauspost/compress`：纯 Go、无 cgo、
Apache-2.0。

**为什么不退回 gzip**：`.mpack` 存在的唯一理由是**离线交付**——一个带
JDK 的包靠 U 盘搬。zstd 对二进制载荷的压缩率与解压速度都明显好于 gzip，
而 Pack 里装的正是二进制。为了省一个纯 Go 依赖去换那部分体积，方向反了。

代价照实写：这是 `go.mod` 里第一个非微型的第三方依赖（此前只有
cobra / yaml / sqlite / goose / grpc / crypto）。它没有 cgo，因此
`CGO_ENABLED=0` 的纯静态构建不受影响——那条约束才是真正不能破的。

### 4.7.2 可复现是**格式的一部分**，不是「顺便做一下」

规范那四条（排序、时间戳归零、uid/gid 归零、无符号链接与 `..`）不是
洁癖。它们各自挡一件事：

| 要求 | 挡的是什么 |
|---|---|
| 条目按路径排序 | 同一份内容打两次得到不同的字节流，于是**摘要对不上**，而摘要是这个系统里一切信任的锚 |
| 时间戳 / uid/gid 归零 | 同上，且顺带避免把打包机器的用户信息带进交付物 |
| 无符号链接 | 解包时软链可以指向归档之外——那是最经典的一类解包逃逸 |
| 无绝对路径与 `..` | 同上，且更直接 |

**后两条在解包侧也要再查一遍。** 打包时校验只能保证「我们打的包是干净
的」，而上传上来的包是别人打的——[§2.7](#27-pack-上传唯一一处新增的供应链入口)
说得很清楚，那是**唯一一处新增的供应链入口**。

### 4.7.3 先校验后落盘，且校验在**临时目录**里做

上传的处理顺序：

```
① 收进临时目录（不是 Pack 集合）
② 解包，逐条查路径（绝对路径 / .. / 符号链接一律拒）
③ 跑一遍完整 lint（与 mechpack lint --strict 同一份实现）
④ 全过了才原子移进 Pack 集合
⑤ 进审计：谁传的、摘要是多少
```

§2.7 已经定了「先校验后落盘」，这里补的是**在哪里校验**：解到 Pack 集合
里再查，那一瞬间放置阶段就可能看见它。临时目录 + 原子改名让「半个 Pack」
这个状态不存在。

### 4.7.4 验收要用一个**真包**，而不是构造的字节流

一个精心构造的畸形 tar 能验「拒绝路径逃逸」，但验不了「合法的包能装进去
并部署起来」。后者才是验收表第 17 条。

真包这件事工具链本来就支持：`mechpack assemble` 会按 `sources` 算真
sha256，而多节点验收里的 `stageWebappBlob` 已经在造真 blob（宿主侧
`go build` 一个 webapp → tar.gz → 算摘要）。把两者接起来即可。

**这与「示例包是格式验证物」不矛盾**：`examples/packs/` 里那些的 sha256
是占位符，它们是给人看格式的。验收要的是一个能装的包，那要自己造。

## 4.8 第 11 步：整张表要做成**可重复的套件**

最容易走偏的做法：写一个脚本，把 25 条挨个跑一遍，贴一份输出，标记完成。
那份输出在两周之后什么也证明不了——它记录的是「那一次跑过」，而不是
「现在还成立」。

**决定：做成 `test/webui` 这个宿主侧驱动的 Go 套件**，与 `test/multinode`
同一形态（驱动跑在宿主，被测系统完整跑在容器里）。每一条判据是一个
子测试，名字里带表格行号。

### 4.8.1 三类判据，要分清并各自说清楚

| 类 | 怎么验 | 表中的行 |
|---|---|---|
| **A 在真集群上验** | 套件直接打 mechd | 1b、2、3b、4、5、6、7、8–14、16–18、20–22 |
| **B 只有浏览器能验** | 不假装能验，指明由哪些单元测试覆盖 | 1（页面渲染）、3（滑块拖动）、15（EventSource 重连） |
| **C 构建期判据** | 在干净目录里编译 | 19 |

**B 类不能糊弄过去。** 一条写着「✓」而实际没验的判据，比一条明确写着
「靠 X 与 Y 推出来」的更糟——后者至少让人知道该补什么。

### 4.8.2 几条判据的「怎么验」需要单独定

**第 5 条「`document.cookie` 读不到它」**：没有浏览器就验不了那句话本身。
但它是 `HttpOnly` 的**后果**，而那个属性在线路上看得见。因此验的是
`Set-Cookie` 里有 `HttpOnly`——**机制成立则后果成立**。

**第 6 条「跨站发起写请求被拒」**：跨站请求的定义性特征是**带不上自定义
头**（浏览器不允许，除非 CORS 预检放行，而我们不放行任何跨源）。因此
一个不带 `X-Mecharion-Request` 的写请求，就是跨站请求在服务端的样子。

**第 22 条「以 `Content-Encoding: gzip` 直出」**：Go 的 `http.Transport`
会自动加 `Accept-Encoding: gzip`、自动解压、**并把响应头里的
`Content-Encoding` 抹掉**。用它验这一条会永远看不到那个头——
必须显式关掉透明压缩（`DisableCompression`）自己发 `Accept-Encoding`。

这是「**判据要落在真正会变的那个东西上**」的又一例：断言「拿到了正确的
内容」在压缩没生效时照样成立。

**第 19–21 条**是构建期的，不需要集群：在一个 `dist/` 只有 `.gitkeep` 的
目录里 `go build`，再看那个二进制的 `/` 回的是不是说明页（而不是 404）。

### 4.8.3 这一步允许「发现问题就地修」，但要记下来

前十步都发现过真实问题（`node list` 的假在线、`.mpack` 没实现、
载荷没入库……）。第 11 步大概率也会。发现了就修，但**每一处都要在
§6.12 里留一行**——一个「跑一遍全绿」的里程碑收尾，如果中途改过代码
却没记，下一个人会以为它一直是绿的。

| 17 | 上传合法 Pack | 进入 Pack 集合，审计留痕 |
| 18 | 节点加入页 | 给出可复制的完整 `node bootstrap` 命令（含 token 与 CA 指纹） |
| 19 | 干净 clone + `go build ./...`（无 node） | **编译得过**（`all:` 前缀让空目录也能 embed） |
| 20 | 上一条产出的 mechd 打开浏览器 | 给出「UI 尚未构建，执行 `make webui`」的说明页，**不是 404** |
| 21 | `make webui` 之后 | 浏览器打开是真正的界面 |
| 22 | 静态资源 | 以 `Content-Encoding: gzip` 直出（embed 前已预压缩） |

第 5、6 条是安全底线；第 9–12 条是这个里程碑的**核心价值**——少了它们，
这就只是一个「能填表的 JSON 编辑器」。

| # | 内容 | 可验证的成果 | 状态 |
|---|---|---|:--:|

| 7 | **ConfigGroup 全链路**：`mechctl config` 动词族 + API + UI + `paths` 多盘绑定 | 12 盘机器那个原始场景真的能配出来 | ✅ |

**第 1 步先行**：`go:embed` 与「没有 node 也能构建」这条约束要最先立住。
反过来做的话，等 UI 写了一半才发现构建链把离线构建破坏了，改起来要动
CI、Makefile 与所有贡献者的工作流。

**第 3 步在第 4 步之前**：先让登录成立，再谈里面有什么。反过来会先写出一个
「谁都能看」的中间状态，而那种中间状态很容易被默认带到最后。

**第 5 步是这个里程碑的核心**，前四步都是为它铺路。若时间只够做到第 5 步，
M8 仍然交付了它的主要价值。

**第 7 步是第 6 步做完之后插进来的**，原因见 [22-multi-node §6.13](22-multi-node.md)
同一类：ConfigGroup 的表、解析链、渲染路径**全都在**，唯独没有任何创建入口
——`ConfigGroups().Upsert` 在生产代码里一次都没被调过，`mechctl config` 整个
动词族一行代码没有，`pathBindingsFor` 是个 `return nil` 的桩。于是第 5 步交付的
那个组选择器在真实集群上永远只有「角色级」一项。

**它没有塞进第 6 步**，因为 [§2.4](#24-ui-的范围只读还是可写) 那条纪律：
UI 不发明 CLI 没有的动作。`mechctl config` 现在整个不存在，先在 UI 里做出建组
等于把这条纪律反过来。因此第 7 步是**CLI 与 UI 一起补齐**，而不是「给 UI 加个
按钮」。

## 6.1 第 1 步落地时定的三件事

**① `//go:embed all:dist` 的 `all:` 少一个字，干净 clone 就编译不过。**
报错是 `cannot embed directory dist: contains no embeddable files`——完全看不出
与前端有关。变异验过：去掉 `all:` 之后确实编译失败。

**② 按需引入不是配上 resolver 就自动生效。**
第一版一边配了 `ElementPlusResolver`，一边又 `import 'element-plus/dist/index.css'`
并 `.use(ElementPlus)`——两者互相抵消，全量组件库照样进了产物。改掉之后：

| | 全量 | 按需 |
|---|---|---|
| JS | 1032 KB | **127 KB** |
| CSS | 360 KB | **17.6 KB** |
| 进二进制（预压缩后） | — | **52 KB** |

**③ 压缩放在 Go 这一侧，不用 npm 插件。**
`internal/tools/webuibuild` 走一遍 Vite 产物，可压缩的类型压成 `.gz`，
小于 1 KB 的与压完反而更大的保持原样。前端依赖树因此少一个插件——
五年后重写它时轻一点。

> 运行期的 handler 优先送 `.gz`；客户端不接受 gzip 时就地解压。
> 后者现实中几乎走不到，但少了它，一个 `Accept-Encoding: identity`
> 的客户端会拿到一坨二进制，而那种故障极难查。

### 6.2 一处升不上去的依赖：TypeScript 停在 6.x

前端依赖全部保持最新，**只有 TypeScript 例外**。

TypeScript 7 是原生重写版（Go 实现），不再导出 `typescript/lib/tsc`，而
`vue-tsc` 靠 require 它来跑类型检查：

```
Error [ERR_PACKAGE_PATH_NOT_EXPORTED]:
  Package subpath './lib/tsc' is not defined by "exports" in typescript/package.json
```

**选择停在 TS 6.x，而不是绕过类型检查。** 把 `vue-tsc -b` 从 build 脚本里
去掉确实能用上 TS 7，但那等于**为了一个版本号放弃整条类型检查**——
而模板里的类型错误正是 Vue 项目最容易漏掉的一类。

`package.json` 里就地写了原因，等 `vue-tsc` 跟上再升。

## 6.3 第 2 步落地时定的四件事

**① 口令没有 `--password` 选项，永远不会有。**
命令行会进 shell 历史，也出现在同机任何用户的 `ps` 输出里。给两条路：
交互式（不回显、输两遍）与 `--password-file`。**非交互且没给文件时直接拒绝**，
不从 stdin 裸读——那会把调用者推向 `echo pw | mechctl …`，而那条命令本身
就进了历史。

**② argon2 的代价参数写进编码串，不写在代码里。**

```
$argon2id$v=19$m=65536,t=3,p=4$<盐>$<摘要>
```

因此将来调强参数**不需要数据迁移**：老口令用它们当初的参数验，
下次改口令时自然升到新的。`Authenticate` 里顺手做了这件事——验证成功那一刻
是唯一能拿到明文的时刻。

**③ 口令只管长度，不管「必须含大小写数字符号」。**
那类规则被反复证明会把人推向 `Passw0rd!` 这种可预测模式。下限取 12 个字符。

**④ 允许删掉最后一个用户。**
它可恢复——CLI 走 admin token 而不是用户，删光之后仍能在服务器上重建。
一条「不许删最后一个」的规则会在真的需要清空时挡住人。要人点头的那一步
放在 CLI 的确认里，不放在服务端。

> **一个容易被忽视的盲区**：把摘要比较改成「只比第一个字节」，
> 当时所有测试**一条都没红**——因为随机的错误口令几乎总在第一个字节就
> 不同（1/256 才碰撞）。而那个改动把强度从 2^256 砍到了 2^8。
>
> 判据因此不能是「错口令被拒」，得是「**摘要的任何一位被改动都会被发现**」。
> 补的测试直接翻转摘要的首、中、尾三位。

## 6.4 第 3 步落地时定的五件事

**① 挑战放内存，会话落库。** 两者取舍不同，因为「丢失的代价」差着量级：

| | 丢了会怎样 | 存哪 |
|---|---|---|
| 挑战 | 用户重来一次，多点一下 | 内存，TTL 三分钟 |
| 会话 | **所有人被登出**，而重启是常规操作 | SQLite |

**② PoW 的目标摘要必须下发。** 它就是题面本身——不给的话客户端无从判断
算对没算对。下发不削弱什么：服务端仍要自己重算核对，攻击者省下的只是
「知道答案长什么样」，那本来就不是秘密。

**③ 无论对错都先核销。** 只在成功时核销的话，攻击者可以拿同一道题反复试
滑块位置——**一次 PoW 的成本被摊到几十次尝试上**。核销那一行因此放在任何
判定之前。

**④ CSRF 做两道，不押在一道上。**

| 道 | 靠什么 | 单独失效时 |
|---|---|---|
| `SameSite=Strict` | 浏览器跨站不带 cookie | 老浏览器/不遵守的客户端就没了 |
| 自定义头 `X-Mecharion-Request` | 浏览器跨源发不出自定义头 | 需要配合 CORS 放行才失效 |

**Bearer token 那条路不受 CSRF 头约束**：它不是浏览器发的，不存在跨站问题。
两条认证路径在 `guard` **一处收口**——散开的话，「某个接口忘了检查会话」
就是一个洞。

**⑤ 改口令要清掉全部会话。** 不清的话，一个已经被偷走的会话在改完口令
之后仍然有效——而改口令的动机通常正是「怀疑被偷了」。

> **测试用桩而不是真谜题**：`API.Challenges` 是接口。谜题本身（Argon2、
> 一次性、容差、过期）在 `authn` 包里验透了，HTTP 层要验的是「登录有没有
> 真的去问它」。这样还避免了在 `authn` 上开一个「能解出答案」的导出方法
> ——那种方法一旦存在，迟早会有人把它接到别处。

## 6.5 第 4 步落地时定的四件事

**① 只读视图暴露了一个后端缺陷，而它一直都在。**

三节点集群接上界面之后，节点页三台全绿，其中两台的 mechlet 早就不在了。
根因在 mechd：`nodes.status` 只有写 `online` 的路径，没有人写回去
（[22-multi-node §6.13](22-multi-node.md)）。CLI 的 `node list` 一直在说
同样的假话，只是在一行文本里它混在别的字段中间，没人盯着看。

结论值得记下来：**「换个前端」不产生新缺陷，它只是换了个照明角度。**
第 4 步因此不只是写页面——修那个缺陷（存储列退回只答「出现过没有」、
在线与否由长连接在读的那一刻算、gRPC keepalive 兜住断电）才是这一步
真正的产出。

**② 收敛那一列必须是三个值，不是两个。**

`converged=false` 底下压着两种完全不同的处境：**在排队等下一批**，和
**出了问题**。前者要等，后者要人去看。二值化之后运维得自己去比对
`pendingVersion`——而那个字段的存在理由（[22-multi-node §6.8](22-multi-node.md)）
正是要免掉这次比对。

同一条理由在节点页出现两次：`cordoned` 与 `revoked` **各占一列**，不并进
状态（一台机器可以既在线又被暂停调和）；节点状态**三个值**，不是二值。
每一次「并成一列更清爽」都在丢一条运维要用的信息。

**③ 重启次数要单独显示。**

一个每分钟崩一次又被拉起的服务，在「running / healthy」两列里与健康的
一模一样。这与 M7 把「重启计数没有增加」加进健康门禁
（[22-multi-node §2.5](22-multi-node.md)）是同一条理由的展示版——
数据早就在上报里，缺的只是把它摆出来。

**④ 漂移与它的策略写在一起。**

看到一条漂移，第一个问题是「它会不会被改回去」，而答案在 `driftPolicy`
（含站点覆盖）里。分成两块展示等于要求看的人自己去查另一处——
那正是这个界面想省掉的动作。

> 轮询而不是 SSE 是**第 4 步的做法**，第 7 步换成 SSE。轮询代码留作
> 兜底：验收表第 15 条明写了「退化到轮询也算通过」。

**验收怎么做的**：节点镜像里没有 curl / wget / python（[22-multi-node
§6.1](22-multi-node.md) 说明了为什么不给被测机器装工具），集群端口也不对
宿主发布。于是加了 `test/uiprobe` 夹具——走完整条 HTTPS 取页面，判的是
「回来的是不是那个页面」。已有的 `tlsprobe` 判不了这个：它只做握手，
答的是「连接接不接受」。

## 6.6 第 5 步落地时定的四件事

**① 「角色级」这一层在 mechd 的存储里不存在。**

§4.1 的模型图画着 `Component → Role → ConfigGroup` 三层覆盖，`render.Overrides`
也确实有 `Role` 这个字段。但 `overridesFrom` 从来没填过它——mechd 存的只有
`components.params`（组件级）与 `config_groups.params`（组级）两层。
`Overrides.Role` 只有 `mechctl render` 走本地 plan 文件时才会被填。

因此表单上「角色级」这个选项，实际显示的是**组件级**取值。这不是缺陷，
是模型比实现多了一层——但界面不能装作那一层存在。做法：不选组时标注
「当前是角色级取值，改这里会影响该角色的全部实例」，说的是**影响面**
（这句话是对的），不承诺它落在哪张表里。

真要把角色层做出来，得先回答「它与只含该角色全部成员的 ConfigGroup
有什么区别」——如果没有区别，那多一层就是纯负债。留到有真实需求时再定。

**② `roles[].params` 是角色专有声明，不是覆盖 default 的手段。**

第一版夹具把它当成「在角色层改掉顶层默认值」用，测试当场变红：类型、
min、max 全没了。查规范（[pack-v1 §7.5](../spec/pack-v1.md)）——
`roles[].params` 是**该角色专有**，只有 `profiles[].params` 才是
「覆盖上述两者的 `default`」。

`paramDecls` 的实现是对的（角色层整体替换、profile 层逐字段覆盖），
写错的是夹具。**这类「代码对、我的预期错」的红灯与真缺陷一样有价值**，
前提是去查规范而不是去改代码迁就自己。

> 顺带留一个口子：`roles[].params` 里写一个没有 `type` 的条目目前不报错，
> 它会悄悄把顶层声明替换成一个无类型的参数。lint 该拦这个，但那是
> `internal/pack` 的事，不在第 5 步。

**③ 单角色 Pack 可以省略 `name`，而表单第一版没认这件事。**

`pack.Role.EffectiveName()` 在 `name` 为空时返回 `default`，`RoleByName`
用的正是它。第一版的 `roleNames` 直接读了 `r.Name`——角色下拉框里于是
是一个空字符串，而按空名字又查不到角色声明。

**单元测试没抓住它**：夹具 `paramkit` 老老实实写了 `name`。抓住它的是
拿真集群跑的那次检查——线上的 `go-webapp` 正是省略写法。

教训是关于夹具的：**照着规范的「推荐写法」造夹具，就会系统性地避开规范
允许的其它写法**。夹具越干净，它掩盖的形状越多。

**④ 表单的判据是「值从哪来」，不是「值是多少」。**

「值是多少」由渲染管线的测试守着。展示层要守的是另一件事：一个把三层
优先级写反的实现，在组与角色恰好设了同一个值时，**每一个值都是对的**。
因此 `TestSourceIsTheDeepestLayerThatSetIt` 让四个参数各只在一层被设过，
一次同时暴露三个错位。

同一条纪律在 secret 上的形态：判据不能是「Value 为空」——一个换成
`"********"` 的实现同样满足它，而它泄漏了长度。因此连 `Default` 一起查。

**验收怎么补的**：examples 里 10 个 Pack 合起来只覆盖 10 种参数类型，
`float` 与 `list<T>` 一次都没出现过。验收表第 8 条说的是「12 种」，
拿覆盖 10 种的样本验不出来。因此新增夹具
`internal/mechd/testdata/packs/paramkit`——它不是示例，是**判据的一部分**。

## 6.7 第 6 步落地时定的五件事

**① 改配置的入口牵出一个雷，见 §4.3 ①。** 结论落成了
`PATCH /components/{name}/params` 与 `mechctl config set`，两者不碰放置。

**② 预览就是确认，不是确认之前多点一次。**

界面上没有「保存」按钮直接生效这条路：点「预览」→ 服务端 dryRun 算出
影响面与 restart/reload 结论 → 摆在对话框里 → 才有「保存」。CLI 那条
`config set` 同样先干跑再问。

理由是 §4.3 ⑤ 那条的延伸：**一个只说「确定吗」的确认没有价值**。要问的
是「会发生什么」，而那句话前端算不出来——前端只知道每个参数的标志，
不知道这一次改动合起来会动到哪几台机器。

**③ 只有会重启 / reload 才拦一下。**

一次纯配置变更（`effect: none`）不弹二次确认。每次都拦会训练用户无脑
点确定，而下一次是真的要重启。回滚是例外，走**二档**（输入组件名）：
它把机器真的换回旧版本，一个 y/N 与它的影响面不相称。

**④ 有未保存改动时必须停掉轮询。**

表单页每 15 秒刷新一次。用户正在填的值会被下一次刷新换成服务端那份，
而症状是「输入框自己清空了」——没人会把它联想到轮询，只会当成界面有
bug。因此 `usePolled` 多了 `stop()` / `start()`，`dirty` 一为真就停。

同一条的另一半：提交的 body 里**只放动过的参数**。服务端是 PATCH（只
合并提到的），前端若送全量，「别人刚改过的另一个参数」会被这次保存
悄悄冲回旧值。

**⑤ 「恢复默认」与「改成空」是两个动作。**

一个参数的合法取值可以**就是**空串。界面上因此是一个单独的按钮，请求里
走 `unset` 而不是 `set: null`。这个按钮只对**被覆盖过的**参数出现——
对一个本来就取 Pack 默认值的参数显示它，点下去什么也不会发生。

### 已知缺口：前端没有测试，只有类型检查

`webui/` 里没有 vitest 之类的测试框架，`npm run build` 跑的是
`vue-tsc -b` + Vite 构建。也就是说**前端逻辑只有类型这一道把关**。

到第 6 步为止，前端已经承载了三处「错了会毁掉用户输入」的逻辑：

| 逻辑 | 错了会怎样 |
|---|---|
| `edits` 只装动过的参数 | 送全量 → 悄悄冲掉别人刚改的另一个参数 |
| `dirty` 时停轮询 | 不停 → 用户正在填的值被刷掉，看起来像输入框自己清空 |
| `unset` 与空值分开 | 合并 → 「清空一个参数」变成「恢复默认」，反之亦然 |

这三条现在靠**真集群上手动走一遍**验证，那不是可重复的判据。补一套
前端测试是独立的一件事，不塞进第 6 步——但它是一个真实的缺口，
不是「暂时不需要」。

## 6.8 第 7 步落地时定的五件事

**① 一个反直觉但正确的事实：路径绑定会波及同角色的其它实例。**

给 n1 绑两块盘之后，n2 的 digest 也变了。第一版测试断言「只有 n1 变」，
当场变红。

原因在 `topology`：**每个实例的规格里都带着同角色全部实例的路径**，
因为模板要能 `range .Topology.Roles.<role>` 去引用同伴（HDFS 的 namenode
列表、Kafka 的 broker 端点都靠它）。

因此要写清楚：**「只改这一台」在路径上不成立。** 改一台机器的多盘绑定会
让同角色其余实例重新物化。参数覆盖没有这个问题（它不进拓扑）。两者的
影响面不同，界面与文档都不该把它们说成一回事。

`TestPathBindingRipplesThroughTopology` 把这条钉住了——将来谁想「精简一下
topology，把 paths 去掉」会立刻看到自己在破坏什么。

**② 重叠成员在写入时拒绝，界面上直接禁掉。**

服务端拒绝重叠（§4.4.2），但让用户填完再被拒是很差的体验。组编辑器把
已属于别的组的节点**禁用并注明它在哪个组**——用的正是服务端错误里那句话。
两处说同一件事，用户不会先看到一个能勾的复选框、再看到一句「不行」。

**③ 建组面板只管成员，参数改动走参数表单。**

一个「调整成员」的操作不该顺手改配置。要改组里的参数，在表单顶部选中
那个组即可——那时来源列会显示「本组覆盖」，影响面那行会列出成员机器名。

**④ 删组的对话框要先干跑。**

与 `config set` 同一条：确认要问的是「会发生什么」。删组的措辞尤其要紧，
因为它长得像清理——面板上写明「这不是清理，是一次真实的配置变更」，
并把受影响的实例逐条列出来。

**⑤ 前端测试落地：先重构，再测。**

三条「错了会毁掉用户输入」的规则原本埋在 `ComponentParams.vue` 里，
测它们要么挂载整个组件，要么把逻辑抽出来。选了后者——
`src/lib/useParamEdits.ts` 是**可测性驱动的重构**，顺带让那三条规则
有了一个说得出名字的位置。

补的测试覆盖三类真实错误：撤销修改时留下 `undefined` 键、`body()`
返回内部引用、设值时不清 `unset`。

> `vite.config.ts` 的 `defineConfig` 要从 `vitest/config` 取，不是 `vite`
> ——后者的 `UserConfig` 里没有 `test` 字段，`vue-tsc` 会当场报 TS2769。

## 6.9 第 8 步落地时定的三件事

**① 重算要有一个与集群规模无关的上限。**

设计里只写了「bump 唤醒 + 5 秒兜底」。拿真集群一跑就看出漏了一层：
`Report` 里**每个实例**都会 bump 一次，而 `reportedAt` 每次上报都变
——于是状态"确实变了"，快照也确实该推。

问题在代价：一个 50 实例的组件、15 秒上报一次，就是**每秒 3 次完整的
解析管线重算**，而每个开着的浏览器各算一份。

Hub 的容量-1 通道只在消费者**慢**时合并；缺的是消费者快时的那一半。
补法是把重算改成固定节拍驱动（`watchMin = 1s`），bump 只把 `dirty`
立起来。代价是界面最多晚 1 秒——对一个人眼在看的页面那不可感知。

对照：拿掉这层节流之后，同一条测试里 3 秒推了 **262** 条（限额 6）——这正是这层节流要防的量级。

**② 流的节拍用真实时钟，不用 `s.now()`。**

`Service.now` 是可替换的，供 rollout 门禁的测试固定时间。SSE 循环里
混用它会让一个冻住时钟的测试把「每秒至多一次」变成「每秒一次」——
两者的区别要到并发压力下才看得见。

判据：**这是 HTTP 流的节拍，不是领域时间。**

**③ `WriteTimeout` 对 SSE 是致命的，而它现在不设是巧合。**

mechd 的 `http.Server` 只设了 `ReadHeaderTimeout`，因此 SSE 能活。
但那是历史巧合而非设计——一个「顺手补齐超时配置」的改动会让页面
在一个整数秒之后停止更新，而那种现场极难联想到 server 配置。

已经在 `serve.go` 那一处写清楚为什么不设，以及慢客户端由什么防护。

```
[  0.0s] 快照 #1  state=succeeded batch=3 batches=3
[  5.0s] 快照 #2  state=running   batches=2
```

## 6.10 第 9 步落地时定的两件事

**① 验收判据是「这条命令真的能把节点加进来」，不是「页面渲染出来了」。**

一条粘过去不工作的命令比没有命令更糟——它看起来完全正常，失败发生在
另一台机器上，而用户会先怀疑自己敲错了。

因此这一步的验收是在三节点集群上**真的走一遍**：把 n2 擦回「还没加入」，
用界面生成的那条命令（含前端替换过的主机名）在 n2 上执行，确认它出现在
`node list` 里并变成 online。

**② 主机名替换是前端唯一「加工」凭据的地方，因此它有自己的测试。**

`fillJoinHost` 的判据里有一条是「token 与 CA 指纹一个字节都不动」——
它们是凭据与信任锚，任何"顺手规范化一下"的处理都可能毁掉它们，而症状
（「token 无效」/「指纹不匹配」）指向的是别处。

配套的 `isLocalOrigin`：用户可能通过 SSH 隧道或 `localhost` 打开 UI，
那时生成的命令带的是新节点连不上的地址。界面要多说一句——这是
[§4.6.1](#461-主机名由浏览器填不由服务端填) 里记下的那个代价。

| token 存哈希，明文只在创建响应里回一次 | `CreateJoinToken` |
| `JoinCommand` 带 CA 公钥指纹 | 同上 |
| 三种失效分开说（过期 / 用尽 / 已吊销） | `JoinTokenView.Reason` |

## 6.11 第 10 步落地时定的四件事

**① 上传必须做「载荷入库」——少了它，包能部署但永远不收敛。**

thick pack 里带着 `blobs/sha256-<hex>`，而节点是按 sha256 向 mechd 的
载荷库要的（`Backend.OpenBlob` 读 `<BlobDir>/sha256/<xx>/<hex>`）。
两处布局不同。第一版的上传只把目录搬进 Pack 集合，**没有搬载荷**。

症状极其难查：`deploy` 成功、`component list` 里有它、没有任何地方报错，
只是那个实例「装上了、一直不收敛」。而 deploy 那一步是对的——规格渲染
得出来，问题在下发之后。

这正是 03-pack §2 里 `mechpack push`（thick → thin，blob 入库）那一半。
**上传 = bundle 的逆运算，两半都要做。**

单元测试为什么没抓到：那个最小 Pack 根本没有载荷。**夹具越干净，
它掩盖的形状越多**——与第 5 步 `go-webapp` 省略角色名那次是同一条。

**② 载荷入库时要重算摘要核对。**

文件名里的 sha256 是**归档自己声称的**。名不副实的载荷进了库，之后
每一次按摘要取都会拿到错的东西——而那时已经查不到是上传这一步引入的。

**③ 「不完整」与「不是这个格式」要分开报，且顺序要对。**

两者的下一步动作完全不同：前者重传一次，后者换个文件。

判断顺序反过来的话，一个传到一半的合法包会被报成「这不像一个 .mpack」
——用户会去检查文件对不对，而它本来就是对的。

而且**两条路径都要包**：小文件在 `tr.Next()` 上断，大文件在读条目内容的
`io.Copy` 上断。第一版只包了前者，于是真集群上传一个截断的 4.6 MB 包，
回的还是一句裸的 `unexpected EOF`。

**④ `isUserError` 加了类型判断，不再只靠措辞。**

一个传坏了的文件是**客户端**的问题，第一版却回 HTTP 500。根因是
`isUserError` 只匹配错误信息里的关键词，而「上传 Pack: unexpected EOF」
一个都不沾。

`faults.Error` 本来就带 `Class`，而上传路径上的错误都用 `Permanentf`
标过——把这个类型判断加在关键词之前即可。那正是那段注释里写着「用类型
标记更严谨」的东西，这次顺手补上一块。

> **只认显式打过标的**：`faults.ClassOf` 把未分类的错误也算成 Permanent
> （那对调和循环是对的），拿它当判据会让每一个内部错误都变成 400，
> 而那会掩盖真正的服务端故障。

### 真包这件事：`hack/realpack.sh`

三步，每一步都是真实工具链：

```
go build          → 真二进制（linux/amd64）
mechpack assemble → 按 sources 算**真** sha256，sources → blobs
mechpack bundle   → tar + zstd，可复现
```

产出一个 4.7 MB 的 `realapp-1.0.0-1.mpack`。第 10 步的验收用它走完
上传 → 载荷入库 → 部署 → **收敛** → systemd 单元起来。

造它的过程本身就验证了校验链是活的：lint 当场拦下夹具里的两个真错误
（`runtime` 没写、`log_level` 声明了 `reloadRequired` 却没有 `execReload`）。

> 这与「示例包是格式验证物」不矛盾：`examples/packs/` 里那些的 sha256
> 是占位符，它们是给人看格式的。**验收要的是一个能装的包，那要自己造。**

### 6.12.1 一条我自己写的假判据

第 6 条（跨站写请求被拒）第一版是**假的**：它送一个**无效**的会话
cookie，于是 401 来自身份校验，根本没走到 CSRF 那一步——把 `authapi.go` 里的头检查整个删掉，那条测试照样通过，证明了这一点。

修法不是把它改对，是**承认它验不了**：真正验第 6 条需要一个有效会话，
而拿到有效会话要先过滑块——滑块的正确位移只有服务端知道，测试客户端
解不开（除非在服务端开一个后门，而那种后门迟早会被接到别处）。

因此它挪进 B 类，指明由 `internal/mechd/authapi_test.go` 的
`TestWriteNeedsCSRFHeader` 覆盖——那里用真会话，且验了「**带上头就
放行**」那另一半。**那一半才是关键**：只验「不带头被拒」的话，一个
「所有写请求都拒」的实现同样通过。

留在 e2e 里的是一条更弱但真实的判据：无凭据的写请求被拒。

> 这是这个里程碑第三次遇到同一类问题（前两次：`previewSecrets` 的判据、
> keepalive 用 `docker network disconnect`）。规律很清楚：**一条测试通过
> 之后要问「把被测的那行删掉，它会不会还通过」**——不问就等于没测。

### 6.12.2 B 类：四条没有端到端验证

| 2（口令错误） | 到不了口令检查——要先过滑块 | `user_test.go` 的同一句 `ErrMismatch` + `internal/password` |
| 3（滑块） | 同上 | `internal/authn` 的 slider 测试 |
| 6（CSRF） | 需要有效会话 | `authapi_test.go` 的 `TestWriteNeedsCSRFHeader` |
| 15（重连） | 需要真浏览器 | `useLive.test.ts` + 本套件验了服务端发 `retry:` |

### 6.12.3 第 19–22 条早在第 1 步就有测试

写这一步时先加了一份 `internal/webui/embed_test.go`，随后发现

### 6.12.4 第 22 条要关掉透明压缩才验得了

Go 的 `http.Transport` 会自动加 `Accept-Encoding: gzip`、自动解压、
**并把 `Content-Encoding` 抹掉**。用默认客户端验这一条会永远看不到那个头，
而断言「拿到了正确的内容」在压缩没生效时照样成立。

必须 `DisableCompression: true` 并自己发那个头。变异验过：把
`webui.go` 里设 `Content-Encoding` 的那行删掉，这条测试变红。

### 6.12.5 限流那条必须放在文件最后

`TestZZ04` 会把测试来源 IP 锁 30 秒，而 `Test05` 要取一道挑战——被锁之后
那个接口也回 429。第一版把它放在前面，`Test05` 当场失败，而失败原因指向
「取挑战回了 429」，与限流这条判据毫无关系。

名字里的 `ZZ` 就是为这件事：Go 按**源码顺序**跑同一个文件里的测试，
而那个顺序是隐式的。
