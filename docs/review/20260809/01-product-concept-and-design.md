# 产品概念与整体设计审阅

## 1. 产品定位

Mecharion 试图填补的是一个真实空档：传统配置管理工具擅长执行与批量变更，却不长期持有应用级期望状态；专用集群管理器理解组件角色、配置组、升级与健康门禁，却通常绑定少数产品。Mecharion 用 Pack 把组件知识外置，用常驻 agent 保持期望状态，价值主张成立。

当前最清晰的一句话仍是：

> **用 Cloudera Manager 的模型深度，管理 Ansible 那样广泛的目标。**

“离线优先”不是营销附加词，而是贯穿 Pack、blob、安装、证书、运行时和示例的约束，构成了差异化。尤其适合内网数据中心、边缘门店、受控生产区和软件交付方管理自带依赖的场景。

### 1.1 产品价值的强项

- 从“执行任务”提升为“管理应用生命周期”，覆盖部署、配置、漂移、升级、回滚、运行态和移除。
- `Role` / `RoleInstance`、Profile、ConfigGroup、依赖导出和 Rollout 能表达中等复杂度的分布式组件，而不是只有单进程模板。
- 断开控制面后，节点继续按最后期望状态调和；控制面故障不会直接成为业务数据面故障。
- 同一 Pack 可用于单机和多节点，避免边缘版、中心版产生两套行为。
- 默认保留数据、缩容要求显式确认、危险删除先展示影响面，产品安全观较好。

### 1.2 需要收窄的产品叙事

项目同时使用了“当前实现”“首版目标”和“远期平台愿景”三种时态，却经常没有标签。例如总览描述数百节点、多团队和 Site 级 RBAC，实际决策则是单一全权 admin、单 SQLite 控制面且 v1 无 HA。这些选择本身合理，问题在于读者难以判断哪一项今天可用。

建议所有能力列表统一标记为：

- `Available`：代码、帮助、文档和验收一致；
- `Experimental`：已实现但接口可能变化；
- `Planned`：已决策但未实现；
- `Idea`：尚未决策。

首页只列 `Available` 与明确的主要限制。路线图和 ADR 再解释未来方向。

## 2. 核心理念评价

### 2.1 离线优先

评价：**优秀，是最有辨识度的产品原则。**

部署阶段不访问包管理器、Registry 或编译服务，使交付可审计、可复制，也降低边缘环境的不确定性。thin/thick Pack、内容寻址 blob 和 hermetic lint 构成了较完整的机制链。

当前缺口是供应链信任：设计明确把 Pack 签名视为唯一信任锚，实际只有格式与内容安全校验，没有发布者签名、可信密钥策略和验证闭环。未实现签名前，产品只能承诺“离线和内容完整性”，不能承诺“来源可信”。

### 2.2 声明式期望状态与命令式逃生舱

评价：**方向正确，入口尚未完全归一。**

`Deploy`、`SetParams`、`Upgrade`、`Rollback` 最终都推动期望状态并由 mechlet 调和，核心路径是统一的。`apply -f` 也复用部署流程，这是好设计。

但设计文档仍称顶层动作是 `apply/status/diff`，实际 CLI 已采用名词优先，`status`、`diff` 均在 `component` 下。原则应描述内部语义，不应绑死已经变化的命令布局。

### 2.3 显式优于隐式

评价：**实现中最稳定的一条原则。**

缩容需 `--allow-remove`、危险移除需确认名称、数据默认保留、secret 不通过普通参数和环境变量传递、依赖绑定固化，这些都直接减少了生产事故概率。

目前最大的反例恰好在底层边界：Component/Node 等名称未统一验证，用户输入可以改变文件路径和 API 可达性。上层确认再完善，也不能替代基础标识符约束。

### 2.4 现场可诊断

评价：**设计充分，产品闭环不足。**

JSON 状态、可读实例键、SQLite、明确 generation 和结构化错误都利于现场排障。但文档反复承诺的 `mechctl --local` 只读恢复入口并不存在，mechd 故障时用户缺少被设计为核心能力的诊断通路。

## 3. 对象模型

| 对象 | 评价 | 建议 |
|---|---|---|
| `Site` | 比 Cluster 更适合同时覆盖单机、边缘站点和数据中心，作为权限/命名顶层也合理 | 在 RBAC 未实现前不要称其为“现有权限边界” |
| `Pack` | 直观地表达可交付组件知识，但通用词导致搜索噪声 | 对外文档首次出现写作 “Mecharion Pack”；API 保留 `pack` |
| `Component` | 表达“一份 Pack 的一次部署”，比 Service 更少与 systemd/网络服务冲突 | 保留 |
| `Role` | 表达组件内职责清楚 | 保留，继续由 Pack lint 约束 DNS label |
| `RoleInstance` | 精确但偏内部；CLI/UI 没有直接要求用户理解它是正确的 | 继续作为领域内部名词，对用户简称“实例” |
| `ConfigGroup` | 比“override”更可解释，能表达配置形态 | UI 应更明确展示成员、继承来源和默认组 |
| `Generation` | 与不可变发布目录和回滚高度匹配 | 统一大小写和对外解释，避免与数据库 revision 混淆 |
| `Rollout` | 适合表达过程状态、批次与门禁，不应简化成一次 upgrade 结果 | 保留 |

对象之间的关系足够支持当前范围。暂时不应新增 Environment、Project、Tenant 等更高层对象；在真实多团队需求出现前，它们会增加空洞层级。

## 4. 单机与控制面概念冲突

这是当前最显著的产品叙事问题。

- ADR-0026、`docs/design/01-architecture.md:30` 和 decision log 明确修订为：单机也运行 mechd，mechd 不是可选，只是与 mechlet 同机。
- `README.md:79-84`、`cmd/mechd/main.go:1-24`、`cmd/mechlet/main.go:24` 和 `cmd/mechctl/main.go:3-22` 仍称 mechd 可选，并宣称 `--local` 可驱动完整单机能力。
- 实际代码没有 `--local` flag、客户端或 mechlet 本地管理 API。
- 新 ADR 中的 `--local` 已退化为 mechd 故障时只读诊断，但这一能力同样尚未实现。

因此应采用 ADR-0026 的模型作为唯一事实：

> 单机部署是 mechd + mechlet 同机；mechlet 在控制面中断时继续执行已有期望状态，但新的管理操作依赖 mechd。`--local` 若保留，仅是未来只读恢复接口。

在实现只读接口前，从 README 和二进制帮助删除 `--local` 及“mechd 可选”的当前能力描述；ADR 中可保留历史修订。

## 5. 产品完成度与非目标

### 5.1 已形成闭环的能力

- Pack 解析、lint、组装和 bundle；
- systemd / Docker / Compose 运行时抽象；
- 单机/多节点期望状态下发；
- 配置参数、ConfigGroup、secret 存储和节点侧注入；
- 状态、漂移、运行态、升级、回滚、Rollout；
- Node 加入、mTLS、cordon、吊销；
- Web UI 的部署、配置、节点、加入、孤儿和实时状态主要流程；
- 移除、孤儿清理、声明式 apply 和临时命令通道。

### 5.2 仍应明确列为非当前能力

- 多用户、RBAC、SSO、多团队隔离；
- 控制面 HA；
- Pack 发布者签名与可信仓库；
- 稳定、公开的 HTTP API/SDK；
- `mechctl --local`；
- context、完整结构化 CLI 输出和动态 shell completion；
- 生产备份/恢复、升级兼容矩阵和版本化发布流程；
- 国际化与无障碍合规；
- Kubernetes Runtime。

## 6. 产品层建议

1. 把首个可服务用户收窄为“可信内网中的单管理员、1–20 个 Linux 节点、由团队自制或审核 Pack”。不要一开始承诺多团队和数百节点。
2. 为 v0.1 选择 2–3 个可真实运行的官方示例，提供载荷、校验和与完整教程。当前 12 个示例是规范夹具，不是用户 quickstart。
3. 定义 3 个用户旅程作为发布判据：边缘单机首次安装、多节点纳管、组件安全升级/回滚。
4. 把“设计完成”与“实现完成”分开统计。冻结规范也应只在首个公开兼容版本后成立；当前 spec 自己已写明 v0.1 前仍可调整。
5. M10 以可信度和边界收口为目标，不再增加横向功能。
