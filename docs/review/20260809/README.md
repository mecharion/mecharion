## 1. 总结论

Mecharion 已经不是概念验证：Pack 模型、解析管线、资源调和、期望/实际状态、generation、漂移、回滚、多节点身份、Rollout、CLI 与 Web UI 已形成一套相互支撑的产品骨架。项目最有价值的资产不是某个命令，而是围绕“离线优先、声明式期望状态、节点持续调和、组件生命周期”形成的完整概念体系，以及 38 份 ADR 对关键取舍的持续记录。

当前更准确的阶段定位是：

> **设计成熟度较高、核心链路覆盖较完整的工程原型；尚未达到公开 v0.1 的契约稳定度，更未达到生产可用标准。**

不建议重写。建议先用一个短的“边界收口阶段”修复标识符、事务、Join、HTTP 输入边界与认证流程，再统一 CLI/API/文档契约，最后补齐公开发布设施。

## 2. 最重要的判断

### 2.1 应当保留并继续强化的部分

- “Cloudera Manager 的模型深度，管理 Ansible 那样广泛的目标”是清楚且有记忆点的价值主张。
- `mechlet` 是唯一执行引擎、`mechd` 不进入数据面，是正确且贯穿实现的架构主线。
- Pack 的逻辑/载荷分离、内容寻址、generation 不变性、显式缩容与保留数据默认值，体现出难得的运维安全意识。
- Runtime 接缝位于资源调和之下，使 systemd、Docker、Compose 复用上层语义，边界选择合理。
- SQLite WAL、单写者、sqlc、嵌入迁移适合当前规模，也符合单机可诊断目标。
- CI 同时覆盖三平台 Go 测试、Linux systemd E2E、三节点验收与示例 Pack lint，早期项目中罕见地完整。
- ADR 不只写结论，还记录放弃方案与代价；这对 AI Agent 主导、变化快速的项目尤其重要。

### 2.2 首个公开版本前的阻断项

1. **统一校验所有用户可控标识符。** Component 名目前可进入 agent 本地文件名和默认受管路径，存在目录逃逸与误删风险；Node 名还进入离线证书输出路径。
2. **重做 Join 的原子状态转换。** token 校验、节点名占用、节点写入与使用次数增加彼此分离，并发请求可取得同名身份，也可能突破 token 使用上限。
3. **让部署变更原子化。** Component、实例、事实和依赖绑定在渲染成功前分步落库，失败会留下半份期望状态。
4. **给未认证 HTTP 入口增加真实资源边界。** 普通 JSON 请求没有大小上限，服务只有 `ReadHeaderTimeout`；挑战签发也没有真正记账限流。
5. **修正首次初始化认证流程。** Setup 页面要求完成挑战，但请求不提交挑战，服务端也不验证；当前流程只有摩擦，没有对应防护。
6. **停止宣称不存在的 `--local` 能力。** README、二进制帮助和已接受 ADR 对单机模型互相冲突，代码中没有该 flag 或通路。
7. **确定 Pack 信任的发布策略。** ADR 把签名定义为强制安全边界，但 `sign`、验证和可信发布者链均未实现；公开发布前必须调整声明或完成闭环。

完整缺陷、证据和优先级见 [06-defect-register-and-roadmap.md](06-defect-register-and-roadmap.md)。

## 6. 建议的阶段目标

下一阶段不宜继续横向增加名词和命令，建议命名为 **M10：契约与边界收口**，目标是：

- P0/P1 缺陷关闭并有回归测试；
- README、CLI `--help`、HTTP API 与当前实现使用同一份可验证契约；
- 完成一个从安装、导入真实 Pack、部署、改配置、升级、回滚到移除的可复制 quickstart；
- 建立安全披露、贡献、版本、变更日志和可验证发布制品；
- 明确 v0.1 的非目标，不用未来的 RBAC、HA、签名能力描述当前产品。

完成这些之后再发布 `v0.1.0-alpha.1` 会比继续增加功能更能提升项目可信度。
