# 开发迭代记录

## 这是什么

存放里程碑执行过程中**过程性**的内容:任务拆解、执行日志、进行中的取舍、真机验收踩的坑。这里的东西允许写得啰嗦、允许事后看是错的、允许被推翻——它记录的是"怎么做到的",不是"现在是什么"或"为什么这样选"。后两者永远是 [`design/`](../design/) 与 [`adr/`](../adr/) 的职责。

## 为什么单独开一个目录

`design/decision-log.md` 已经积累到 340 余条决策,其中不小一部分其实是实施日记——哪个 sqlc 版本会吃掉字面量引号、哪次三节点真机验收发现了唤醒缺失、哪条测试在 Windows 上"绿错了"。这不是失误,是过去没有专门的地方放这些内容,只能就近记进决策清单。2026-08-09 的[全面审阅](../review/20260809/)把这一点点名为 **REV-027**(P3):"超长 design 混入实施日记和未来愿景"。

这个目录就是那个"就近"该去的地方。规则很简单:

- **过程写在这里。** 一个里程碑/阶段进行中的所有东西——任务表、每次会话的日志、探索性决策、真机验收踩的坑,全部往这里堆,不必顾虑影响 `design/adr` 的可信度。
- **结论回写到 `adr/design`。** 里程碑收尾时,从这里提炼出**还需要被未来的人知道**的部分,按性质分流:

  | 内容性质 | 回写到哪 |
  |---|---|
  | 改变了系统当前形态 | 对应的 `design/NN-*.md` 正文 |
  | 一次有代价的权衡,后人需要理解"为什么" | 新写一份 ADR(`adr/` 只追加,不改历史) |
  | 一条能独立成句的简短决策 | 追加进 `design/decision-log.md`(编号延续,不重号) |
  | 只是"怎么修的""踩了什么坑" | 留在这里就够了,不回写 |

  回写不要求覆盖这里的全部内容——大多数执行细节注定不会被回写,这是设计的一部分,不是遗漏。

## 目录结构

```
docs/dev/
├── README.md                     本文件
├── _template/                     新开一个里程碑/阶段时复制这份模板
│   ├── plan.md
│   └── log.md
└── M10-boundary-and-contract/     一个里程碑/阶段一个目录,命名 `M<序号>-<slug>`
    ├── plan.md                    任务拆解与验收标准;随进度更新状态列,允许改写
    └── log.md                     执行日志;只追加,按时间顺序,历史条目不删除
```

- 目录名延续 [`design/25-roadmap.md`](../design/25-roadmap.md) 的里程碑编号(M0–M9 已完成),不新开一套编号体系。
- 一个目录对应一个已经在 `25-roadmap.md` 挂了号的里程碑;里程碑本身的定义(属于哪个阶段、要交付什么)仍然由 `design/25-roadmap.md` 说了算,这里只放"怎么做到"。
- `plan.md` 是活文档,可以随时改写;`log.md` 是日志,只追加。这条区别对应 `adr`(只追加)与 `design`(可变)的关系,但级别低一层——`plan.md` 本身也不是设计结论,仍属过程,里程碑收尾后随时可能被判定为"这部分不值得回写"而原样留在这里。

## 与 `review/` 的关系

[`review/YYYYMMDD/`](../review/) 是外部只读快照,一旦发布不再修改。这里的 `plan.md` 可以引用其中的编号(如 `REV-001`)作为任务来源,但两者性质不同:review 记录的是"发现了什么问题",dev 记录的是"打算怎么修、修到哪一步了"。修完之后 review 文档本身不用回去改——它如实记录的是审阅当时的事实,后续状态变化体现在 dev 的任务表和(回写后的)decision-log 里,而不是改写快照。

## 何时新开一个子目录

新的里程碑/阶段开工前。按项目一贯的纪律([[design-before-code]]):先把 `plan.md` 写清楚——目标、任务拆解、验收标准,再动代码。
